## Apple 4.3 and 5.6 release gate

Treat Apple 4.3 and 5.6 as engineering requirements, not copy-editing issues. Before implementation, write `.codex-work/differentiation-brief.md` with the concrete user problem, audience, existing alternative, domain model, signature action, task sequence, first useful result, revisit-able outcome, and recovery rules. The shipped app must implement and verify those differences in data, routes, interaction rules, and results on the current iPhone build. A changed name, Logo, palette, gradient, font, image set, copy, card size, or navigation shell alone is not meaningful differentiation and must be recorded as `4.3 risk: Failed`.

Use one real Bundle ID and one consistent product identity. Do not create regional, branded, themed, or batch clones, duplicate App Store records, hidden review modes, reviewer-only content, remote switches that change the submitted product, fake accounts, fake billing, fake services, fake permission results, or fabricated testing evidence. The normal user path and the reviewer path must use the same facts and behavior.

For 5.6, keep developer identity, support information, App Store metadata, screenshots, About, Intro, and Review Remarks truthful and mutually consistent. Do not add custom rating prompts, review incentives, five-star requests, search/ranking/referral/install manipulation, or spam marketing. If a rating request is a real product requirement, use only Apple's system review API and verify that it does not interrupt the core task. Scan for crashes, blank screens, placeholders, dead links, broken permissions, data loss, false buttons, and incomplete core flows.

Run the final audit after listing/About/Remarks generation and record it in `.codex-work/app-review-risk.md`. Include identity, differentiation, review/discovery manipulation, material-fact, and quality checks with current-build or configuration evidence. External network or asset failures may be recorded as `Blocked` while independent local tasks continue, but a critical 4.3/5.6 failure must set `Release readiness: Blocked`; never report submission readiness without evidence.
