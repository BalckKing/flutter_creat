## 17. 记录、证据与发布判定契约

本节定义 `.codex-work/` 内部记录的机器可读边界。它只保存开发过程、证据和判定，不进入 App bundle、`aduit/` 或正式运行时依赖。`.codex-work/` 是用户明确指定的工作目录名，因此在项目自有命名禁用词扫描中作为唯一明确例外；其余项目自有路径仍按第 9.3.1 节扫描。

### 17.1 记录对象

每个 `.codex-work/records/*.json` 文件必须是一个对象，`schema_version` 固定为 `1`，并包含：

```json
{
  "schema_version": 1,
  "run_id": "run-2026-11-18-001",
  "project_root": "/absolute/path/to/flutter-app",
  "bundle_id": "com.example.app",
  "build_id": "debug-2026-11-18T12:00:00Z+abc123",
  "device": "iPhone Simulator",
  "udid": "SIMULATOR-UDID",
  "recorded_at": "2026-11-18T12:00:00Z",
  "freshness_window_hours": 24,
  "status": "Passed",
  "evidence": [
    {
      "path": ".codex-work/evidence/home.png",
      "sha256": "<64 lowercase hex characters>",
      "captured_at": "2026-11-18T11:59:00Z",
      "source": "same iPhone build",
      "kind": "screenshot",
      "build_id": "debug-2026-11-18T12:00:00Z+abc123",
      "device": "iPhone Simulator",
      "udid": "SIMULATOR-UDID"
    }
  ],
  "next_action": "None"
}
```

`status` 只能是 `Planned`、`In progress`、`Passed`、`Failed`、`Blocked` 或 `Not verified`。所有时间戳必须带时区并使用 ISO-8601；未来时间、超过 `freshness_window_hours` 的证据、证据文件不存在、哈希不匹配、构建标识/设备/UDID 不一致均失败。`Passed` 至少要有一项证据。缺少目标工程、记录或真实 iPhone 证据时报告 `Not verified`，不能用资料包检查结果冒充运行通过。

运行 `python3 <skill-root>/scripts/validate_work_records.py --project-root <target-project-root>`。该检查只读，不创建记录、不修改证据，也不把“没有记录”改写成通过。

### 17.2 并行执行与恢复

并行任务统一写入 `.codex-work/execution-state.json`：顶层包含 `schema_version`、`run_id`、`status`、`started_at`、`heartbeat_at`、`retry_count`、`tasks`；每个任务包含 `id`、`status`、`started_at`、`heartbeat_at`、`retry_count`、`resume_action`，阻塞任务另填 `blocked_reason`。运行中超过十分钟没有心跳必须标为可恢复阻塞，先记录恢复动作再跳过，不重复调用同一无变化工具。`queued`、`running`、`passed`、`failed`、`blocked`、`skipped` 是任务状态全集；重试次数必须是非负整数，任务 ID 不重复。

运行 `python3 <skill-root>/scripts/validate_execution_state.py --project-root <target-project-root>`。它验证状态可恢复性，不等待外部服务，也不创建新的后台进程。

### 17.3 能力与真实消费者

非游戏能力矩阵写入 `.codex-work/capability-matrix.json`，每行包含 `capability`、`real_tool_or_sdk`、`version`、`license/source`、`actual_consumer`、`fallback`、`runtime_evidence`、`formula_record` 和 `status`。状态使用 `Selected`、`Implemented`、`Runtime verified`、`Declined fallback` 或 `Not appropriate`。选用能力必须有真实页面消费者、运行证据和六部分效果公式；仅安装包、写入 `pubspec.yaml`、设计稿或静态截图不算消费者。拒绝或不适用必须写明回退或主题依据。

运行 `python3 <skill-root>/scripts/validate_capability_matrix.py --project-root <target-project-root>`。地图、图表、媒体、定位、日历、语音、扫描、3D 等能力继续按第 6.14.5 节使用真实工具与合法数据，不为凑数量安装组件。

### 17.3.1 资源、依赖、无障碍、恢复与安全矩阵

### 17.3.2 统一图片暂存与生成记录清理

所有图片生成、下载、浏览器导出和转码必须先进入 `/Users/admin/Downloads/<sanitized-project-name>/` 这一项目专属根目录，并分为 `logo-candidates/`、`backgrounds/`、`content/`、`exports/`。项目启动时运行 `prepare_asset_staging.py` 写入 `.codex-work/asset-staging.json`；`validate_asset_staging.py` 检查根目录归属、四个子目录、公共 Downloads 根目录是否散落图片、跨项目路径、未登记子目录和符号链接。该暂存根目录位于工程外，不得成为 App 运行时依赖；验收只复制已核验文件到工程 `assets/`。

每个生图批次下载并验收完成后，必须使用 Stargate UI 或明确记录的官方删除动作删除本批记录，不能猜 API 或删除其他项目历史。`.codex-work/generation-cleanup.json` 至少记录 provider URL、下载完成状态、全部 generation task IDs、下载文件路径、`trigger: after_download`、精确删除 task IDs、删除时间、执行方式和证据。运行 `cleanup_generation_history.py`；状态未完成、只删部分、删除早于下载、执行方式不明或证据缺失均为 `Blocked`/`Not verified`。

`.codex-work/quality-matrix.json` 记录最终工程中每个资源、依赖、页面可访问性和恢复场景的实际证据。资源行至少包含 `path`、`asset_type`、`role`、`source_kind`、`source`、`license`、`consumer`、`display_position`、`sha256`、`bytes`、`max_bytes`、`status` 和 `visual_review`；图片的 `max_bytes` 不得超过 `262144`，欢迎页和 Logo 等存在更窄限制时填写实际限制。`sha256`、文件大小、MIME/签名、解码结果和展示位必须与当前工程文件一致，不能用下载链接或规划记录代替。每个资源都要能追溯到真实页面/服务消费者，不能把公共 Downloads、临时目录或仅在清单中出现的文件标为通过。

依赖行至少记录 `name`、精确 `version`、`license`、`source` 和实际 `consumer`；包已安装、写入 `pubspec.yaml` 或出现在设计稿中都不算消费者。`accessibility` 为逐页面矩阵，至少记录 VoiceOver、Dynamic Type、Reduce Motion 和对比度状态及当前构建证据。`resilience` 必须覆盖 `offline_cold_start`、`permission_denied`、`foreground_background` 和 `clear_data_interrupted`，记录预期、实际观察、状态和证据；不适用场景也要明确写 `Not applicable` 与理由。`security` 记录密钥/令牌扫描状态和证据，源码、配置、构建输入和脚本中不得留下真实 API key、私钥或密码。

运行 `python3 <skill-root>/scripts/validate_quality_records.py --project-root <target-project-root>`。检查器会校验文件哈希/大小、图片签名和 256 KB 上限、来源/许可证/真实消费者、四类无障碍状态、四类恢复场景和可疑密钥；缺少矩阵或目标工程时返回 `Not verified`，不把资料包静态检查改写成运行通过。

### 17.4 产物级门槛

最终 iOS 检查必须同时区分源配置与可用产物：`Info.plist` 可解析；`ios/Flutter/AppFrameworkInfo.plist` 有标准 `MinimumOSVersion`；使用 CocoaPods 时 `Podfile` 存在且 `ruby -c` 通过；实际需要 PhotoKit 整库读写时，从 Podfile/解析后 Pods 配置确认 `PERMISSION_PHOTOS=1`；ATT 的用途键、请求 API、框架、宏、IDFA 访问和追踪初始化全部没有残留。未提供 `.app`/Archive 时产物状态必须是 `Not verified`。

运行 `python3 <skill-root>/scripts/validate_ios_artifacts.py --project-root <target-project-root> [--photo-access none|picker|read-write|add-only] [--artifact <path>]`。缺少真实工程时不在资料包内创建伪工程。

最终 `aduit/` 只能有 `intro.md`、`welcome.html`、`imgs/`、`site/` 和 `review/`；`site/` 只能有与 `aduit/welcome.html` 字节一致的 `index.html`、三个固定协议页和 `img/logo.png`；不得有其他 `index.html`、符号链接或本地协议 HTML 副本。声明最终交付时，`aduit/imgs/` 必须恰好有五张原始 1206×2622 PNG。

运行 `python3 <skill-root>/scripts/validate_aduit_allowlist.py --project-root <target-project-root> [--final]`。该检查不把目录存在当作截图内容已验收。

### 17.5 最终 release-readiness

`.codex-work/release-readiness.json` 汇总 `runtime`、`ios_artifacts`、`aduit`、`quality_records`、`asset_staging`、`generation_cleanup`、`logo_quality`、`git_handoff` 等门槛，顶层必须有带时区的 `generated_at`，每行包含 `name`、`status`、非空 `evidence` 路径；失败或阻塞行必须有 `blocker`。`asset_staging` 必须引用 `asset-staging.json` 与其验证结果，`generation_cleanup` 必须引用 `generation-cleanup.json` 与其验证结果。只有全部适用项为 `Passed`/`Not applicable`、没有 `Not verified`、没有阻塞，且文件中的 `release_readiness` 正确写为 `Ready for submission`，才可输出该结论；否则输出 `Not ready`，并列出 `Failed`、`Blocked` 和 `Not verified` 缺口。

运行 `python3 <skill-root>/scripts/validate_release_readiness.py --project-root <target-project-root>`。资料包本身没有真实 App，因此资料包回归不得生成 `Ready for submission`。

### Welcome HTML 的 site 交付副本（本轮硬规则）

生成和精修 `aduit/welcome.html` 后，按字节复制一份为 `aduit/site/index.html`。`site/index.html` 只是 Welcome 交付副本，不是协议索引、协议选择页或 App 运行入口；校验时必须与 `aduit/welcome.html` 字节一致。`aduit/site/` 最终只允许 `index.html`、`PrivacyPolicy.html`、`Terms&Conditions.html`、`Support.html` 和 `img/logo.png`，不允许其他首页或额外 HTML。App 运行时仍只使用 `lib/welcome.dart`，不加载或打包这些 HTML。

## 通用 `final_visual_product` 最终视觉成品门禁（硬门槛）

功能垂直切片只证明技术闭环；它不是最终视觉成品。游戏、非游戏和混合项目都必须另行通过 `final-visual-product.json` 的最终视觉成品门禁。未通过时只能记录 `Blocked`/`Not verified`，不得生成最终截图、发布材料或 Git handoff。

阶段顺序固定为：`technical_vertical_slice → full_scope_implementation → final_visual_product → release_materials → Git handoff`。垂直切片通过后必须继续完成已确认的全部领域/游戏范围、页面、内容、资源、状态、错误恢复和视觉精修，再建立项目根目录 `.codex-work/final-visual-product.json`；切片证据、引擎依赖、单张截图、默认控件或可点击首屏均不能单独设置最终完成状态。

`final-visual-product.json` 必须明确 `schema_version: 1`、`project_type: game | non_game | mixed`、`claim: final_visual_product`、`development_stage: final_visual_product`、`prototype_boundary.vertical_slice_status: Passed` 与 `prototype_boundary.cannot_substitute_for_final: true`。公共契约必须记录 `no_simple_line_art`、`no_flat_color_blocks`、`no_solid_color_background`、`no_placeholder_or_static_mock`、至少三轮 `refinement_rounds`、`authored_asset_review`、`composition_review`、`motion_review`、`state_coverage_review`、`accessibility_review` 和当前同一 iPhone 构建证据。

游戏项目还必须提供最终 `2.5d` 或 `3d` 视觉契约：主题化成品资产、前中后景或等价空间层次、相机/遮挡、材质与光影、状态变体、动画/粒子反馈、清楚 HUD、完整玩法范围和当前 iPhone 运行证据。非游戏项目必须提供领域专属视觉语言、至少三个不同结果或页面构图、真实 UI/动效/渲染组件的精确版本/许可证/实际消费者/运行证据、具有主体与材质深度的图像层、完整状态覆盖和当前 iPhone 运行证据。混合项目必须同时通过游戏与非游戏两套契约；非游戏没有游戏引擎时，视觉完成度、真实消费者、状态覆盖和运行证据门槛不降低。

最终报告、公开文案、`release-readiness.json`、截图说明、Review Remarks 和 Git handoff 报告不得把当前交付称为 `prototype`、`functional demo`、`rough build`、`visual prototype`、`unfinished`、`to be polished` 或等价的未完成状态。早期历史记录可以描述原型或垂直切片，但必须明确它是早期阶段；最终状态只能使用 `Passed`、`Failed`、`Blocked` 或 `Not verified`。运行 `python3 <skill-root>/scripts/validate_final_visual_product.py --project-root <target-project-root> --json`，并在发布就绪记录中保留 `final_visual_product` 门禁及其证据。
