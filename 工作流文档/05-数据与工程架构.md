## 8. 状态、数据与持久化

### 8.1 状态层

- `AppState`：启动阶段、首次使用介绍展示记录、当前目的地/任务导航状态和全局错误；具体字段由选定导航决定，只有实际存在 Tab 时才维护选中 Tab，不为无 Tab 项目创建 `selectedTab` 或固定下标。
- `AppFlowState`：内存中的 `welcome`、`active`、`clearing`、`exiting` 与条件性的 `entry`。`entry` 只能表示采用 `Clear Data` 的项目在同一进程内完成真实清除后的返回页，不是初始状态或正常启动目标；初始状态始终是 `welcome`。结束模式按第 7.7 节由已确认功能与数据清单确定。打开确认框保留来源状态，确认后才进入所选模式的执行状态并防重复/隔离旧回调；只有 Clear Data 的真实成功才转 `entry`。clear 的破坏性步骤失败与重启按第 8.5 节恢复；exit 仅结束当前会话，不删除数据/偏好或建立删除标记，成功后留在当前可恢复边界，失败显示可重试状态，新进程正常进入 Welcome。任何状态均不含身份/认证信息、不持久化路由或伪造登录状态。
- **启动状态机硬契约**：`new process → welcome → active`（仅由 Welcome 的 `Continue` 进入）；`active → clearing → entry` 只在项目采用 `Clear Data`、用户确认且全部清除核验成功后成立；`active → exiting → active/current boundary` 用于 `Exit App`，成功不得创建、注册或打开 `/entry`；清除中断、失败、取消、后台恢复及旧回调均先回到 Welcome 或原来源状态，不得自动显示 Initialization。不得从持久化路由、上次页面或启动标记直接恢复到 `entry`。用户可见按钮文案固定为 `Enter`；`/entry` 只是内部路由名，禁止把 `Entry`、`ertyr`、`entryr`、`entyr`、`entery` 或 `enrty` 作为按钮文案。
- `EndActionState`：选定模式 clear/exit、确认框来源与显示状态、操作 ID、实际资源停止/释放、真实阶段/进展、失败与可重试性。clear 才包含实际删除/默认重建及第 8.5 节最小持久化恢复标记；exit 只做会话收尾/导航复位，不创建虚构删除阶段。已有 `ClearDataState` 可作为 clear 专用状态复用，展示文案由同一模式配置提供。
- 按实际任务/模块划分状态对象，维护所需的查询、筛选、排序、视图、内容、加载、空、错误、成功及任务草稿；单一工作台不为凑导航拆成多份重复状态。目的地返回和切换时保留适用状态，清除成功后统一重置。
- `DetailState`：内容加载、展开区段、相关内容，以及第 10.1.1 节确认确有公开义务时才使用的必要署名；不默认加载或展示素材来源清单。
- `PlayerState`：媒体来源、位置、控制器生命周期、重试和中断。
- `PolicyState`：本地文档读取状态、错误原因、标题和文档版本；版本属于文档元数据，不是个人同意记录。
- `CaptureState`、`ImportState`、`RecordingState`：仅为实际选用的拍照、导入、录音分别建立，未选项不建；处理实际所需权限、设备准备、采集中、预览、保存、取消、错误和已释放状态；回调带操作标识，旧任务不得覆盖新状态。
- `LocalMediaState`：仅在存在用户私有媒体时管理已保存媒体、主题关联、预览/播放、删除与存储错误；`PermissionState` 仅在实际 API 需要授权时建立，从系统读取对应状态。三项媒体可全部不存在；无受保护 API 时不添加权限状态、服务或权限插件，也不添加追踪授权状态。

### 8.1.2 主题 iOS 能力矩阵（硬门槛）

非游戏项目按主题价值主动评估照片/相机、麦克风/语音、通知、定位/地图、日历/提醒事项、联系人/分享、文件、蓝牙/NFC、运动/HealthKit 和其他适配度高的 iOS 能力。每项写入能力矩阵并记录真实页面入口、API/插件、用途键、权限宏或 entitlement、授权时机、拒绝降级和运行证据；状态只能是 `Selected / Implemented / Runtime verified / Declined fallback / Not appropriate`。适用能力必须实现，不得只放弹窗或占位页；不适用必须说明主题与平台依据。ATT、IDFA、追踪授权和广告能力保持移除。

### 8.1.1 Flutter 原生导航与 GetX 禁用（硬门槛）

- 全项目禁止 GetX：不得在 `pubspec.yaml`、Dart 源码、生成配置或实际依赖树中加入 `get`，也不得使用 `GetMaterialApp`、`GetCupertinoApp`、`GetX`、`GetBuilder`、`Obx`、`GetPage`、`GetController`、`Rx`、`.obs`、`Get.to`、`Get.off`、`Get.offAll`、`Get.back`、`Get.dialog`、`Get.bottomSheet`、`Get.snackbar`、`Get.put` 或 `Get.find`。不使用 `go_router`、`auto_route` 等外部路由框架。
- App shell 必须使用 Flutter 原生 `MaterialApp`、`CupertinoApp` 或 `WidgetsApp`；页面跳转使用 `Navigator.of(context)` / `NavigatorState` 的 `push`、`pop`、`pushReplacement`、`pushAndRemoveUntil` 等 API，并使用 `MaterialPageRoute`、`CupertinoPageRoute`、`PageRouteBuilder`、`RouteSettings` 或 `NavigatorObserver` 表达路由。
- Welcome 的 `Continue`、Initialization 的 `Enter`、Settings、三个协议 WebView 入口以及主流程页面都通过同一套原生 Navigator 图连接；状态使用 `StatefulWidget`、`setState`、`ChangeNotifier`、`ValueNotifier`、`InheritedWidget`、`ValueListenableBuilder` 等 Flutter 原生机制，不能用 GetX 状态或服务定位 API。
- 验收运行 `scripts/validate_flutter_navigation.py --project-root <实际 App 根目录>`，同时扫描 `pubspec.yaml`、Dart 源码、原生配置和实际构建依赖；页面能够打开不能替代依赖与 API 扫描。

### 8.2 本地持久化白名单

只持久化确实能改善核心体验的数据：

- 不保存颜色、明暗模式或外观切换偏好；复用工程停止读取这些旧键，按第 6.2 节定点清理，不影响实际业务偏好。
- 首次使用介绍展示记录；只调整所选结束操作成功后 Initialization 的内容展示，不作为进入条件；不改变每次启动进入 Welcome 的规则。
- 如果需要，保存英文 locale 标记。
- 与主题相关的筛选偏好。
- 主题确实需要时保存当前浏览或媒体位置。
- 仅实际具备对应功能时持久化用户明确保存的照片、导入文件、录音、主题关联与必要元数据，以及准确的格式、尺寸或时长；文件仅放在 App 私有目录，临时采集不作为已保存内容。

不得持久化邮箱、密码、验证码、登录状态、认证令牌、个人协议同意记录、远程账号凭据、社交、云端媒体上传、社区或个人资料数据，不建立用户账号实体。`AppFlowState` 不写入本地存储，也不从旧登录记录恢复；实际选用的本地导入、采集与私有媒体索引才按上述白名单保存。保存/删除事务和全量清除可持久化最小故障恢复信息，仅用于保证数据一致性，不记录身份、媒体正文或个人协议同意；成功后移除相应标记。clear 模式下白名单中的用户数据与偏好均属于第 8.5 节的全量清除范围；exit 模式保留持久化偏好与随包内容，只结束当前会话和导航，不为退出创建或删除用户数据。

### 8.3 内容模型

根据用户创意生成聚焦而完整的领域模型。以下 `ContentItem` 仅是内容浏览类 App 的字段示例，不是所有主题的必选模型；模型名称、实体关系和字段均由实际核心功能决定，不得为了套用示例把产品改成阅读或媒体浏览工具。

```text
ContentItem {
  id,
  title,
  subtitle,
  category,
  tags,
  description,
  mediaRefs,
  duration,
  source,
  license,
  attribution,
  searchableText,
  sortWeight,
  consumerScreens
}
```

列表的 `featured`、`standard`、`compact` 等视觉角色属于页面展示策略或 ViewModel，不是领域事实；只在确有策展/排序意义时存储相应稳定标记，不把屏幕像素尺寸、卡片高宽或随机样式写入核心领域实体。用共享的列表呈现策略将语义角色映射到可响应式调整的布局尺寸，并保证排序、筛选、数据身份和 VoiceOver 顺序不受外观层级意外改变。

主要内容集合按第 4.4 节建立稳定唯一 ID、确定排序、查询/筛选快照和无重叠页边界，数据与页面索引明确当前批次/终点；防止重复追加、过期请求覆盖、详情返回丢失位置或末页循环回填。全量 ID 去重与页间交集校验结合语义复核，不把相同内容改措辞视为新条目。

每个可见条目都必须对应本地模型；随包媒体对应资源清单条目，若存在用户运行时拍摄、导入或录制的媒体，则使用私有本地索引，不写入随包清单、公开归因页或日志。私有媒体模型至少记录 `id`、`sourceType`、`localPath`、`mediaType`、`createdAt`、`sizeBytes`、适用的 `dimensions`/`duration` 与主题记录关联，不保存无用途的定位或身份元数据。缺失字段或文件必须产生可观察的空/错误状态，不得静默忽略。

内容模型和资源清单中的 `source`、`license`、`attribution` 用于内部追溯，不要求生成可见来源区；UI 只按第 10.1.1 节提供确有义务的必要声明。`PlayerState` 的媒体来源指实际加载输入及生命周期，不代表必须展示供应商或下载地址。

### 8.4 本地媒体事务、存储与故障恢复

仅对实际选定并保存用户媒体的功能适用，按已有来源实施所需事务；没有这些能力时不创建媒体仓库、采集/导入/录音服务或索引。其他主题数据仍须可靠保存与恢复。

- 区分随包只读资源、可清理的派生缓存、待提交临时采集和用户已保存媒体；永久文件放在稳定的 App 私有目录，不使用系统可能回收的临时目录。主题记录持久化稳定媒体 ID，由服务解析当前沙盒路径，不依赖安装后可能变化的绝对沙盒前缀。
- 保存使用唯一操作 ID，先写临时文件并校验实际格式、可读性及必要元数据，再在同一文件系统完成原子移动并提交索引/主题关联。文件操作与数据库不假称天然处于同一事务；使用可恢复的暂存记录或等价提交协议，只有文件与关联均提交后才向 UI 报告成功。失败保留可重试的当前预览或回滚本操作，重复点击不生成重复记录。
- 启动或进程中断后核对待提交操作、缺失文件、孤立暂存文件与索引，不误把用户内容当缓存清掉；恢复不能阻塞全部启动，按第 7.1 节延后处理非关键扫描。对已保存内容的损坏提供具体错误与恢复路径，不静默覆盖或伪造空列表。
- 删除只针对用户明确选中的媒体 ID，先停止其预览/播放，处理所有实际关联，再清理该媒体文件、派生内容与索引。可用删除标记支持失败重试，部分清理失败不能显示已全部删除；不得删除其他记录仍引用的文件、系统相册原件或无关项目数据。
- 不按性能预设单文件大小、导入批量、录音时长、缓存或空间配额；主题本身确有的业务边界写入方案。运行前检查实际可用空间并处理写入期间耗尽，避免数据损坏。使用流式复制/受限解码处理大文件，导入取消、录音停止和确认后的全量清除均有反馈；普通取消与空间管理只清理本操作临时文件，不擅自删除已保存媒体，用户明确确认的全量清除另按第 8.5 节执行。
- 文件保护、备份排除、缩略图与临时文件的生命周期一并核验；目录遍历、文件名碰撞、失效路径和过期回调不能覆盖已有内容。日志只记录脱敏操作与错误，不输出私有媒体路径、正文、缩略图或音频数据。
- 保存、单条删除、存储恢复与全量清除共享写入协调机制。全量清除先阻止新事务，再让已进入提交阶段的操作完成或可靠回滚，随后删除其目标内容；迟到回调不得提交到已重置的数据集。不能让启动恢复服务在清除期间重新导入孤立文件或重建已删除记录。
- 导入与采集只保留主题确实需要的元数据；不需要的位置、设备标识等嵌入元数据应从 App 自有副本安全移除，并复验方向、色彩和可读性，不改动系统相册原件。不能只删除索引字段就声称已去除文件内 EXIF 等信息。

### 8.5 全量清除范围与中断恢复

本节仅适用于第 7.7 节确认存在用户内容、采用 clear 模式的项目。无此类数据的 exit 模式不套用此删除表、默认偏好重置或删除恢复标记，按第 7.7 节执行会话收尾与成功返回 Initialization；不能为了沿用清除实现暗中删除偏好。

为每个实际使用的本地存储登记所有者、位置、清理方式和验证依据，所有清理限制在已核实的 App 自有数据项与目录；不靠广泛递归删除整个沙盒、共享容器、系统照片库或开发工作目录完成清理。新增数据类型、SDK 或缓存时同步更新此清单、确认文案、隐私政策和验收用例。以下按实际存在的类型裁剪，未选媒体能力不生成对应数据、索引或清理服务；清除确认只列真实数据范围。

| 数据范围 | 清除或保留规则 |
| --- | --- |
| 用户媒体与主题数据 | 仅删除实际存在的 App 私有拍摄照片、导入副本、录音、可变主题记录、关联、索引与元数据；共享引用在全量清除中统一处理，不留下孤立副本 |
| 临时和派生内容 | 删除暂存/未提交文件、缩略图、波形、转码文件、App 私有的迁移/恢复副本与旧版本数据、运行时下载缓存及磁盘/内存缓存；旧后台任务不能重新生成 |
| 本地设置 | 清除介绍展示记录、locale 偏好、筛选、排序、视图、浏览/播放位置等实际持久化项，重新初始化默认值；不保留旧偏好 |
| WebView 与第三方本地状态 | 清理实际存在的 App 自有 WebView 缓存、Cookie、网站存储及 SDK 本地缓存；使用平台/插件支持的接口，核验覆盖范围，不清除系统浏览器或其他 App 的数据 |
| 随包只读内容 | 保留 Logo、AppIcon、许可素材、种子内容、About/Support、协议及版本信息；重新从种子源构建默认内容，不重新下载、不冒充用户媒体 |
| App 外的数据与系统状态 | 不删除系统相册原件、已经导出到 App 外的文件或现存备份，不重置 iOS 摄像机/相册/麦克风授权；后续状态从系统读取 |
| 开发产物与恢复标记 | 不涉及源码、资源源文件或开发目录 `aduit/`；运行时恢复标记仅在全部清理与重建核验通过后移除，失败时保留 |

清除操作使用稳定的操作 ID 和数据版本/代次，恢复标记在破坏性步骤开始前以原子写入/替换方式可靠落盘，并验证实际提交状态；只包含恢复所需的操作、阶段和未完成项，不记录媒体正文、身份或协议同意。该标记与待清数据分离，不能被清理设置/数据库的步骤先行删除。逐阶段更新并验证实际结果，数据库连接、事务、旁路文件与 SDK 存储按实际实现关闭/清理，不能只清空 UI 列表或删除一个数据库文件就算完成。

进程关闭、崩溃或后台中断后，先读取标记并隔离旧数据，幂等继续已确认的清除，不再次询问是否清除；已完成步骤可核对后跳过，缺失目标视为该项已删除，真实错误仍须重试或显示可恢复失败。清除过程中无网络也能执行。默认数据重建使用随包源，只恢复示例与默认设置，不恢复被删除的用户媒体；恢复服务、旧事务和迟到回调不得跨数据代次提交。

成功判定须核对实际存在的用户文件、主题记录、索引/关联、派生文件、临时项、偏好、WebView/SDK 存储、内存状态及在用设备释放；任一实际目标未清理就不能标记成功。移除恢复标记是最后的持久化完成步骤，完成前不开放 `Enter`。不承诺物理安全擦除、删除系统备份或删除 App 无法管理的副本，隐私政策与 UI 必须使用准确的范围说明。

### 8.6 数据版本与升级兼容

种子清单、用户数据与偏好使用明确版本；更新 App 时迁移应保留已有用户媒体与稳定 ID、关联和合法偏好，不把升级当作清除。迁移先验证可读性与恢复路径，失败保留原数据并给出可恢复错误，不以解析失败、未知字段或缺失文件为由静默重置；临时迁移副本也纳入 App 自有数据与备份边界。存在未完成清除时优先处理该操作，禁止迁移或恢复旧副本重新带回已删除内容。只有当前结构确有迁移需求时实现对应迁移，不添加无用途的数据库层。

## 9. Flutter 工程架构

以下仅示意职责边界与固定路径契约，不是所有项目必须复制的模块树或页面骨架。按第 9.5 节为当前项目定制领域模块、状态流、导航和视觉风格；涉及游戏时再执行第 9.6 节。复用已有项目时保留兼容的业务状态结构，但 GetX 永远禁止，导航必须迁移到 Flutter 原生 Navigator；同时遵守第 9.3.1 节命名，不为凑目录机械重写。新增 Dart 文件采用 `lower_snake_case`；已有外部引用文件改名时同步引用并验证，不能仅按示意树批量重命名。

本工程只生成 iOS 平台目标，应用设备 family 固定为 iPhone；最低 iOS 部署版本为 15.6，默认设置为 15.6，实际依赖要求更高时保留更高版本并记录依据。创建参数、各构建配置、运行目标与产物检查统一按第 0.10 节执行。架构树不新增其他平台目录、入口、适配层或打包脚本；可注入服务只用于隔离边界和故障注入；不以单元/Widget/集成测试代替 iPhone Simulator 上的真实 App 验收，不用跨平台运行代替 iPhone 验收。

`ios/Podfile` 是 iOS 权限插件的构建配置来源之一。依照第 0.7 节，在确认插件和 API 后尽力设置最小权限宏；若当前 API/插件需要 PhotoKit 整库读取宏，最终 Pods 编译设置必须包含并生效 `PERMISSION_PHOTOS=1`，不能把缺失该宏当作可忽略的警告。只用 PHPicker/系统照片选择器时不启用整库读取宏。若宏配置失败，使用最后一个语法有效版本继续安装 Pods 并尝试打包，同时单独记录宏状态和权限验证缺口；不能把受影响路径标为通过。宏配置失败本身不是停止打包的条件。按第 0.7 节不启用 ATT，清除其框架/API、用途键、IDFA 访问与启用宏，不保留空请求路径。

### 9.1 最低 iOS 部署版本

创建工程时显式设置 `platform :ios, '15.6'`（或实际依赖要求的更高版本），并将 Runner、UI 测试和其他实际参与构建的 target 在 Debug、Profile、Release 及自定义配置中的 `IPHONEOS_DEPLOYMENT_TARGET` 设为不低于 15.6。执行 `pod install`、Flutter iOS 构建及归档前后，使用 `xcodebuild -showBuildSettings` 或等价工具核对解析后的值；最终 `.app`/Archive 的 `MinimumOSVersion` 也不得低于 15.6。若 CocoaPods、插件、Flutter 或 Xcode 要求更高版本，统一提升相关设置并在 `.work/` 记录原因、依赖版本和证据，不通过修改 `Info.plist` 伪造版本，也不降级依赖规避要求。

### 9.1.1 最新稳定版 iOS 与 UIScene 生命周期（硬门槛）

每个新建及复用项目都必须适配执行当日最新正式稳定版 iOS 的应用、Scene 和 Flutter engine 生命周期。最低部署版本与最新 SDK 兼容性分开检查：继续遵守第 9.1 节的 15.6 或真实依赖要求的更高下限，不通过把最低版本直接升到最新系统来代替迁移。此门槛不受主题、功能随机组合、硬件档位或是否提出性能指标影响。

**先核实版本与迁移依据**：在已有 `.work/quality.md` 登记核查日期、Apple/Flutter 官方依据、当前 `flutter --version`、`flutter doctor -v`、`xcodebuild -version`、实际选用 SDK、可用 iPhone runtime，以及本项目采用的稳定版本组合。执行时重新核对官方版本和 breaking changes，不把文档示例、Remarks 固定设备名单、已装 runtime 或 beta 当作“最新稳定版”。官方依据为 [Flutter UIScene 迁移说明](https://docs.flutter.dev/release/breaking-changes/uiscenedelegate) 和 [Apple 应用生命周期说明](https://developer.apple.com/documentation/uikit/app_and_environment/managing_your_app_s_life_cycle)。当前 Flutter 说明明确：Xcode 27／iOS 27 SDK 构建的 UIKit App 未采用 UIScene 会启动失败；Flutter 3.41 起默认使用 UIScene，自动迁移仅覆盖符合条件的未定制工程，旧工程和自定义 AppDelegate 必须人工核验。选用能支持目标 SDK 的稳定 Flutter/插件组合，不因 `flutter create` 或编译成功就假定迁移完成；确需工具链调整时采用项目隔离方式，不擅自改动影响其他项目的全局 Flutter/Xcode 选择。官方资料暂不可用时保留最近有来源的依据、记录核查缺口，继续可执行工作，不虚报版本已确认。

**原生入口与配置必须成套落地**：

1. 核对实际 scheme/target/configuration/flavor 使用的 AppDelegate、SceneDelegate、`Info.plist`、storyboard 和构建 phase，包括生成式 plist 与覆盖项。最终产物必须解析出有效的 `UIApplicationSceneManifest`，`UIWindowSceneSessionRoleApplication` 配置指向真实存在、可加载的 Scene delegate；如 `configurationForConnecting` 动态返回配置，必须与 manifest、类名及实际 storyboard 一致。iPhone 单窗口项目默认 `UIApplicationSupportsMultipleScenes = false`，不为迁移增加多窗口功能。
2. 标准 Flutter 工程可直接使用 `FlutterSceneDelegate`，无需为凑文件创建空自定义类。确有原生承接层或 Scene 回调定制需求时，按当前 Flutter 官方方案继承 `FlutterSceneDelegate` 并保留应调用的 `super`；Swift 自定义类的 plist 类名使用 `$(PRODUCT_MODULE_NAME).SceneDelegate`，Objective-C 按其真实运行时类名配置，源文件必须加入当前 Runner target 编译。已有自定义 Scene 集成按官方 `FlutterSceneLifeCycleProvider` 方案接入，不覆盖原有有效职责。
3. 以下只是标准 Main storyboard 工程的配置示意，必须合并既有配置并核对最终包；自定义类/动态配置/无 storyboard 工程按实际入口调整，不盲加 `Main`，也不能把 `LaunchScreen` 当作应用 Scene 的内容 storyboard：

**插件、通道和窗口就绪时机**：标准隐式 engine 工程让 AppDelegate 遵循 `FlutterImplicitEngineDelegate`，在 `didInitializeImplicitFlutterEngine(_ engineBridge: FlutterImplicitEngineBridge)` 中使用 `GeneratedPluginRegistrant.register(with: engineBridge.pluginRegistry)`；依赖 engine 的 MethodChannel/平台视图注册使用该 engine 的 registrar/messenger，并确保每个实际 engine 只注册一次。显式 engine、已有 add-to-app 或其他自定义启动方式须保持其正确的创建/注册顺序，不机械套用隐式回调或重复注册。不得在 `didFinishLaunchingWithOptions` 中用 `window?.rootViewController as! FlutterViewController` 强制访问尚未建立的窗口，也不靠延时猜测 engine 可用；App 级初始化仍保留在其正确的回调，例如实际使用的 BGTaskScheduler 注册须在系统规定的启动时机完成，不把全部代码一股脑迁入 engine 回调。

采用 UIScene 后，UI 相关的 AppDelegate 生命周期不再作为 Scene 回调的替代。将实际使用的激活/失活、前后台、URL、Universal Link 和启动连接数据分别迁入 `sceneDidBecomeActive`、`sceneWillResignActive`、`sceneWillEnterForeground`、`sceneDidEnterBackground`、`scene(_:openURLContexts:)`、`scene(_:continue:)`、`scene(_:willConnectTo:options:)` 等对应位置。核对冷启动的 `connectionOptions` 和运行中的后续事件，各消费一次，不漏收或重复导航；没有相关产品功能时不增加 deep link、后台模式、权限或服务。实际依赖 Scene 事件的插件核对其版本和 `FlutterSceneLifeCycleDelegate`／`registrar.addSceneDelegate` 支持，保留父类转发，避免 MissingPluginException、无效 messenger、重复回调和未识别 selector。

**Scene 与原生启动承接层联动**：第 10.4.3 节的遮罩必须绑定当前有效的 `UIWindowScene`、实际窗口、engine 和启动操作代次；通过正确 Scene 的连接/窗口建立时机安装，所有 UIKit 变更在主线程。不得依赖废弃的全局 keyWindow、任取 `windows.first`、过早读取 AppDelegate.window 或另建无归属窗口。准备中的 Scene 失活、断开、重连或窗口替换时取消/清理旧订阅、计时器和动画，迟到回调不得操作已释放窗口；实际恢复时按该节重新核实首屏与前台连续 250 毫秒保持，再淡出。普通前后台恢复保留当前有效页面和数据，不重新进入 Welcome、不重放遮罩；新进程启动仍进入 Welcome，只有 Clear Data 确认且真实成功才进入 Initialization，Exit App 成功留在当前边界。

**Flutter 侧状态与资源清理**：用当前稳定 Flutter 支持的 `AppLifecycleListener` 或 `WidgetsBindingObserver.didChangeAppLifecycleState` 统一管理 `resumed`、`inactive`、`hidden`、`paused`、`detached` 的实际语义，区分进程、Scene、路由可见性和 Widget dispose。权限弹窗/系统面板导致的临时 inactive 不是退出或清除数据；后台/不可见页暂停动画、粒子及实际使用的媒体采集/播放，恢复只重启当前有效页面的活动，不重建多份 controller 或重新请求权限。处理不保证逐项到达的生命周期事件与进程直接终止：保存走已有事务和中断恢复，不依赖最终回调才落盘。取消/销毁幂等，异步回调核对 mounted、操作代次与资源有效性，防止 setState after dispose、销毁后绘制/调用平台通道或清除后的旧事务回写；修复不缩减已确认的 UI 效果。

完成后按第 11.1.1 节对当前构建验收；不能通过删除/禁用 Scene manifest、压制迁移警告、降低 SDK、空指针强转、吞掉异常或加启动等待来冒充兼容。源码配置、编译、安装启动和前后台恢复分别记结果；最新稳定 runtime/真机不可用时对应项为 `Blocked`／`Not verified`，继续其他独立任务与完整材料生成，但不得报告该生命周期门槛通过或发布就绪。

### 9.1.2 打包前源配置补齐与复验（硬门槛）

新建或复用的 Flutter iOS App，在首次 Pods 安装/构建前及最终打包预检前，实际检查 `ios/Flutter/AppFrameworkInfo.plist`。文件名为 `AppFrameworkInfo.plist`，标准键必须是 `MinimumOSVersion`，大小写敏感；`MinimumoSVersion` 等拼写不能代替。该键为非空数字版本字符串，按第 9.1 节的实际最低部署版本设置，至少 15.6，已有更高值不得降低。保留其他 plist 内容。文件缺失或无效时，按当前 SDK 的真实模板恢复/合并，不用只含一个键的假 plist，也不覆盖整个 `ios/`。

部分 Flutter SDK 模板省略该源键，并在构建时给 App.framework 的 plist 写入版本；迁移也可能删除旧固定值。外部打包预检若读取源文件，仍可能报告缺少键。因此源配置兼容检查和真实构建产物核验均须执行：补源键不能代替 `IPHONEOS_DEPLOYMENT_TARGET`，也不能证明 App 或 App.framework 实际可运行。

使用当前技能随包的 `scripts/prepare_ios_config.py`。以下示例适用于已确认通过 CocoaPods 使用 `permission_handler_apple`、且真实调用 PhotoKit 读写授权的工程；将两个路径替换为当前技能目录和实际 App 根目录，将版本替换为已核对的部署下限：

```bash
python3 "<当前技能目录>/scripts/prepare_ios_config.py" \
  --project-root "<实际 App 根目录>" --minimum-ios 15.6 \
  --photo-access read-write --permission-handler --apply
```

- `read-write` 设置 `PERMISSION_PHOTOS=1`、`PERMISSION_PHOTOS_ADD_ONLY=0`；`add-only` 设置读写宏为 0、`PERMISSION_PHOTOS_ADD_ONLY=1`，不冒充整库读写授权。仍按真实 API 配齐相应用途键。
- 仅系统选择器选中项用 `picker`，无照片 API 用 `none`；两者不增加整库授权。已因其他权限保留共享插件时仍传 `--permission-handler`，将其两个照片宏设为 0；未通过 CocoaPods 接入该插件时不传此 flag、不改 Podfile，按实际插件/集成方式验证。
- 受管宏块放在唯一现有 `post_install` 的末尾，只配置 `permission_handler_apple` 的全部 build configurations，保留继承及相机、麦克风和自定义宏；共享插件的 `PERMISSION_APP_TRACKING_TRANSPARENCY=0` 不代替专用 ATT 依赖、请求和链接清理。遇到缺失 Podfile、多个 Hook、无法安全修改的语法或无效 plist，工具报错并保留源文件，按真实配置人工恢复/合并后复验。
- 默认不带 `--apply` 为只读检查，发现需补齐内容返回非零；带 `--apply` 时先验证全部计划、备份到 `.work/ios-config-backup/` 再原子替换，可重复执行。写入后的 JSON `build_verified: false` 明确表示尚未验证构建。先保存错误和命令结果，宏配置失败仍按第 0.7 节继续可执行的 Pods/构建尝试，不将缺少必需宏判为通过。

应用后去掉 `--apply` 运行同一命令复查，并对源 plist 执行 `plutil -lint`、对 Podfile 执行 `ruby -c`。CocoaPods 工程从实际 `ios/` 目录运行 `pod install` 后，用 `xcodebuild -project ios/Pods/Pods.xcodeproj -target permission_handler_apple -configuration <实际配置> -showBuildSettings` 或等价解析证据逐个核对真实配置中的 `GCC_PREPROCESSOR_DEFINITIONS`，不能只搜 Podfile 文本或 Runner；target 名按实际解析结果确认。构建/归档后检查实际 App 及内嵌 `App.framework/Info.plist` 中的 `MinimumOSVersion` 与部署设置兼容，并复验照片授权路径。若构建迁移再次删除源键，按本节重新补齐并重跑读取源文件的打包预检，同时保留已构建产物的独立核验证据，不反复无变更重建。源补齐、有效宏、实际构建和运行四种结果分开记录在 `.work/ios-permissions.md`，第 11.6.1 节再次核对，未执行项不写通过。

#### 9.2.1 `.work/` 可删除与工程独立性（硬门槛）

`.work/` 只保存思维导图、执行文档、开发台账、证据、临时输出和可恢复备份，用户确认可提交后可以整目录删除。主项目必须在该目录完全不存在时仍能解析依赖、生成代码、测试、构建、打包、启动和完成全部功能；最终 `aduit/` 材料也必须完整可用。不得把它作为工程根目录、依赖根目录、资源仓库、构建输入或正式输出位置。

- **单向引用**：工作记录可以指向项目代码、资源和产物供开发核对；项目代码、运行数据、依赖、构建配置和最终交付文件不得反向依赖工作记录。开发智能体读取逐页图和执行文档仍按第 3.6 节进行，不将它们转换成 App 运行条件。
- **实际文件归位**：源码在 `lib/` 或对应原生目录；Logo、图片、字体、动画、着色器、种子数据及运行清单在实际声明的项目资源目录；必要代码生成器、构建工具和测试夹具在项目正式工具/测试目录。正式文件须是独立的真实副本，不能是指向 `.work/` 的软链接、路径别名或需要恢复备份才能得到的唯一文件。主题色值实际写入 `lib/common_module/theme/app_theme.dart`，三个协议 URL 原值实际写入 App 注册表，不能运行时读取工作台账。
- **所有消费者遵守**：禁止 Dart 的 import/export/part、文件读取、资源声明与清单、`path`/`dependency_overrides`/开发依赖、测试/CI、代码生成、Xcode 工程、xcconfig、Podfile、Build Phase/脚本、资源复制及 HTML/CSS/JavaScript 从这里取文件。不能用绝对路径、`../`、环境变量、生成配置、外部脚本或链接间接转指。正常的 `.dart_tool/`、Pods、插件链接与 `build/` 仍用各自标准位置，其解析后的输入也不得落入工作目录。
- **临时成果先转存**：工作目录中的任何图片、生成代码或配置若被选为正式输入，先复制到正确项目目录、同步所有引用，再重新生成相关配置并验收；原文件只作记录。开发期备用品牌图也放入实际项目资源目录，来源和未验证状态才记在工作目录。`aduit/` 的正文、图片及自包含欢迎 HTML 均不得依靠此目录中的链接或附属文件。
- **开发检查不变成生产依赖**：Skill 的视觉/命名检查器可以读取开发证据并将报告写入这里；它们不是 App 的运行、常规检查或构建前置条件，不在项目测试、CI 或 Build Phase 中强制要求工作记录存在。最终需随项目保留的文件不得只存在于证据或备份中。

实施中每次新增路径/依赖时即检查这条边界；第 13 节第 19 步必须按第 11.12 节实际做可逆的移出目录验证，修复后复验。保留工作记录供用户自行决定删除，不以直接删除它代替独立性验证。

### 9.3 全局主题、页面组织与命名

主题架构契约：`lib/common_module/theme/app_theme.dart` 是统一的全局主题入口，由 `AppPalette` 与 `AppTheme` 提供明亮主色、辅助色、语义色、明亮阅读表面及按需创建的渐变令牌。统一采用明亮色调，不设冷暖色系数量或渐变配额；Logo 取色仅作可选参考。页面和组件统一调用该 API，HTML 用对应设计的 CSS 变量，避免散落或冲突的硬编码。按第 6.2 节固定明亮外观，不建立颜色控制器、明暗切换状态或偏好存储；旧设置不再驱动主题。选择 Logo 取色时记录真实像素与 HEX 来源，未取色时不虚报；不要求每页有渐变。

项目自有 `assets/` 文件和分类目录按第 10.1.2 节使用主题/用途短名，去掉外部下载附带的网站、日期和资源 ID；路径中的专有名词统一简写，映射留在 `.work/asset-names.md`。保持上述固定品牌与页面背景路径契约，迁移旧名时同步所有资源声明、数据与代码引用，重建并确认实际加载。

页面架构规则：

- `lib/app/` 按第 5.1 节的选定方案装配导航壳层、目的地与返回栈，不预装所有项目共用的底部导航容器。只有方案确实选用底部导航时才引入相应组件与选中状态；目录、步骤流程、画布或单工作台按其真实路由和任务状态组织，不能仅隐藏默认底栏却保留其布局/下标依赖。
- `lib/main.dart` 只负责初始化 Flutter 并启动根 App；根路由/壳层放入 `lib/app/`。每个实际 App 自有页面有稳定 `page_id`；Welcome 是用户指定固定路径例外，入口与 `WelcomePage` 定义在 `lib/welcome.dart`（`page_id=welcome`），其余页面 Widget 定义在独立的 `lib/page_module/<page_id>/<page_id>_page.dart` 中；不得将多个路由页面集中写在 `main.dart`、单个 `pages.dart` 或其他聚合 Dart 文件里。
- 功能/页面分类以目录边界表达：Welcome 入口固定在 `lib/welcome.dart`、复杂子组件可放 `page_module/welcome/wgt/`；Initialization、每个主要目的地、Settings、Protocol/WebView、About/Support，以及实际选用的 Detail、Player、Camera、Photo Import、Audio Record、Media Library 和适用状态分别归入对应的 `page_module/<page_id>/` 目录。iOS 原生 Launch Screen 仍由原生 storyboard/资源提供；Welcome 内的启动准备状态是页面状态，不建立 Loading 路由或独立页面。路由表只注册并引用 Flutter 页面，不内嵌页面实现；共享呈现组件进入 `common_module/wgt/`，单页专属复杂组件放入该页面自己的 `wgt/`。
- 在思维导图与 `.work/page-inventory.md` 维护完整页面清单，至少列 `page_id`、页面类别/路由、对应实现文件、页面状态、背景模式及实际图片路径或 scene_id/代码入口/动画资源、实际消费者和测试/截图证据。另按第 3.6 节逐行关联 `.work/map/page/<page_id>.md` 与 `.work/exec/page/<page_id>.md`、同版方案/修订和需求/任务/用例；全部独立页面、Sheet/Dialog、原生及 HTML 表面均有各自一对文件，状态和内容实例在所属页面内展开。图、执行正文与全局索引分开，实施每页前完整读取该页两份文件，变更与恢复同步图文、清单、索引和引用；不能只创建文档而不据其实施。
- 按第 6.11 节区分背景实现：实际图片单独放在 `assets/backgrounds/<page_id>/<page_id>_background.png` 或真实格式，目录/短名与稳定 page_id 一致；登记 `pubspec.yaml` 和真实页面消费者，不存入 `aduit/site/img/` 或 Dart 超大 Base64。程序/动画场景按页面/公共职责存放实现，登记 scene_id、入口、所用着色器/组件/本地动画资源及声明，纯代码场景不创建图片或虚构 asset key。动画工具、服务和组件组合不限，须真正完成环境、导入、页面调用和 iPhone 运行/录屏；共享引擎不等于复用整页场景。
- 页面拆分以可独立理解和维护为准：一个文件可包含同一页面必要的小型私有子组件，但第二个可路由页面必须有自己的页面文件；不得为了凑拆分把共享业务状态复制多份，也不得为目录数量重写兼容且清晰的既有页面。生成并登记新页面时同步更新页面清单、路由、Dart 测试和对应背景资源映射。

共享代码和其他规则：

- 页面组合组件；状态和业务逻辑放在独立、可测试的状态/服务模块，默认使用各页面的 `state.dart`，已有等价结构可复用。
- 共享令牌、按钮、卡片、空/错误状态、协议容器和媒体容器放在 `common_module/`。
- UI 不直接访问偏好、文件、网络客户端或平台通道。
- Flutter 运行时读取审核通过的种子数据、清单和随包资源；按主题能力矩阵接入适用的拍摄、导入、录音及其他 iOS 能力对应的受控原生服务；不适用项仅在记录依据后不创建服务、插件或权限。开发期协议、About Home 与 Support 页面可用于本地预览；`aduit/` 生成完成后，正式 App 将三个协议 URL在生成阶段写入具体项目名称，生成阶段将用户提供的项目名称替换后写入固定注册表，例如项目A写入 `http://项目A/PrivacyPolicy.html`、`http://项目A/Terms&Conditions.html`、`http://项目A/Support.html`；同时保存到固定 URL 注册表，并在 App 内 WebView 显示。三个文件名保持原样和大小写，不改名；Enter 只暴露 Terms/Privacy 两条文本链接，Settings 只暴露 Privacy Policy、Terms of Use、Support 三个 WebView 入口；首页保留为站点文件，不加入 Settings 入口。目标不可达时仍使用已写入的具体 URL并显示可读错误与有限重试，不跳转外部 App，也不阻断其他 App 功能。不得夹带未披露的分析或追踪脚本。
- 第三方供应商客户端、凭据读取和下载只能放在 `tools/med_ing/` 或受控 CI。
- 依赖通过 `iface.dart`、现有依赖注入入口或明确记录的 facade 暴露；避免 UI 直接构造平台与文件服务。
- 开发阶段复用旧项目时移除登录页面、邮箱输入与校验、认证依赖及其路由和测试；仅迁移/清理已识别的旧登录持久化字段，保护已有内容与非账号偏好，不将旧登录记录映射为 `AppFlowState`。此规则不代替运行时用户明确确认的全量清除，后者按第 8.5 节删除 App 自有用户数据与偏好。

#### 9.3.1 项目自有资源、文件夹与文件短名（硬门槛）

只修改能够准确、清楚缩写的项目自有名称：有公认或项目内可辨认缩写的完整词组、专名采用统一短名；原本已简短、没有合适缩写或缩写会丢失含义/造成歧义的名称保留，不按字符数截断，不为了“全部变短”编造缩写。范围包括图片/视频/音频/字体、数据文件、页面/组件/服务、工具、测试及其自定义分类目录，不仅限于外部下载素材。Dart 和普通自有路径使用小写英文 `lower_snake_case`，保留真实扩展名；复用工程中能够缩写的旧名也应迁移，不能只约束新文件。

**禁用工具与 AI 相关命名**：项目根目录及项目自有文件夹、文件名不得出现 `codex`、`ai` 或相关工具/模型词，例如 `openai`、`genai`、`aigc`、`llm`、`gpt`、`chatgpt`、`人工智能`、`智能体`，也不得用大小写、驼峰、分隔符或版本后缀变体绕过。以主题、业务职责或资源用途命名，如 `scene_bg.png`、`content_svc.dart`；不用 `ai_cover.png`、`codex_notes.md` 等名称。按相关词和组合词识别，不把普通单词中的字母子串当作相关词，`main.dart`、`rain.jpg`、`terrain.jpg` 不因含有 ai 字母而失败；`detail` 的缩写仍独立按本节处理。工程内部开发记录同样受约束，统一使用 `.work/`，不为隐藏文件或 `keep` 记录豁免禁用词。外部技能安装路径、工程根目录之外的父路径、标准构建缓存与第三方依赖的强制名称不机械改写；不能把项目自有实现藏入这些目录规避检查。保留用户显示名不代表可以用禁用词作磁盘名；遇到用户指定的磁盘根目录或项目名冲突时，列明具体冲突及可用主题短名，不擅自移动当前工程或改动展示品牌，也不将冲突判为通过。

**旧记录目录迁移**：复用项目存在旧 `.codex-work/` 时，先停止本任务会写入旧位置的进程，将记录实际迁移到 `.work/` 并更新内部证据路径、配置、脚本与忽略规则；不要只改规则文本。两目录都存在时逐文件检查冲突与内容哈希，不覆盖或删除已有记录，必要旧副本放在工程外的恢复位置，不能靠软链接保留旧目录名。检查残留引用，运行命名、视觉及受影响 iOS 配置检查，确认 `.work/` 仍满足第 9.2.1 节的独立性，再完成迁移。命名检查器只读报错，不自动移动目录或编辑工程。

- **先确定再创建**：在首次创建普通自有代码/资源前建立 `.work/path-terms.json` 和 `path-names.md`；Logo 固定命名链仍按第 2.5 节优先执行。记录实际会使用的主题词/专名与可辨认缩写，规划文件直接使用最终短名，不先大量生成长名再把整理留到交付以后。每次新增页面、组件、数据或资源时沿用同一词表；不为满足命名规则增加用户确认。
- **同义同写法**：默认采用 `configuration/config → cfg`、`service → svc`、`repository → repo`、`controller → ctl`、`component → cmp`、`dialog → dlg`、`thumbnail → thumb`、`detail → det`、`model → mdl`、`widget → wgt`、`route → rt` 等可辨认约定；同一含义的单复数统一使用同一短名。目录示例只表达职责，非固定名称也必须执行本节。例如 `lib/services/detail_controller.dart → lib/svc/det_ctl.dart`，`lib/page_module/initialization/initialization_page.dart → lib/page_module/init/init_page.dart`；后者的背景目录与 `page_id` 同步改为 `init`，`/entry`、`/welcome` 等固定运行路由不因此改动。使用语义短名而非随机串或无意义单字符；同名冲突使用简短用途词或稳定序号，禁止覆盖不同文件。主题专名的缩写与第 10.1.2 节保持一致，下载来源与时间仍不得进入名称。
- **改名与引用是同一任务**：改名前在 `.work/path-names.md` 记录“完整含义/旧路径 → 缩写/新路径 → 所有消费者 → 复验结果”；素材清单沿用 `asset-names.md` 并相互链接，不重复维护冲突映射。同步 Dart `import`/`export`/`part`、路由与资源常量、`pubspec.yaml`、生成访问器、JSON/种子数据/清单、HTML/CSS/脚本中的项目内路径、原生工程/资源引用、构建工具、测试及快照。只改文件或文件夹名、留下旧引用即为失败；父目录改名须更新全部后代引用。生成文件通过对应生成器更新，不手工修补依赖缓存冒充源文件修复。

- **改名后必须复验**：检查路径唯一性、大小写和内容未误换；大小写单独改名需经临时名完成真实文件系统变更。用 `rg` 检查当前源码/配置/数据中的旧项目路径残留，排除内部迁移记录、备份和必要来源事实；重新生成访问器、解析资源并执行适用的静态分析、测试与 iPhone 构建。逐一走查受影响页面、图片/视频/音频及 Welcome，断网确认随包加载，没有缺失引用、占位图、解码失败或旧路径回退；无运行条件时只标未验证，不能声称改名后全部可用。将结果纳入第 11.1、10.7 节既有验收，不新增用户确认。

**实际目录检查是必做项**：在架构建立后、每轮文件/资源整理后及最终交付前运行 Skill 自带的只读检查器，不能仅核对计划树或人工编写的文件清单：

```sh
python3 <Skill根目录>/scripts/validate_path_names.py --project-root <目标工程根目录> --json > <目标工程根目录>/.work/path-check.json
```

词表格式如下；`terms` 仅补充当前主题实际需要且能够准确缩写的词，通用缩写内置于检查器。没有主题补充时允许空对象；不要为了通过检查删除实际应缩写的主题词：

```json
{"terms": {"central_business_district": "cbd"}, "keep": []}
```

必要保留项的形式为 `{"path":"精确的项目相对路径","reason":"具体歧义或工具契约及依据"}`。`keep` 不接受通配符、整个子树授权、空理由或不存在路径；禁止以“方便”“旧项目一直如此”或赶进度为由绕过规则。检查器检查工程根目录名，并递归扫描空目录、资源、额外自定义目录和自有原生代码；仅排除已知构建/缓存/依赖。`.work/`、`aduit/`、`AppListing/` 继续递归检查禁用词，不套用普通代码的缩写/格式规则；已有 iOS 资源集等固定名称及 `keep` 路径也先查禁用词。报告列出完整检查、保留、仅禁用词检查（`name_only`）、排除路径及失败项；人工复核保留理由、排除范围及词表是否覆盖当前主题，不能借排除依赖目录隐藏自有实现。

命中工具/AI 相关禁用词、可缩写完整词、同义不同写法、大小写冲突或未检查的自有符号链接时修复，再运行至静态命名检查通过。没有命中的未知领域词仍需人工判断是否能够清楚缩写；脚本通过不证明所有语义正确，也不代替引用分析、构建和运行加载复验。命名未过只阻断该项验收，其他独立交付继续完成；不得宣布全项目命名合格或把错误移入排除目录以绕过检查。

#### 9.3.2 转场与动态背景的实际组织

按第 6.14.1–6.14.3 节把可复用的时间控制、遮罩/路径、绘制与生命周期放入适合的公共 motion 模块，自有文件可简写为 `rt_fx.dart`、`bg_fx.dart`；每页独立配置其主体、图层、轨迹、时序及真实任务状态。`rt.dart` 或实际中央路由表绑定各目标页独立的 `transition_id`，覆盖实际使用的 push/replace/go 与局部目的地切换，返回动画读取实际手势进度；不能在 main.dart 里堆所有页面，或用一份不变的全局转场应付全部导航。颜色统一取自 `common_module/theme/app_theme.dart`，实际使用的背景图片在 `assets/backgrounds/<page_id>/`，动画成品在 `assets/media/anim/<page_id>/` 等用途分类目录；直接动画生成、第三方组件合成和程序场景均按第 6.11 节接入，工具不限；每页另外保留真实半透明主题图片层，不能由动画/着色器替代。图片位于内容下方的可见装饰区域，不能被 Scaffold/Container 的不透明背景完全盖住；登记实际 asset、opacity 与 placement。实际 shader/动画资源按所用 Flutter 版本正确声明打包。

背景持续状态由各可见页面的 controller/场景状态管理，不在 build 内反复创建，切页/后台暂停、销毁释放，避免旧回调控制新页面；交互状态与路由状态保持单一来源，不另存一份导航栈。背景在内容后、触摸穿透，清除成功后的转场不保留用户私有内容快照。记录仍使用 ui-motion-gates.json 与 ui-visual-gates.json，不新增用户数据、账号、权限或性能测试工程。静态原生启动与就绪后 250ms 承接规则不变。

#### 9.3.3 非游戏真实能力实现边界（硬门槛）

非游戏页面按主题能力而非页面数量选择真实工具，并在 `.work/dependencies.md` 与能力矩阵记录 `capability`、`real_tool_or_sdk`、`version`、`license/source`、`actual_consumer`、`fallback`、`runtime_evidence` 和 `formula_record`。工具是否安装不构成实现；依赖必须被页面、服务或原生桥真实调用，并在当前 iPhone 上留下操作证据。

地图只能由真实地图 SDK、真实地图瓦片或许可地理数据承担：MapKit、Google Maps、Mapbox、HERE，或 `flutter_map` 配合许可明确的真实瓦片/地理数据。数据源、许可证、网络边界、缓存/离线降级、定位与隐私用途必须进入工程记录。禁止线条路径、色块、静态地图截图、假坐标网格、手工道路或装饰图冒充地图。地图页面需要真实缩放、平移、定位、标记、路线或图层（按主题适用），并处理瓦片失败、权限拒绝和前后台恢复。

图表绑定领域数据模型，包含空态、错误态、动态更新和可读性；3D 由真实渲染工具承担，媒体/时间线/扫描/语音能力由对应真实 API、插件或原生服务承担。每个动态实现使用六部分 `formula_record`（风格锚定、动画清单、技术手段、数字参数、包授权、约束与回退），并记录 Reduce Motion、生命周期释放和失败路径。组件目录是候选项，不为了数量安装全部包；选中和拒绝的版本/许可证/理由都要可追溯。

### 9.4 产品差异化与真实功能边界

工程结构必须服务当前创意的真实问题，不能只是一个可批量换皮的通用壳。开发前在 `.work/differentiation-brief.md` 固化以下字段，并在实现与验收中逐项回指：目标用户和具体问题、现有替代做法、领域实体及其关系、主题专属的核心动作、任务完成顺序、首个有用结果、可回访成果、失败/恢复规则和不适用能力。

- 领域模型、种子数据、状态机、路由和本地持久化必须解释真实产品问题；不能只把同一组通用卡片、列表、统计数字或媒体占位符替换成另一套字符串和图片。
- 每个项目至少实现一个主题专属核心任务，并产生可观察、可保存或可再次打开的真实结果；任务结果必须能由当前页面和数据模型证明，不以 Logo、主题色、字体、渐变、动画或素材变化代替。

- 产品身份、Bundle ID、显示名称和数据命名在配置中保持唯一且稳定；不生成地区克隆、品牌克隆或同一功能的批量变体，不使用远程配置在审核期间切换另一套产品。
- 领域功能必须在普通运行路径和审核路径中一致。不得放入隐藏审核入口、虚假数据、伪造权限结果、假计费状态、无效 CTA 或为了截图临时改变内容的开关。

`.work/page-inventory.md` 另记录每个主题专属页面/动作对应的领域实体、输入、结果、恢复路径和当前 iPhone 证据。缺少真实结果或只有换皮差异时，标记 `4.3 risk: Failed`，先整改再进入发布复核。

### 9.5 每个项目独立的架构与视觉样式（硬门槛）

每个新项目都要有自己的产品组织、核心工作区、导航、页面骨架、视觉语言和交互节奏；不能把不同主题重复套进同一套 Tab、卡片墙、列表详情与设置壳。按领域任务决定技术模块、状态所有者、数据流和渲染边界，而非只改目录名称、换状态管理包或替换素材。固定的主题入口、Welcome 文件、清除流程、权限及交付契约继续保留。

在已有 `.work/navigation-design.md`、差异化 brief 与逐页文档中记录本项目的核心循环、领域模块/依赖方向、状态与结果流、主工作区/导航路径、图文或场景媒介、字体/材质/构图和动效节奏，并说明这些选择与主题的关系。游戏可分规则/领域状态、引擎场景/实体/输入、HUD/Flutter 外层和存档；非游戏按实际内容、工具、创作或混合任务划分。示例不是固定架构菜单，也不要求为不同项目随意更换框架；基础控件、正确的服务边界可以复用，整套产品结构不能机械复用。

结合第 5.1、6.13 节比较本项目各页与可取得的历史方案，检查主工作区、导航/任务路径、空间编排、媒介关系、排版/材质及交互方式是否形成可辨认的项目专属样式。不能只以 Logo、配色、名称或随机转场说明差异，也不能将同一套骨架在几个预置主题间轮换。沿用现有历史索引和规划/质量记录，不新增一套重复台账，不扫描无关工程；历史不可取得时如实记录比对范围，仍完成当前独立设计。同一项目恢复时保留已确认设计，不为“不同”每次重做。

最终对照实际领域代码、导航行为、页面区域轮廓、动态图/场景及当前 iPhone 截图录屏核验，覆盖全项目而非仅 Welcome。发现与已知方案整体同构、架构不符合任务或只有换肤时实际调整并复验；设计描述与文件数量不能替代成品差异。

### 9.6 游戏项目专用引擎与环境搭建（硬门槛）

游戏是可选主题分支，不是所有项目的默认类型。只有用户选择游戏主题，或创意明确包含可操作的游戏世界/棋盘、玩法规则、回合或实时更新、关卡/挑战及游戏结果等真实游戏模块时，才识别为游戏项目或游戏模块。识别为游戏后先执行**专用引擎必要性决策门**，不得默认所有游戏都接入引擎：持续世界、实时物理/碰撞、复杂 3D、编辑器导出管线或高频实体更新通常需要 Flame、Godot、Unity 等专用引擎；回合制、卡牌、问答、轻量棋盘、有限状态解谜等玩法若由 Flutter 状态与规则即可稳定承载，可选择 Flutter 原生实现。仅有知识介绍、普通问答、进度奖励或界面动效，不因此自动把普通产品判为游戏；用户明确要求的问答/解谜游戏仍走游戏分支。混合产品只在真实游戏模块执行该决策，其他页面仍按自身职责实现。

| 真实玩法需求 | 引擎选型方向 |
| --- | --- |
| 2D 休闲、解谜、棋盘/卡牌、动作或场景互动 | 优先评估 Flutter 原生集成的 Flame；让引擎实际承担场景、实体、输入和适用的更新循环，不只添加依赖或显示静态图片。 |
| 需要真实碰撞、刚体、重力或关节的 2D 玩法 | 评估 Flame + 兼容版本的 `flame_forge2d`，核对坐标、时间步长、碰撞过滤和生命周期；不需要物理时不安装物理模块。 |
| 需要完整 3D 世界、复杂空间玩法或专用编辑器管线 | 评估 Unity、Godot 等确实支持当前 iOS 的引擎及可验证的 Flutter 原生嵌入方案；只有实际版本、导出工具链与 iPhone 集成能跑通时才采用，不把纯模型播放器或动画库当作完整游戏引擎。 |

非游戏项目跳过第 9.6 节游戏决策和可玩闭环门槛，不安装或配置游戏专用依赖。游戏项目才适用以下决策规则：在既有 `.work/dependencies.md` 和规划文档写明 `implementation_mode: engine | flutter_native`、`engine_required: true | false`、判定依据、玩法复杂度、输入/更新/结果所有权、视觉效果路径及 iPhone 验收方案，不另问用户选引擎。选择 `engine` 时，根据玩法、视觉目标、五档目标硬件和现有 Flutter/iPhone 约束明确一个主引擎、精确版本、必要扩展及理由；引擎负责真实游戏运行，Flutter 负责适合的外层页面/HUD/导航与共享契约。选择 `flutter_native` 时，Flutter 状态、规则、场景、输入、结果和重开由 Dart/Flutter 原生代码负责，不得因为没有引擎而降低游戏深度或视觉质量；必须使用第 6.14 节的动画/效果包与工具目录，逐项记录实际包/工具、版本/来源、许可、采用范围、替代方案及未选原因，并为每个动态任务填写六部分效果提示词公式。两条路线都保持当前 Flutter 根工程和 iPhone-only 范围，不另造浏览器游戏或其他平台 App 作为交付替代。

**游戏实现契约（`.work/game-engine.json`，游戏/混合项目必填）**：在实现前创建项目根目录内的 `.work/game-engine.json`，并在每次实现模式、引擎、原生桥、场景入口、动画工具或构建命令变化后同步。契约先记录是否需要引擎；`engine` 仅在 `implementation_mode: engine` 时必填，Flutter 原生路线必须明确 `engine: null` 和 Dart 运行时入口。字段名不得改写成模糊描述：

```json
{
  "project_type": "game | mixed",
  "implementation_mode": "engine | flutter_native",
  "engine_required": true,
  "decision_reason": "为什么需要或不需要专用引擎",
  "engine": null,
  "runtime": {
    "entrypoint": ["项目内真实 Dart 入口或引擎场景"],
    "scene_assets": ["项目内真实角色、场景、纹理或资源包"],
    "runtime_owner": "引擎或 Flutter 原生负责的状态、输入、规则、更新、结果与重开",
    "native_bridge": "引擎路线的原生桥、PlatformView 或 channel；Flutter 原生路线写 null",
    "animation_effect_catalog": ["实际使用的包/工具/版本/来源记录"],
    "prompt_formula": "Flutter 原生动态任务使用的六部分效果提示词记录路径"
  },
  "build_commands": ["实际依赖解析、导出和 iPhone 构建命令"],
  "evidence": ["项目内相对路径的构建、录屏、截图、日志证据"]
}
```

`implementation_mode` 与 `engine_required` 必须和第 9.6 节的决策一致。`engine` 路线的 `engine.name`、`engine.version` 必须与实际锁定依赖/导出工具一致；只写 `game engine`、只在 `pubspec.yaml` 添加依赖、只显示静态图片或只显示空场景都不构成接入。`runtime.entrypoint` 与 `runtime.scene_assets` 必须是工程内真实存在且被运行时消费的路径；`runtime_owner` 要明确引擎或 Flutter 原生拥有实体/状态、输入、规则和更新循环。Godot/Unity 等需要原生嵌入时，`native_bridge` 必须列出实际宿主、channel/view 和资源包；Flame 也要列出 `Game`/`GameWidget` 入口。Flutter 原生路线必须列出 Dart 状态机/规则入口、输入命中、HUD/反馈、重开路径和实际动画/效果包或工具；动画/效果包已安装但没有真实消费者不构成通过。`build_commands` 与 `evidence` 不得指向工程外、静态设计稿、浏览器演示或隐藏调试工程。

**实现决策与环境核验**：规划确认前只读核对玩法是否需要专用引擎，检查 SDK/包的支持条件、Flutter/Dart/Xcode/iOS SDK、最低部署版本、原生架构、动画/效果工具及资源导入方式，列出真实缺口，不能提前安装或绕过 Logo 首任务。整体确认后先完成 Logo 选择校验 → 明亮主题设计 → Flutter 工程创建；`engine` 路线再补齐所选引擎的实际依赖、原生桥/Framework/Pod 配置和导出资源，`flutter_native` 路线补齐 Dart 规则状态、动态效果包/工具和本地资源。两条路线都逐项记录可执行路径、实际版本、解析/构建结果及证据；需要专用编辑器时也验证编辑器与 iOS 导出链，不能只看到命令或包存在就认为环境成功。

在同一 App、同一 Bundle ID 和一个现有 iPhone 上做最小但真实的游戏闭环。`engine` 路线固定顺序为：`引擎环境 → 场景启动 → 已创作资源加载 → 真实输入 → 更新/物理 → 结果 → 反馈 → 重开`；`flutter_native` 路线固定顺序为：`Flutter 运行时 → 场景启动 → 已创作资源加载 → 真实输入 → 规则更新 → 结果 → 反馈 → 重开`。初始化运行时 → 加载本地角色/场景资源 → 真实触摸/手势 → 规则/适用物理更新 → 可观察结果 → 重开都必须在同一构建中留下证据；Flutter 原生路线还必须证明动画/效果包或工具的真实消费者、动态前/中/后状态和 Reduce Motion 回退。每一步都要有输入、输出、当前 iPhone 录屏/截图或日志路径。它是工程内的早期集成验收，不能另建调试安装或用空场景冒充完整游戏；通过后才允许继续全部已确认玩法与内容。核对场景卸载、前后台/系统中断、音频如有、Scene/engine 生命周期、控制器释放、存档如有及按第 7.7 节选定的 Clear Data / Exit App 操作，不能添加无用权限或 ATT。环境失败按既有有限诊断规则修复；可在记录依据后切换到满足玩法的另一条路线，不缩水为静态 UI；确实不可用时据实标记对应缺口，继续独立工作，不伪报引擎或玩法已运行。

### 9.6.1 游戏可玩闭环硬门槛与并行推进
游戏可玩闭环硬门槛：完整一局必须覆盖开始、真实输入、规则更新、成功或失败结果、重开。独立游戏验收记录必须列出主入口、引擎场景、输入、规则、结果、重开和当前 iPhone 证据。禁止用空场景、彩色方块、静态截图或点击穿透演示充当可玩游戏。


游戏项目在扩展关卡、商店、收藏、设置或发布材料前，必须先通过一个可重复的真实可玩垂直切片。切片按契约选择路线：`engine` 执行 `引擎环境 → 场景启动 → 已创作资源加载 → 真实输入 → 更新/物理 → 结果 → 反馈 → 重开`；`flutter_native` 执行 `Flutter 运行时 → 场景启动 → 已创作资源加载 → 真实输入 → 规则更新 → 结果 → 反馈 → 重开`。两条路线都从 Welcome `Continue` 到主游戏目的地，最多经过一个可见 `Play`/`Start`；加载本地角色和场景资源；接受真实触摸/手势或项目所需输入；产生明确的成功或失败结果；允许重开并恢复到可玩状态。Flutter 原生路线还要证明选定的动画/效果包、工具目录与六部分提示词实际产出动态反馈，而不是只列依赖。若玩法需要暂停/继续、碰撞、音频、存档或前后台恢复，也必须按实际需求在同一闭环中验证。没有完成该垂直切片的项目不得扩展全量内容、进入“游戏完成”、制作最终截图或执行 Git 交接；并行任务不能绕过该门槛。

以下内容不计入可玩游戏：空场景、纯色方块、简单几何碰撞演示、静态截图、只播放动画、点击后穿透到下一页、无效按钮、自动播放后伪造胜利、只在隐藏路由可玩的场景或只在浏览器/独立调试工程中运行的玩法。角色/卡面/棋盘、场景、HUD、反馈和规则结果必须在当前 iPhone 的同一 App/Bundle ID 中实际出现；引擎依赖已安装、动画/效果包已安装、编译通过或首帧显示都不等于玩法通过。

把游戏实现拆成可并行的独立任务：主入口/路由、引擎场景与输入、规则与结果状态、主题美术与反馈、存档/生命周期、设置与交付材料分别记录负责人、输入、输出和阻断。某个资源或页面任务失败时，继续推进不依赖它的工作；只有主游戏可达性、输入、规则、结果和重开闭环全部通过，才可汇总为“可玩”。任何核心路径失败、崩溃、卡死、无法重开或入口不可达，统一记录 `Release readiness: Blocked`，不得用截图或静态文档覆盖。预检与运行日志必须同时记录：`setState() called during build`、RenderFlex overflow、stale callbacks after dispose、duplicate engine registration、engine timeout、input mismatch、overlay occlusion、lifecycle resume duplication，以及 crash/white-screen/hang；任一项未修复并在同一 iPhone 重放通过，游戏发布状态保持 Blocked。

**游戏美术与精修**：按主题精修角色/物体造型与多帧动作、场景前中后景、相机/视差、纹理/材质/光影、主题粒子、规则反馈和可读 HUD，具体手段由玩法决定。优先完整角色/场景素材和有层次的构图，拒绝用纯色矩形、简单几何碰撞演示或通用按钮画面充当最终游戏。素材遵守既有来源、许可、本地 assets、短名、圆角与真实图片边界；角色/帧序列按用途分目录，不用同图反复充数。引擎选对、编译成功或测试场景能动都不代表最终游戏好看；必须在当前 iPhone 上实际游玩并录屏精修，记录视觉与玩法问题及修复复验。既有独立页面骨架、动态图/实时背景适用边界、完整 UI、减少动态与最终截图规则继续执行。
