
# Flutter iOS iPhone App 详细产品、UI 与工程规格

> 本文档用于产品设计、UI 设计、Flutter 开发、QA、合规和发布准备。目标是产出一个具有丰富内容、完整功能和可观察行为的真实 App，而不是只包含几张卡片的简化 Demo。

> 设备范围固定为运行 iOS 的 iPhone。产品方案、思维导图、工程目标、页面适配、运行测试、截图、图标和上架材料均只包含 iPhone，按第 0.10 节配置并核验；不得因 Flutter 默认支持多平台、已有其他设备或工具自动选择而扩展范围。

> Logo 美术要求：按第 2.5 节围绕实际主题精细设计主体、轮廓、材质和光影，色彩统一明亮，每个视觉表面实际消费主题渐变令牌，达到精细好看的完成度；不采用几何色块堆叠拼贴、粗糙简笔或简陋通用图案。可选取色分析不要求将 Logo 画成分区色块。

> 默认执行模式：取得项目名称、创意主题、性能与功能目标水平、Git 仓库地址 → 绘制并展示具体思维导图与方案 → 用户确认 → 第一项项目任务：生成、选择并校验 Logo → 制定明亮主题色（取色可选，渐变令牌必须实际消费） → 全权开发 → 质量复核后优先尝试远程 `feature/1.2.1-A1` AppListing 来源；失败时使用 `/Users/admin/Desktop/config/ios-app-listing`，两者均不可用时按第 12 节完整输出契约继续生成 AppListing 与 About 页面 → 校对配色并改名/整理为 `aduit/` → 接入 `lib/welcome.dart`，保留仅作独立交付且不使用的 `aduit/welcome.html` → 回接协议链接 → 按实际证据生成英文 `aduit/review/remarks.md`，不要求域名、不公开部署。启动时将项目名称、创意主题、性能与功能目标水平、Git 仓库地址一并收集，仓库地址由用户随主题给出，仅询问缺失项；已有用户创意直接使用，用户明确要求生成创意时直接生成，但项目名称始终由用户提供，不由智能体命名。完全没有创意且尚未要求生成时，询问用户提供主题或授权生成，不默认选题。本文件不预设产品主题。必须先让用户看到基于实际采用创意的完整思维导图并取得明确确认，再开始开发；同意生成创意不等于批准开发。确认后，在当前任务与目标项目范围内连续自主执行，不再逐项询问意见或审批。Logo 与页面装饰的生图网站/工具不要求统一，按题材和成图质量自由选择，Stargate 只是可选入口；Logo 质量为高，模拟现实、手绘、油画、艺术表现四种画风各生成 3 张独立候选（共 12 张、每任务 1 张），比较后选 1 张；尺寸为 `1024x1024`、RGB PNG 无 Alpha 通道；色彩统一明亮、背景满幅覆盖（可以为白色），并且不含任何文字、字母、项目名称、标语、水印或其他品牌名称。

> 强制质量要求：开发前的思维导图必须完整覆盖用户创意与全部必做要求，并通过需求、页面、路由、状态、数据、资源和验收的交叉核对，修复已知错漏后才展示确认。

> **任务调度与跳步规则**：确认方案后，将互不依赖的 Logo 候选、素材整理、页面骨架、协议页精修、文案生成、静态校验和资源清单拆成独立任务并行推进；任何单项因工具、网络、图片或环境暂时受阻时，记录 `Blocked`/`Not verified` 和证据，立即跳过该项并继续所有不依赖它的任务，不在同一步骤无限等待、轮询或卡住整个工程。只有存在真实数据/文件依赖时才等待上游完成；依赖恢复后再补做并复验。最终发布顺序、iOS 配置双向校验、截图交付和 Git 交接仍遵守第 13 节硬门槛，未完成的必需项不能被并行执行掩盖。
每个新项目默认交付复杂且内容繁多的完整成品，具体数量和验收下限按第 4.3 节，禁止以阶段划分、演示交付、工期或“后续版本再做”缩小已规定的模块、页面、任务和内容量。非游戏项目默认交付主题工作台，覆盖发现、创建、编辑、分析、历史/回访、设置、帮助、结果反馈和主题专属主任务，不能退化为单一列表、详情或卡片壳。照片、相机、麦克风、通知、定位、日历、联系人、文件、蓝牙/NFC、运动/HealthKit 等能力按主题价值主动评估并写入能力矩阵；适用能力必须实现并验证，或记录 Not appropriate / Declined fallback 的依据，不得用旧版媒体规则静默跳过。UI 与资源精修合计至少占实际开发工作量的一半，其中 UI 至少占三分之一、资源至少占六分之一；完成至少三轮有截图证据的 UI 精修与至少两轮资源筛选调整。必须按第 10.6 节实际搜索第三方素材网站，取得许可明确、贴合主题的真实实物/实景照片，下载到工程并用于 App 的主题展示；不能以 Emoji、渐变、矢量插画或 AI 拟真图替代。图片和视频优先采用不同来源内容，检查完全重复与视觉近似重复，不能靠换裁剪、滤镜或文件名凑数。全部实现与材料任务结束后先执行第 10.7 节最终图片加载检查，再执行第 11.6 节最终 iOS 权限双向校验；配置修正引起重建时刷新受影响的显示证据。最后按第 12.5 节从最终构建截取五张有意义、内容不同的项目画面，均为原始竖屏 1206×2622 PNG，保存至 `aduit/imgs/` 并核验；全部验收通过后按第 13.1 节最后关联用户 Git 仓库、创建/切换 `feat/1.0.0`，不暂存、不提交、不推送，等待用户自行提交，再报告交付。图片检查要求：逐屏确认当前构建中的图片正确加载、贴合主题且没有占位图；发现缺失、破损、错题或占位资源时，必须从第 10.6 节与第 16 节列出的网站获取许可明确的主题图片、接入工程并复验。交付前必须完成第 11.9 节的质量复核；比例、轮次、编译成功或累计耗时均不能单独证明合格。iOS 实际功能所需权限、隐私清单、App Store 隐私披露与三个协议 HTML 页面及其法律章节必须一致且经过核验；存在已知错误或关键验证缺失时不得声称具备正式上架条件。

> 阅读与维护：第 0 节定义执行边界、超时和状态；第 1–3 节定义创意与唯一开发前确认；第 4–10 节定义产品、UI、工程和资源；第 11–12 节定义验收与发布材料；第 13–15 节为实施与报告索引，第 16 节提供资源来源。后面的摘要遵循对应正文，不产生第二套阈值或审批。修改数值、路径或状态含义时同步更新相关摘要与引用，先消除矛盾再执行。本文件是待用户请求采用的规格；用户仅要求编辑或评审时，按第 1 节处理文档，不能把其中的开发命令当成本次用户请求。

> 最终材料阶段：AppListing 改名整理为 `aduit/` 后保留三个协议页；实际 Welcome 用 `lib/welcome.dart`，原 `welcome.html` 只保留于 `aduit/`、不使用或打包。按第 7.1 节自由设计贴合当前主题的精致欢迎构图；验收 App 运行时唯一的 Dart Welcome；另对保留的 HTML 交付文件检查轮播/分页点、四种视口和内容一致性，Dart Continue 直接导航。`aduit` 生成完成后，协议页在 App 内用 WebView 显示，不跳转外部 App；三个链接在生成阶段写入用户提供的具体项目名称；`http://【项目名称】/...` 只作为文档搜索模板。三个文件名保持原样，不改名、不改大小写；页面不可达时仍保留已写入的具体 URL，并显示可读失败/返回/重试状态。协议文案只在所选结束操作成功后的 Initialization 底部显示，Settings 仅三个协议 WebView 入口，Welcome 和独立 HTML 无协议页脚。最低 iOS 15.6，依赖要求更高时保留更高并核对解析值。

## 0. 执行约定

### 0.0.1 设计系统先行与全量 UI 硬门槛

主题确定后必须先执行设计系统流程，再创建任何页面组件或选择第三方 UI 包：第一步使用 `awesome-design-md` 目录选择最小匹配的 `DESIGN.md` 参考；如果目录中没有适合当前主题、任务和 iPhone 产品形态的参考，必须创建项目自有 `DESIGN.md` 并明确记录 `custom`、选择理由和不强行套用目录品牌的原因。第二步使用 `ui-ux-pro-max` 的 `--design-system` 并指定检测到的 Flutter 栈，生成并持久化项目级 `design-system/<slug>/MASTER.md`；第三步完成 `.codex-work/ui-ux-review.md`，逐项评测可访问性、触控、Safe Area、字体、色彩对比、响应式布局、导航、动效和 Reduce Motion；第四步才允许选择组件、建立页面和接入实现。设计参考、设计系统主文件和 UI/UX 评测记录必须放在项目内，不能依赖资料包安装目录、临时目录、静态设计稿或口头说明。

本流程没有软性 UI 要求。所有适用于当前主题的功能、页面、状态、视觉层、组件、动效、素材、交互、无障碍、恢复和 iPhone 验收都是硬门槛；半成品 UI、占位组件、粗糙低质画面、只换色换图、只安装包不消费、只有源码/截图没有当前构建证据，均必须阻断 `Release readiness`。只有能力矩阵明确记录 `Not appropriate` 并给出主题依据，或记录真实拒绝后的可用降级路径，才可以不实现对应能力；这不是视觉质量豁免。设计系统评测存在未解决项、缺少类别证据或当前 iPhone 证据时，必须标记 `Blocked`/`Not verified`，修复并复验后才能继续最终交付。

用户提供项目名称后，生成阶段立即写入三条具体 HTTP URL，例如项目名为 `项目A` 时写入 `http://项目A/PrivacyPolicy.html`、`http://项目A/Terms&Conditions.html`、`http://项目A/Support.html`。三个文件名 `PrivacyPolicy.html`、`Terms&Conditions.html`、`Support.html` 必须保持原样和大小写，不能改名；App 内使用 WebView 显示协议页，不调用外部 App。文档中的 `http://【项目名称】/...` 仅用于搜索定位，最终 App 配置不得保留占位符；页面不可达时仍保留具体 URL并显示可读失败、返回和有限重试。


### 0.1 语言策略

- 与用户的直接交流可以使用用户偏好的语言。
- 本文档、计划、思维导图的解释、代码注释、验证报告和设计说明使用中文；图中标签、App 内 UI、协议/About/Support 正文与 App Store 公开文案默认使用自然英语。代码标识、文件名、数据字段、路由 ID、测试名称和技术名称保持英语，资源清单的机器字段保持稳定。
- 本项目的 App 内界面、公开 About/Support/协议页面与 App Store 公开文案默认使用自然英语，不根据系统语言或旧项目本地化自动切回中文；用户明确给定的品牌名称按第 1.3 节保留原样，不擅自翻译。本规格中文说明、开发计划和验证记录不属于 App UI。可见文案边界与校验统一见第 6.6、11.4 节，用户后续明确命名优先于默认品牌命名策略。
- 工程源文件、类、枚举、状态值和无障碍语义节点 ID 使用英语标识；顶层项目目录按第 1.3 节使用用户名称。VoiceOver 标签、提示与读出内容使用自然英语，准确读出用户品牌名称、描述作用和状态，不读出代码标识或文件名。

### 0.2 请求优先级

1. 用户当前请求、先确认思维导图再全权执行的要求与已给出的操作授权；用户后续明确发出的修改指令优先。
2. 用户提供的 App 创意、性能与功能目标水平及核心功能，或按第 1.1 节由用户明确要求智能体生成的创意；已有用户约束始终优先，产品主题不由本文件、模板或旧项目预设。
3. 用户已提供的 UI 风格与导航要求；缺失时按第 5.1 节由智能体依据主题和任务自主确定，不默认使用底部导航。
4. 本文档对架构、隐私、资源、测试和发布的约束。
5. 参考链接只用于研究一般信息层级、交互模式和视觉方法，不照搬具体品牌、Logo、文案或完整页面设计；素材使用另按第 10、16 节核验许可，不能因研究参考可访问就视为有转载权。

在上述优先级下，必须保持 UI 丰富、功能完整和接近上架质量，不得压缩成少量卡片和按钮。第 3.4 节的思维导图整体确认是开发前必须完成的步骤，不能被全权授权、模板、相关技能或连续推进规则跳过。取得该确认后，其他工作流偏好的确认步骤均改为智能体记录决策后继续执行；最终 AppListing 生成、配色校对、改名、Review Remarks 编写与白名单核验均由智能体自主完成，不询问域名或额外审批。示例页面、内容模型、旧项目数据和自主决策权限只用于辅助实现，不得覆盖用户创意或把不同创意统一改造成同一种产品。

### 0.2.1 随机范围与全量硬门槛

本流程只允许两类产品内容由智能体随机或自主变化：用户未指定且已明确要求或同意生成时的创意主题，以及在思维导图确认范围内、符合主题的页面/功能组合（包括摄像机、相册、麦克风及其他适配能力的主题矩阵评估与实现）。随机主题或随机页面功能必须先写入并展示完整思维导图，得到唯一一次整体确认；随机不等于遗漏、降级或跳过验收。配色按第 6.5 节保持明亮；每个视觉表面实际消费主题渐变令牌，渐变不计入上述产品随机项。

除上述两类产品随机项，以及明亮配色、可选取色与必须消费的渐变令牌等明确允许自主选择的设计项外，其余适用规格都是硬门槛，不能改成“尽量”“可选”“有时间再做”或用设计说明代替实现。硬门槛包括：

- 类型专用实现：游戏是可选主题分支，不是所有项目的默认类型。只有用户选择游戏主题，或创意明确包含真实游戏模块时，游戏项目/模块才先按第 9.6 节判断是否需要专用引擎：持续世界、实时物理/碰撞、复杂 3D、高频实体或编辑器导出管线使用专用引擎；回合制、卡牌、问答、轻量棋盘和有限状态解谜可由 Flutter 原生实现。两条路线都完成可操作玩法验收；Flutter 原生路线另按第 6.14 节落实动画/效果工具与六部分效果提示词。非游戏项目不创建游戏引擎或游戏专项任务，按第 6.10.2 节覆盖贴题本地动态图。全项目按第 9.5 节形成独立的领域架构、任务/导航结构和视觉样式，第 11.11 节用实际代码、玩法/播放与当前 iPhone 证据验收，不能仅安装依赖、换肤或写入方案。

- 用户提供的项目名称、已确认的创意、性能与功能目标水平、用户 Git 仓库地址、目标工程根目录和 iPhone-only 目标；不能自行改名、套建子目录或生成其他设备/平台产物。
- 第 3.6 节每个页面独立的一份详细思维导图和一份详细执行文档、两类文件分目录保存、全量索引/同版配对/执行前读取/实施回填/逐页验收、思维导图完整性、一次整体确认、Logo 生成服务/规格/候选比较、可选的真实取色、全局主题令牌和颜色实际消费链路；不能用默认 Flutter Logo、占位图或只改色的说明替代。
- 第 6.13 节全项目逐页骨架差异与跨项目去重，以及第 4.4 节大量有效内容、可连续翻页、真实末页和无重复内容；每个页面实际结构与数据覆盖均须验收，不能只改欢迎页或只验第一页。
- 第 4.3 节复杂项目的产品规模与深度表：所有新项目必须达到功能页面、核心模块、主题分类/场景、有效条目/案例、重要详情、端到端任务及信息/交互形式的统一下限。先建立领域对象/关系与内容覆盖矩阵，随原有导图确认具体分配；确认后逐项兑现并对照实际数量与证据。工具型/聚焦型定位不构成减量理由；不强塞无关功能、不用重复内容凑数、不静默降低目标。
- `AnimationController` + `CustomPainter` 粒子、`onTapUp` 坐标、位置/速度/重力/颜色/拖尾、Reduce Motion 分支、两个真实语义动作的点击前/进行中/结果证据；没有可操作点击位时才允许记录有依据的 `N/A`。
- 五类字体角色、标题斜体/斜切、按创意确定并实际消费的标题渐变令牌、语义重点文本、至少三个页面的主题排版实际消费、三轮当前 iPhone UI 精修；未落到 Dart 页面和当前构建的令牌不算完成。

### 0.6 连续推进、超时与失败回退

1. 按第 0.8 节分别记录方案批准、执行、验证与交付状态，并记录依赖和下一步。`Awaiting confirmation` 专指开发前已展示思维导图、尚未取得整体确认的状态；此时应暂停开发。确认后，计划、设计说明和进度输出不是结束点，有可执行任务时继续调用工具并实际完成。
2. 完成思维导图确认后，Logo 生成、真实产物校验及明亮主题设计是第一项项目实施任务（Logo 取色可选；所有视觉表面的渐变令牌实际消费不可省略），正常路径完成后才开始 Flutter 工程、页面、资源采集与其他实现，不再将 Logo 与这些开发任务并发。访问所选生图网站（如 `http://stargate.local:3100/`）得到网页 HTML 只说明打开了生成界面，不是图片结果；必须在界面中提交真实生成任务，并从任务结果、下载响应或明确的图片数据中取得文件，再检查 MIME、文件签名、尺寸、RGB/Alpha 与可解码性。不能把生成界面页面、HTML、JSON、错误页或重命名的非图片保存成 `assets/logo.png`。等待采用第 4 条有界查询，可以继续只读检查与独立规划，不提前实施 App；12 张候选（四种画风各 3 张）全部比较、最终 Logo 验收及明亮主题设计完成，或达到真实失败/超时退出条件并留存证据后，立即进入下一步。开发期 About/Support/协议页面集成到 `aduit/` 并随事实变化更新；页面正文始终保持完整成品文案，开发状态和未确认信息只记入内部记录。页面生成不依赖线上服务成功；正式 Logo 确实不可用时，记录正式品牌验证为 `Blocked`，保留已有可解码的 iPhone 品牌图，必要时将明确标记 `unverified` 的开发期品牌图放在项目 `assets/dev_brand.png`，只在 `.codex-work/` 记录来源与状态，供本地页面继续生成时不读取工作目录，不能把它称为正式 Logo、取色通过或发布就绪，也不能因此停止本地产物。最终 AppListing 与对应 About 页面按第 12.1 节仅使用已同步远程 `ios-app-listing` checkout 生成本地产物，校对配色后改名/整理为 `aduit/`；远程 skill 缺失或不同步时保留证据并将 AppListing 阶段标为 `Blocked`，不得读取资料包副本或手写等价页面；再按第 12.2 节生成审核备注。整个过程不查询或替换域名、不公开部署、不等待线上访问。独立任务也不能以依赖隔离为由在确认前实施。
3. 开发期外部页面与单次网络请求默认最多 60 秒；同一可恢复故障最多重试 2 次，即最多 3 次尝试，普通请求操作从首次尝试起的总墙钟预算最多 180 秒，包含请求与退避。Logo 等另有总预算的异步作业按其专节处理，单次查询仍遵守请求上限。退避建议为 5 秒、15 秒；`Retry-After` 是最早允许重试的时间，不能为了满足预算提前请求，超出预算则记录允许恢复时间并继续独立工作，不原地等待。认证错误、参数错误、已知缺失凭据和不可用工具不原样重试。只对幂等读取或已核实可安全重试的操作自动重试；Logo 提交、部署或其他产生副作用的请求超时时，先检查真实任务/目标状态，不盲目重复提交。App 运行时的协议加载与启动分别采用第 7.6、7.1 节的更短预算，不沿用开发期 60 秒等待。
4. Logo 12 候选优先阶段从首次访问生成服务起设定 30 分钟墙钟截止时间，包含打开页面、提交、查询和重试；不通过扣除只读检查或规划耗时延长该期限。记录截止时间与下次允许检查时间，查询间隔不少于约 30 秒，单次等待/工具调用不超过 60 秒并持续提供有意义的进度；工具支持非阻塞状态查询时优先使用。正常路径中，未校验真实 Logo 并完成明亮主题设计前不推进 App 实现，Logo 取色可选，页面渐变令牌必须实际消费；期限到达后停止主动等待与重复查询，按第 2.5 节记录限制并继续可完成工作。若之后任务边界或服务事件直接提供真实完成结果，可一次性获取、校验并更新受影响品牌素材；需要参考取色时再提取真实色彩，不另开等待循环、不重复提交。
5. 依赖安装、构建和测试命令至少每 60 秒检查输出与进程状态。有实质进展时继续；连续 5 分钟无进展时先诊断进程、网络和锁，再修复或切换可用方案。同一失败最多 3 轮，每轮必须有新的证据或改动，禁止原样循环。
6. 工具或本地技能文件缺失时先检查实际可用能力与已知位置；能直接实现的本地任务使用等价流程，但 AppListing 是例外：只接受安装器同步的远程 `ios-app-listing` checkout，不能用等价本地实现。缺少素材 API 凭据或资源下载技能时，按第 10.6 节继续尝试可用的公开网页搜索、素材来源页与合法下载途径，不能直接跳过第三方真实照片搜索。遇到 403、429、超时、登录墙或无许可证据时立即记录可观察结果，切换另一个合规来源或英语同义查询；不要绕过访问控制、反复请求同一失败地址或把搜索缩略图当文件。经有限跨来源尝试仍不可用时，可用明确标记的开发资源继续独立页面、About 整理和 Review Remarks；真实照片要求保持 `Blocked`，不能以原创插画替代后标为通过。Logo 的生成来源不要求统一，按题材、质量和可用性选择并记录实际网站、工具、模型与任务证据，不能把某个供应商作为强制入口。
7. 确认后的外部故障只影响依赖它的子任务，继续完成所有无依赖任务。故障记录包含失败步骤、可观察错误、尝试次数、替代结果和影响；不得新增未经要求的“等待确认”，也不得只写“等待服务”后结束整项任务。第 3.4 节的初次思维导图确认是唯一的流程性等待点；图库或 Logo 失败只使对应素材/品牌验收保持 `Blocked`/`Not verified`，不阻断基于已核实事实的独立开发与质量记录。远程 `ios-app-listing` checkout 缺失、来源/分支/revision 不符或执行失败时，仅将 AppListing 及其依赖的 About/目录整理阶段标为 `Blocked`，不得读取资料包副本、旧安装或以手写页面替代；安装器恢复同步后从该阶段继续。若远程生成器发现 Logo 候选缺失，按远程技能自身的输出契约记录失败并继续其允许的验证步骤，不把缺图称为已通过。
8. 任务恢复或上下文压缩后先检查创意状态、来源、生成请求或同意来源、思维导图版本、确认来源和第 0.8 节执行记录：已确认时核对文件与进程的真实状态，从下一步继续，不重做仍有效的已验证步骤、不重新要求确认；创意仍缺失时保留原输入等待状态，不重复询问，不将其误记为思维导图待确认。已有有效生成请求且尚未生成时直接生成，已有创意则继续规划；方案尚未展示时为 `Draft`，已展示但未确认时保持 `Awaiting confirmation`。AppListing 阶段核对技能生成状态、配色核验、目录改名与站点白名单；Review Remarks 阶段核对事实来源、生成状态和完整白名单，从最近一个未完成步骤继续，不引入域名状态或线上部署等待。只复验新改动影响的范围；证据过期或实现已变时不能沿用旧结论。确认后只有全部可执行任务均已完成，且剩余事项确实依赖不可用的外部条件时，才以真实状态交付。有限诊断耗尽不代表已知本地缺陷自动通过，应尝试有依据的替代路径并准确记录残余缺陷。

本节的超时与重试上限只约束无进展等待和故障处理，不是整个 Flutter 工程的制作时限，也不能用于压缩 UI、资源或质量验收。整个工程按第 0.2.3 节不限总制作时长，以第 11.9 节的实际成果和质量证据决定完成，不按历史 3 小时/8 小时、首次构建成功或最低迭代轮次自动结束。

Logo 实际生成失败时，先按第 2.5 节切换为其他实际可用、满足同样质量/格式要求的图像模型、工具或网站，再决定是否使用开发资源回退；无需另行询问。按第 2.5 节先生成四种画风各 3 张的 12 个独立候选；12 次初始提交与最多 12 次补图共享最多 24 次生成提交及整组 30 分钟墙钟预算，不按候选、模型或并发重置；状态不明的提交先查任务，不盲目重复。无可用替代模型或预算耗尽时如实记录并继续本地交付。

### 0.7 按实际功能配置 iOS 权限与数据使用规则

开发者的全权授权不代替最终 App 用户的 iOS 系统授权。按实际使用的 API、最低 iOS 版本、Flutter 插件及其原生实现确定配置；发布前以 Apple 最新官方要求复核，不能照抄旧模板。最低部署版本按第 0.10 节设置与验收。

下表是主题能力矩阵的最小覆盖，不是可以跳过的旧版可选清单。先从批准的主题工作台建立“功能页面/动作 → 调用 API/插件及版本 → 是否适合主题 → 系统授权 → 用途键/权限宏/entitlement/capability/隐私清单 → 授权时机 → 拒绝降级 → 运行证据”映射。每个适合主题的能力必须接入真实用户结果；不适合项必须有主题和平台依据，不得只写“未选择”。显示随包图片或播放已有音视频不等于使用相册、摄像机或录音权限。

| 能力 | 配置与授权 | 正确触发与拒绝处理 |
| --- | --- | --- |
| 摄像机拍摄（仅实际选用时） | `NSCameraUsageDescription`；实际访问摄像机前检查并请求系统授权 | 用户点击主题相关拍摄动作时才请求；拒绝或受限时保留实际存在的其他路径与已有内容，不假设 App 另有相册功能；无设备时明确说明 |
| 麦克风录音 | `NSMicrophoneUsageDescription`；使用当前系统与插件支持的录音授权 API | 用户点击录音时才请求；拍照不连带申请麦克风，带声音录像确实需要时分别处理两种权限 |
| 相册选择与导入 | 优先使用 `PHPickerViewController`、`PhotosPicker` 或原生实现等价的 Flutter 系统选择器；仅取得用户选中的项目，不额外请求整库权限 | 用户点击导入时显示选择器；取消不报错。处理格式、大小、方向及 iCloud 项目下载失败，不伪造导入成功 |
| PhotoKit 相册读取 | 只有确实需要枚举或管理照片库时才使用 `.readWrite` 并配置 `NSPhotoLibraryUsageDescription` | 接受 `.limited` 授权并提供系统管理已选照片的入口；不得要求开放全部照片才允许使用 App |
| 保存到系统相册 |
| 通知/提醒 | 若主题有提醒、复习或回访价值，配置通知用途说明并请求授权；拒绝后保留 App 内提醒/历史 | 在用户创建提醒或开启回访时请求，拒绝可在设置中重试，不阻断主任务 |
| 定位/地图 | 主题需要地点、路线或地理分析时配置定位用途与地图能力 | 仅在地图/位置动作触发；拒绝后允许手动地点或无地图模式 |
| 日历/提醒事项 | 主题结果需要日程、提醒事项或时间线同步时接入对应 EventKit 能力 | 用户主动导出/同步时请求；拒绝后保留 App 内结果 |
| 联系人/分享 | 主题需要联系人选择、分享或协作交付时接入对应系统 API | 只在选择联系人/分享时请求；拒绝后提供文件或系统分享替代 |
| 文件/文档选择 | 主题需要导入/导出文档时使用 document picker、FileProvider 或等价 API | 取消、格式错误和安全范围失败均可恢复，不伪造导入成功 |
| 蓝牙/NFC | 主题明确需要外设、标签或近场读取时接入对应能力与描述 | 仅在扫描/读取动作触发，硬件不可用有可见替代状态 |
| 运动与 HealthKit | 主题涉及运动指标或健康数据时按 Apple 要求配置授权、能力和隐私披露 | 逐项请求并支持拒绝/撤销，保留不含健康数据的核心路径 |
 若实现此项，按仅添加需求使用 `.addOnly` 并配置 `NSPhotoLibraryAddUsageDescription`；最终按实际 API 核验 | 仅在用户主动保存到相册时请求；拒绝不影响保存在 App 私有目录的内容，不能误报已保存到系统相册 |

权限用途字符串必须为自然、具体的英语，说明该主题中的真实用途，例如拍摄什么、导入后用于什么、录音如何使用；不得写成 `Need permission`、虚构用途或复制与产品不符的示例。检查每个实际发布 target 的最终 `Info.plist`、构建变量和插件配置，防止声明缺失、拼写错误、空字符串或未使用权限残留；新增本地化时同步 `InfoPlist.strings`。

#### Podfile 权限宏设置（尽力配置，不阻断打包）

Flutter 工程创建并确认实际权限插件及版本后，检查 `ios/Podfile`，在运行 `pod install` 和 iOS 构建前执行一次权限宏配置。若使用 `permission_handler_apple`，按当前插件文档和实际调用 API，在既有 `post_install` 中幂等设置所需宏；摄像机、PhotoKit 照片库读取、麦克风分别使用其对应的 `PERMISSION_CAMERA=1`、`PERMISSION_PHOTOS=1`、`PERMISSION_MICROPHONE=1`。仅图片选择器不需要整库读取时，不启用 PhotoKit 读取宏。保留已有 Hook、`$(inherited)` 与其他构建设置，不重复创建 `post_install`，不套用与当前插件版本不符的宏。

实际执行第 9.1.2 节的 `scripts/prepare_ios_config.py`，补齐 `ios/Flutter/AppFrameworkInfo.plist` 的标准 `MinimumOSVersion` 键；CocoaPods 接入 `permission_handler_apple` 时显式传 `--permission-handler`，按真实 API 选择 `--photo-access read-write|add-only|picker|none`。读写模式在已有 Hook 末尾为插件 target 的每个配置设置 `PERMISSION_PHOTOS=1`，避免被前面的旧设置覆盖；保留其他宏，不改 Runner 的宏。该工具先完整验证、备份再写入，默认仅检查，不能以其成功代替 Pods 解析设置、用途键、ATT 清理及真实构建验收。

宏写入、自动配置脚本或宏语法校验失败时，不得因此终止工作流或跳过打包：保留/恢复最后一个语法有效的 `Podfile`，记录失败步骤与原因，继续对该有效文件执行 `pod install` 和 Flutter iOS 构建/归档尝试。宏配置命令的失败状态与 CocoaPods/构建命令的真实结果分开记录；不得用忽略所有错误的方式掩盖独立的安装或构建失败。失败的宏不得报告为已配置，受影响的权限运行路径须标记为未验证或受阻；仍需核对最终 `Info.plist`、解析后的 iOS 构建设置及实际运行授权路径，不以 Podfile 文本单独判定权限完整。

本流程不集成追踪功能，也不申请 ATT 权限。权限矩阵、思维导图、状态模型、页面、启动准备及测试计划均只处理实际实现所需的受保护能力，不创建追踪授权入口、弹窗、四状态流程或触发条件，也不将其列为待实现功能。

### 0.8 执行记录、状态与恢复

执行记录只服务开发，不是 App 用户账号、协议同意记录或运行时数据。确认前写入独立规划文档；确认后统一在项目根目录的非公开工作目录（例如 `.codex-work/`）维护，记录真实路径，不把执行记录、质量报告、品牌取色记录、备份或其他开发文件写入 `aduit/`。仅第 12.2 节生成的最终 `aduit/review/remarks.md` 是审核材料白名单例外，不得用其他新增文件保存台账，也不要为了建台账重复复制全文或创建 Git 产物。

| 维度 | 可用值 | 判定边界 |
| --- | --- | --- |
| `Idea status` | `Awaiting idea choice`、`Awaiting user idea`、`Generating`、`Ready` | 分别为已询问是否生成且未收到明确回答、用户选择自行提供但尚未给出创意、按明确请求正在生成、已有可用于规划的具体创意；与思维导图批准状态分开 |
| `Git input status` | `Awaiting user repository`、`Ready` | 第 1.5 节用户 Git 仓库地址缺失或已有当前任务可追溯地址；输入齐全不代表已关联或联网验证 |
| `Name status` | `Awaiting user name`、`Ready` | 第 1.3 节用户项目名称缺失、已取得可追溯的用户名称；主题已生成不代表名称已取得 |
| `Plan approval` | `Draft`、`Awaiting confirmation`、`Approved` | 只依据第 3.4 节，批准版本及确认来源单独保存 |
| `Decision source` | `Confirmed`、`Selected`、`Assumption` | 分别为用户明确给定、自主选定、缺失细节的假设，不表示已经实施或获批 |
| `Task status` | `Pending`、`Running`、`Done`、`Blocked`、`Deferred`、`Not applicable` | `Done` 表示操作已完成；`Blocked` 记录具体依赖或故障；暂缓与不适用需有范围依据，必做项不得借此排除 |
| `Verification` | `Verified`、`Not verified`、`Failed`、`Blocked`、`Not applicable` | `Verified` 必须对应当前产物的实际通过证据；未运行、失败、无法运行和不适用分别记录 |
| `Delivery` | `Local only`、`Published`、`Not published` | 本地完成不等于已上线；`Published` 只表示实际发布完成，公开访问仍须另行验证 |

例如摄像机可以是 `Task status: Done / Verification: Blocked`（缺真机），About 可以是 `Task status: Done / Verification: Verified / Delivery: Local only`。`Not implemented` 用于明确尚无实现的结果说明，不能用来描述已实现但未实测；`Deferred` 不等于不适用。正文出现简写状态时必须说明是哪个任务或验证项。

每条执行记录至少包含任务 ID、对应需求 ID、当前产物/路径、上述适用状态、依赖、证据、最近动作和下一步。外部作业另记任务 ID/位置、开始时间、截止时间与下次允许检查时间；最终材料阶段记录 AppListing 技能生成、About 页面配色核验、目录改名/整理、Review Remarks 事实来源、白名单核验及本地产物路径。关键错误记录可观察信息，日志脱敏，不记录密钥、用户私有媒体或无关个人信息。里程碑、真实阻断、确认来源和恢复点变化时更新，不为每个点击制造文档工作。

创意输入另记第 1.1 节的 `Idea origin`、`User idea`、`Generated idea`、`Effective idea`、用户约束、是否已询问及生成请求或同意的对话来源。用户同意生成后尚未产出具体创意时，设为 `Idea status: Generating`，记录生成任务 `Running` 并立即处理，不继续停在输入等待状态；创意形成后设为 `Idea status: Ready`，`Plan approval` 仍为 `Draft`，不能自动变成 `Approved`。

Git 输入另记第 1.5 节的 `Git repository URL`、用户消息来源及状态，恢复时保留；第 22 步验收后的关联/分支结果单独记 `Git handoff`，不能把工具仓库地址当成用户工程地址。详细命令及冲突处理见第 13.1 节；全流程不暂存、不提交、不推送代码，等待用户自行提交。

名称与路径另记第 1.3 节的 `User project name`、`Name source`、`Name status`、显示名称/目录名/内部标识映射，以及第 0.4 节的 `Invocation cwd`、`Workflow resource root`、用户指定路径原文与最终 `Target project root`。任务恢复时同时检查创意和名称：只要必需输入仍缺失，就保留原等待状态；不要从文件名、资料目录、旧计划或主题生成结果推断用户已给出名称。确认后所有产物与命令都以记录的工程根目录为准，不能因读取技能而改动输出位置。

并发以依赖为依据：先完成 Logo 优先阶段与明亮主题设计，或记录第 2.5 节规定的真实失败回退，之后独立页面、资源筛选和本地协议可交错推进；同一文件、资源清单、构建目录或品牌引用的修改按先后顺序合并并核验。没有安全的后台能力时用短状态查询与任务交错，不虚构后台进程、子任务或完成通知。提交与等待分开，任何阶段退出都不能丢失其他任务的下一步。

### 0.9 模拟器启动时机、复用与数量限制

1. **先完成工程创建**：Logo 优先阶段后创建 Flutter 工程时，不启动 Simulator、不 boot 模拟设备、不安装或启动 App，不用模拟器等待创建进程。只读查看已有设备列表和状态允许先做。新工程以创建命令实际成功退出、必需目录/文件完整且创建阶段依赖解析完成为准，至少核对 `pubspec.yaml`、`lib/main.dart` 和 iOS 工程；创建失败或仍在运行时先修复，不通过打开模拟器掩盖问题。复用已有工程时核对相同的基本就绪条件，不重建已有项目。
2. **就绪后测试页面**：工程创建完成，且当前待测页面已具备可构建、可运行版本后，才启动或连接现有模拟器，安装运行并检查页面。允许逐步开发、逐页测试，不要求等所有功能或全部精修完成后才运行；构建不需要已启动模拟器时，可先完成构建再启动测试设备。
3. **只复用现有 iPhone**：先只读查看设备类型、运行时与启动状态，筛选运行 iOS 的现有 iPhone 模拟器；用户已指定且符合该范围的设备优先，否则复用已启动且兼容的 iPhone。没有合适的已启动 iPhone 时，只启动一个已存在且运行时可用的 iPhone。记录型号、iOS 版本和 UDID，后续运行、截图、UI 检查和测试均明确指向同一 iPhone，不使用默认设备选择，不新建、克隆或批量启动设备；已启动的其他设备不能成为回退目标。
4. **同一时间只使用一个**：本任务同一时间最多使用或启动 1 个 iPhone 模拟器；UI 精修、截图与交互测试共享它，避免多个运行器同时安装/启动 App 或争抢截图。工具提供并行测试、自动克隆或多个 UI worker 时，使用其实际支持的串行/单 worker 配置关闭这些行为，不猜测参数。小屏、标准屏、大屏 iPhone 或其他支持的 iOS 版本按风险选择现有 iPhone 并依次测试，先结束当前测试会话再切换，不因数量限制削减必要的 iPhone 适配检查。
5. **保留无关会话**：记录测试前已有设备状态与本任务启动的设备；任务前已运行或属于用户/其他任务的模拟器不擅自关闭、重置、删除或清空数据，不使用全局 shutdown/erase。需要切换时，仅停止本任务 App/运行器，按需关闭本任务自行启动且无其他会话使用的设备；验证结束后释放本任务测试进程与媒体资源，保留用户已有会话。
6. **不可用时有限回退**：没有兼容的现有 iPhone、iOS 运行时缺失、Simulator 控制不可用或启动失败时，按第 0.6 节有限诊断并记录受限范围，不改用其他设备或平台，不连续启动多个实例、不临时创建新设备或下载运行时；继续可执行的静态分析、iOS 配置检查及无需模拟器的构建，但不把未实际点击运行的页面标为通过，也不以工具限制卡住所有独立工作。

将创建命令退出结果、工程就绪证据、选用设备/UDID、复用或启动时间、逐台测试顺序与具体结果写入第 0.8 节已有执行记录；第 6.7、11.3、13 节的页面检查统一遵守本节，不新增设备选择或逐轮测试审批。

- **稳定目录、串行会话**：复用当前工程已有 build 和工具可配置的 DerivedData/结果目录，不按页面、时间戳或随机 ID 克隆输出。只运行一个本任务构建/安装/调试会话，按工具实际支持关闭并行 worker、自动克隆。替换会话前正常结束本任务旧调试连接、录屏、日志流与媒体句柄，防止孤儿进程持续占用内存；不影响无关会话，不删减 App UI 效果。
- **有限保留、精确清理**：默认保留当前可运行产物；覆盖更新确需回滚时最多另留一份最近可用产物，验证新安装后移除本任务失效的旧 .app、重复 IPA/archive、临时测试目录与无用结果附件。清理前核对归属、精确路径和恢复依赖，保留必需截图、日志及故障证据。不全局清理 DerivedData/Downloads、不重复执行 flutter clean，不删源码、assets、根目录 aduit、依赖缓存、用户数据或其他项目产物。缓存损坏须有依据并局部处理，随后更新同一安装并复验。
- **身份可追溯**：在已有 `.codex-work/quality.md` 和执行记录中登记 Bundle ID、配置、UDID、构建标识/产物路径、当前安装版本、复用/更新原因、结束进程与精确清理路径；续作先核对实际安装，匹配即复用。身份不明或版本不符不能拿旧证据通过验收。本规则减少重复产物的磁盘占用和并发进程的内存压力，不取消必要构建、测试及最终证据。

### 0.9.2 执行时间优化与增量复验（不改变验收范围）

执行优化只减少重复读取、重复静态检查、重复构建和无进展等待，不减少任何页面、功能、资源、权限、截图、协议、游戏或 Git 验收细节。先按顺序完整读取一次入口和十份工作流正文，建立全局索引，至少记录章节、需求 ID、页面 ID、依赖关系、检查器、证据路径和当前状态；后续任务按页面和受影响章节读取，不能为每个子任务重复从头扫描全文。每次需求、资源或配置变更后，依据索引和依赖图只重跑受影响节点及其下游，不变节点可以复用已有结果；依赖关系不明时按更大影响范围复验，不能把不确定性当作通过。

互不共享工程目录、资源清单、构建目录、Simulator、日志流、截图目录或可变状态的静态检查、文案生成和材料整理可以并行；会写入同一工程或共享资源的生成、构建、安装、真实 App 点击、日志捕获、录屏和截图必须保持单会话串行。并行检查完成后按原验收顺序回放输出和状态，任何一个失败仍返回失败，不能因并行而跳过或提前宣布通过。真实 App 的 build/install、Simulator 交互和最终证据永远不能用并行静态检查替代。

每次检查记录输入指纹（相关文件内容哈希及关键外部输入）、脚本/技能版本、命令与工作目录、开始/结束时间、耗时、退出码、证据路径和状态。输入、脚本版本与依赖均未变化时可复用结果；任一变化必须使对应检查失效并重跑，构建输入不变时复用同一 Bundle ID、配置、DerivedData/输出目录和安装。等待外部任务或终端时使用有界等待、有限重试和可观察进展；连续无进展或达到上限就记录 `Blocked`/`Not verified`，立即继续不依赖的任务，恢复后再按受影响范围补做。优化过程不能把缺失日志、截图、产物或运行证据改写成 `Verified`。

1.1 **Xcode 目标与方向硬门槛**：验收 Xcode target 的 General 页面时，Supported Destinations 仅保留 iPhone；移除 iPad、Mac、Mac Catalyst、Apple Vision/visionOS 等其他 destination。iPhone Orientation 仅勾选第一个 Portrait，取消 `Upside Down`、`Landscape Left`、`Landscape Right`；若工程已有其他方向勾选，必须在验收修正后重新解析构建设置与产物，再继续后续验收。

3. **原生配置**：在实际参与构建的配置中，使应用 target 和 UI 测试 target 的 Debug、Profile、Release 及自定义配置最终解析为 `TARGETED_DEVICE_FAMILY = 1`，`SUPPORTED_PLATFORMS` 仅为 `iphoneos iphonesimulator`，并令 `SUPPORTS_MACCATALYST = NO`。不得启用面向其他设备或平台的兼容选项；若工程或工具存在此类设置，必须关闭并核验最终解析值。核对继承值与覆盖值，不以源 `Info.plist` 手写字段代替 Xcode 设备 family 设置。

### 0.11 Apple 4.3 与 5.6 工程级发布门槛

Apple 4.3 与 5.6 不是只在提交表单里检查的文案问题，必须在创意、工程、测试和交付材料中形成可追溯证据。下列规则属于发布前硬门槛；失败项要记录在项目根目录 `.codex-work/app-review-risk.md`，不能在最终报告中写成 `Verified` 或“可上架”。不相关的本地产物仍可继续生成，但不能用外部阻断掩盖这些风险。

1. **4.3(a) 产品身份与变体**：一个产品只使用一个真实的 Bundle ID 和一套可验证的产品身份；不为同一产品批量创建地区、品牌、主题、名称或 Logo 变体，也不把同一二进制复制到多个应用记录。检查 Bundle ID、显示名称、App Store Connect 记录、截图、About、Support 和 Review Remarks 的一致性，记录实际核验结果。
2. **4.3(b) 实质差异化**：每个项目在思维导图确认前建立差异化 brief，至少写清目标用户的具体问题、现有替代做法、主题专属内容模型、标志性核心动作、首个有用结果和可回访成果。实现必须在领域数据、任务顺序、交互规则和结果状态中体现这些差异，并有当前 iPhone 构建证据。只更换名称、Logo、渐变、字体、图片、文案、卡片尺寸或导航外壳不构成差异化；复用代码时必须逐项说明哪些共享能力不会抹平产品差异。
3. **禁止审核或分发操纵**：不创建隐藏审核模式、审核专用内容、远程开关来临时改变功能、虚假账号、伪造测试/计费/服务/权限结果，或用安装量、引荐、搜索词、榜单、评价和推荐机制操纵发现。所有功能必须对普通用户和审核人员按同一事实运行。
4. **5.6.1 评价行为**：不自定义评分弹窗、不诱导好评、不以奖励或解锁换评价、不要求用户提供五星反馈；若产品确实需要请求评价，只使用 Apple 的系统评价 API，并验证触发时机不打断核心任务。没有该功能时不创建相关入口、文案、依赖或测试。
5. **5.6.2 身份与公开材料**：开发者身份、支持渠道、App 名称、描述、分类、截图、About、Intro 和 Remarks 必须来自已确认事实并能相互核对；不虚构运营主体、联系方式、测试设备、服务、地区、账号、计费或用户数据处理。缺失信息写入内部记录，不用营销措辞补齐。
6. **5.6.4 质量与诚实状态**：启动白屏、崩溃、占位图、死链接、无效按钮、错误权限、数据丢失、虚假功能和无法完成的核心任务必须在发布前修复或明确阻止上架。`Not verified`、`Blocked`、`Failed` 与发布状态分开记录，不能把“流程继续”解释为“质量通过”。

最终复核必须同时输出差异化 brief、产品身份核对、评价/发现操纵扫描、材料事实核对、核心质量结果及残余风险；统一写入 `.codex-work/app-review-risk.md`。只有适用项全部有证据、没有关键失败时，才可报告 `Release readiness: Ready for submission`。
