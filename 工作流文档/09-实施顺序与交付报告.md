## 13. 实施顺序

> 独立页面、素材、协议页、静态检查和文案任务可并行推进；某一项无新输出或暂时受阻时记录阻断并跳过到可执行任务，不重复轮询同一无进展终端会话。游戏项目的核心闭环不得被并行任务绕过：先完成“专用引擎必要性决策”，再按 `engine` 或 `flutter_native` 路线完成对应可玩垂直切片，最后扩展全量玩法。所有页面的路由最终汇入 Flutter 原生 Navigator，GetX 禁用检查必须在最终 iOS 验收前完成。

先判定项目类型，再决定是否执行游戏引擎与游戏闭环任务：将项目记录为非游戏、游戏或混合。只有用户选择游戏主题，或创意明确包含真实游戏模块时，才执行第 9.6 节；非游戏项目跳过游戏决策、引擎场景、游戏入口和游戏专项验收，继续其自身主题的页面、动效、数据与质量任务。游戏/混合项目在规划阶段先建立 `.codex-work/game-engine.json`，明确 `implementation_mode`、`engine_required` 和 `decision_reason`；复杂实时玩法再记录精确引擎名称/版本、入口、场景资源、运行时所有权、原生桥和构建命令，Flutter 原生玩法则记录 Dart 入口、动画/效果工具和六部分效果提示词。缺少该决策契约时不得进入玩法扩展。

非游戏项目并行执行“真实能力与视觉工具决策”，但不能因此跳过质量门槛：先为地图、图表、媒体、3D、时间线、动态背景、扫描、定位、日历、语音和数据可视化等适用能力建立 `capability` → `real_tool_or_sdk` → `version` → `license/source` → `actual_consumer` → `fallback` → `runtime_evidence` → `formula_record` 链路。地图必须选真实地图 SDK/真实瓦片/许可地理数据并规划缩放、平移、定位、标记、路线或图层；禁止线条、色块、静态截图、假网格和手绘道路。组件目录只帮助比较选型，不把“安装所有包”当作完成；所有动态任务按六部分效果提示词公式记录数字参数、版本/许可证、Reduce Motion 与失败回退。非游戏不接入游戏引擎，但必须达到与游戏项目相同的精致视觉、真实消费者和当前 iPhone 证据标准。

生成 Review Remarks 时按第 12.2 节使用实际存在且大小写正确的 `Intro.md`/`intro.md` 文件；先列基本信息，再用七个精确英文标题 `Actual Device`、`Test Devices and Operating Systems`、`App Purpose, Intended Audience, and Problem Solved`、`Setup Steps`、`External Services`、`Regional Differences`、`Unique Value`。第 1 项按第 12.2 节的当前 Apple 规格快照，依次写 `- iPhone 18 Pro, iOS 27` 与 `- Screenshot size: 1206 x 2622 pixels (portrait).` 两条项目符号；实际原始竖屏截图核验宽 1206、高 2622，不裁切/缩放其他机型凑尺寸，不把配置本身当成真机测试或截图通过证据。第 2 项固定按顺序列出 `iPhone 15 Pro, iOS 18.6` 和 `iPhone 13, iOS 17.7.1` 两条精确配置，不随机、不替换、不遗漏、不新增；第 1、2 项各自非空且不得互相替代。保留用户指定配置，只有当前 App 的真实记录或用户明确确认才支持测试完成声明；未知结果省略，缺口只记内部；通读全文并删除所有其他设备、系统、测试、兼容性和排除示例。登录/账号、计费、外部服务及广告/AI/第三方 SDK 逐项核实；未知、待提供或无法核实的字段直接删除，不写 `Not provided; pending confirmation.`，只有确认未使用才写 `Not used.`，无功能才写 `No such feature`。不要复制与产品不符的登录/计费测试宣称。第 6 项固定写 `All regions are the same.`，须先核实实现地区一致。最终仅英文、不超过 4,000 字符、不用 `**`、不暴露自有内部 package/模块；生成后运行 `validate_review_remarks.py`。

第 17 步完成 `AppListing/` 到 `aduit/` 的改名整理并立即新建空的 `aduit/imgs/` 后，先执行协议页视觉顺序硬门槛：逐页完成三个协议页的主题色、背景、图片、排版和实际渲染复核，再进入具体项目名 HTTP 协议链接注册与 Review Remarks。随后第 18 步生成 Review Remarks 前，必须按第 12.1 节完成具体项目名 HTTP 协议链接注册、Initialization 页协议文案及 Entry/Settings 链接接入和定向回归。三个链接固定为 `http://【项目名称】/PrivacyPolicy.html`、`http://【项目名称】/Terms&Conditions.html`、`http://【项目名称】/Support.html`；三个文件名保持原样，App 内用 WebView 显示且不跳转外部 App。只有实际采用 `Clear Data`、确认并完成真实清除后显示的 Initialization 页底部实际呈现 `By continuing, you agree to our` 换行 `Terms of Use and Privacy Policy`，两处链接分别可点；Welcome、其 HTML 引导页和原生启动页均没有该协议文案。Settings 只提供 Privacy Policy、Terms of Use、Support 三个入口，站点首页不进入 Settings。使用无网络 WebView stub/fake 验证文案、布局、映射与失败状态，不访问或检查真实 URL 有效性，WebView 失败不得阻断 App 其余流程。完成检查或记录客观受阻证据后继续生成 Review Remarks，不无限等待外部验证通过。第 18 步和其他任务均结束后，还必须执行第 19 步最终图片加载检查，接着完成第 20 步最终 iOS 权限双向校验及修复复验，执行第 21 步的五张项目截图；全部验收通过后执行第 22 步 Git 交接，再提交最终报告。

运行验收贯穿第 6–21 步：按第 0.9.1 节首次安装真实 App 后复用同一 Bundle ID，不按页面、用例或轮次新建调试包；资料包 flutter_check/ 只验证工作流自身。无变化复用，必要变更增量构建并覆盖同一 Bundle ID，最终验证对应最新产物。复用现有 iPhone、稳定输出目录和单一串行 runner，结束本任务多余进程并精确清理失效副本，保留必需证据，不缩减 UI 或跳过复验。最终报告在既有构建/验证结果中说明复用、覆盖更新和清理情况。

### 13.1 验收后的 Git 交接

第 22 步是最后一项工程操作。所有适用功能、视觉、资源、平台、材料、工程独立性及五张最终截图验收均通过，且受改动影响的证据已更新，才可开始。若仍有 `Failed`、`Blocked` 或 `Not verified` 的必需验收，记录 `Git handoff: Deferred — acceptance incomplete`，继续可执行的整改和独立任务，不能为完成 Git 步骤提前关联仓库、建分支或声称验收通过。这里的验收是既有工程验收，不新增用户确认。

执行时使用 `flutter-engine-runner/scripts/prepare_git_handoff.py`，不要只手写几条 remote/branch 命令。脚本是可复核的本地交接实现：它要求目标是真实 Flutter 工程根目录，必要时在该根目录执行 `git init`，确认工程根目录拥有自己的 `.git` 且 `.git` 归属于工程本身，准备 `feat/1.0.0`，写入用户 remote，解析 `user.name`/`user.email` 并生成 `.codex-work/git-handoff.md`。没有首个提交的新仓库仍可保持 `unborn`，但必须已经完成本地初始化；身份缺失时标记 `Git handoff: Not directly commit-ready`，不编造身份。

- **确认工程边界与原状**：读取第 1.5 节用户提供的 `Git repository URL` 和来源，实际命令显式指定 `Target project root`。先检查该目录自己的 `.git` 及 `git rev-parse --show-toplevel`，解析真实路径后须与工程根一致；共享 worktree、父仓库、子模块或其他工程边界不能冒充工程自己的仓库，发现后保留原状并记录具体冲突，不能改动父仓库、资料包、技能或依赖仓库。存在仓库时先记录 HEAD、`git status --porcelain=v1`、索引/工作区差异与远程配置，后续核对不丢失文件、修改及既有暂存内容。
- **本地初始化**：工程没有自己的仓库且不在父仓库控制下时，可在工程根执行 `git init --initial-branch=feat/1.0.0`。允许空仓库保持 `unborn`，不要求 HEAD 提交、不创建初始或空提交；用 `git symbolic-ref --short HEAD` 核对分支名，无 HEAD 时明确记录。已有自己的空仓库也可用 `git symbolic-ref HEAD refs/heads/feat/1.0.0` 设置未出生分支，先确认没有同名有效分支，并保留索引和全部文件。
- **关联用户远程**：脚本先核对已有 remote 的全部 fetch URL 与显式 push URL；已有同地址远程则复用；没有 `origin` 时执行 `git remote add origin <用户模板地址>`。已有不同 `origin` 时保留其原配置，优先复用其他同地址远程，否则新增未占用的 `user-origin`（必要时附唯一序号），报告实际 remote 名，不自动 `set-url` 或删除原远程。多个地址或 push URL 指向其他地址时保留并新增独立 remote。地址作为独立参数安全传递，不作为 shell 代码。这里只验证本地关联，不需要凭据、联网、clone/fetch、远端分支或 push 测试；不能声称远程访问已通过。
- **创建与切换分支**：已有提交的仓库从当前本地 HEAD 执行 `git switch -c feat/1.0.0`，不拉取或切换远端默认分支。当前已经是该分支则复用；同名本地分支已存在且指向当前 HEAD 时可安全 `git switch feat/1.0.0`。同名分支指向不同提交、切换会覆盖修改、仓库处于未完成合并/变基等状态时保留代码及分支，记录 `Git handoff: Blocked` 和具体原因；不能强制重置现有分支，或切换到未经当前验收的其他代码。对 detached HEAD 也从其当前提交建分支。分支名用 `git symbolic-ref --short HEAD` 实查，不因无提交而误判失败。
- **保留代码待用户提交**：交接脚本不执行 `git add`、`git commit`、`git push`；不创建任何提交，不自动 stash、reset、clean、merge、rebase，不覆盖文件或改变原有暂存范围。Git 配置或分支操作受阻时保留真实证据，不用提交或丢弃代码来凑成功。已有提交的前后 HEAD 必须不变，空仓库交接后仍为 unborn；新增/修改文件及原有暂存状态保持，流程记录自身的正常新增另行说明。交接记录明确列出未执行的三项命令，用户打开 Git 界面即可自行暂存和提交。
- **最终核对与交付记录**：在 `.codex-work/git-handoff.md` 记录工程绝对路径、用户地址/来源、实际 remote 名、全部 fetch/push URL、当前分支、HEAD 或 unborn、操作前后工作区与暂存状态、命令/退出码、提交身份、验收依据和 Git 交接结果。核对未产生新提交、未推送、代码均保留后，最终报告写明“已初始化、已关联、未提交、未推送，等待用户自行提交”；若身份缺失则写明无法直接提交及缺失字段。该记录仅为可删除的内部记录，不加入 `aduit/`。分支/关联失败与工程验收结果分别报告，不能把配置成功当成验收通过，也不能把本地关联冒充已上传代码。

## 14. 最终报告格式

### 15.1 4.3/5.6 最终报告门槛

第 14 节最终报告必须单独列出 Apple 4.3/5.6 专项结果，并链接 `.codex-work/app-review-risk.md`。至少报告以下事实：

- 产品身份核对：唯一 Bundle ID、显示名称、App Store Connect 条目和公开材料是否一致，是否存在地区/品牌/主题克隆。
- 差异化证据：目标用户问题、领域模型、主题专属核心动作、任务顺序、首个有用结果和可回访成果对应的页面、路由、数据和当前 iPhone 证据；Logo、配色、图片、字体、文案或卡片变化不能单独计为差异。
- 5.6 诚实性检查：开发者/支持信息、功能、权限、设备、服务、地区和计费材料是否均有事实依据；是否存在隐藏审核模式、虚假数据、远程换功能、假按钮或不一致的审核路径。
