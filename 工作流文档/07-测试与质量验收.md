Logo 视觉核验还须按第 2.5、10.3 节实际查看原尺寸与图标尺寸，根据主题元素判断模拟现实、手绘、油画或艺术主画风是否选得合理，核对记录依据、提示词和成品一致，记录对应画风的精致度、造型、笔触/材质/光影及小尺寸辨识结果；不得有粗糙简笔、几何色块堆叠、简陋图案、3D 造型或明显 AI 生成感。Logo 及自有界面保持明亮色调，不因特定色名或无渐变判失败；整体灰暗或压黑须修正；生成选项中的“高质量”和文件尺寸本身不代表视觉合格。

### 11.4 反向验收

扫描源码、依赖、路由、文案、资源名、模型、fixture 和快照，确认没有实现邮箱输入、登录/登出、密码、验证码、认证服务、个人协议同意记录、社交、收藏、云端媒体上传或个人资料能力；没有普通项目之外的独立退出/登出流程。非游戏项目每次启动进入 Welcome 并使用 `Continue`（引导页接入前的开发预览可用 `Enter`）；游戏/混合项目每次启动只进入 `lib/welcome.dart` 的沉浸式游戏大厅，并按 `Play`、`Load`、`Operation` 与顶部 `Exit`、`Settings` 验证对应流程。清除数据只通过 `Clear Data` → 二次确认 → 真实清理成功进入 Initialization 并显示 `Enter`，不能用其他名称恢复旧退出行为。普通返回、关闭预览和单条媒体删除仍须可用。能力矩阵中的适用摄像机、相册、麦克风、通知、定位、日历、文件、蓝牙/NFC、运动/HealthKit 与私有数据路径必须保留并验证，不得将合法功能误删；不适用项反向核验无残留，并记录其依据。词汇命中必须结合上下文判断；第三方依赖内部名称、明确说明不支持该能力的法律文案和测试描述不构成违规，不得因纯关键词命中删除有效产物或反复重写。`AppFlowState`、系统权限状态、清除恢复标记和协议 WebView 属于明确允许的能力。

显示文案另行验收，不把上述工程能力扫描当作 UI 文案通过证据。

先运行 `python3 <flutter-engine-runner-root>/scripts/validate_public_copy.py --project-root <target-project-root>`。该只读补充扫描覆盖可检测的 Dart 直接 UI 字符串、独立 `aduit/welcome.html`、三个协议静态 HTML 页面与无障碍属性，检查第 6.6 节的中文及禁词（含大小写、空格及 HTML 实体/分标签变体）；不扫描 `.codex-work/`、内部标识或 Remarks。它不解析完整 Dart 数据流或 JavaScript，不证明间接/拼接字符串、种子数据、图片嵌字、视频字幕及系统界面全部合格；扫描无命中后仍须执行下列显示复核。Remarks 的真实外部服务与必要事实按第 12.2 节单独披露，不因 UI 禁词而隐瞒或误写为未使用：

### 11.5 可选媒体轮换

只有智能体判断主题确实需要轮换时才启用，不询问用户是否开启。轮换是可选机制，第 10.5 节的资源多样性、去重和两轮资源调整始终必须执行，不能因未启用轮换而省略：

- 每个状态或分类至少四套专属图片/视频。
- 同一状态连续四次成功更新不得复用相同图片或视频。
- 不同状态的轮换池不能共享路径、SHA-256 或相同原始内容/视觉重复组；统一品牌和确有语义的一致内容展示按第 10.5 节说明复用，不混入轮换池凑数。
- 失败或取消不得推进轮换索引。

#### 最终 iOS 权限双向校验（最终截图前执行）

全部实现、AppListing/About、协议回接、Review Remarks、目录整理、图片显示与依赖清理完成后，第 12.5 节最终五张截图前执行。先按第 11.6.1 节检查 iOS 配置文件、构建日志和 ATT 残留，再以当前实际可达功能、代码调用、依赖版本和最终构建为准，从功能正查所需配置，再从每条配置反查真实用途；验收目标是“该有的完整有效，不该有的全部移除”，不是固定添加三种媒体权限。

1. **实际能力清单**：遍历全部页面、操作、服务、原生代码、插件及其原生实现，建立 `功能/入口 → API → 插件及版本 → 是否需授权 → Info.plist/本地化用途键 → Podfile 宏 → entitlement/capability → 隐私清单 → 触发/拒绝行为 → 证据` 表。相机、相册、录音只是条件项；定位、通知等其他实际使用的受保护能力也须纳入。用户已选但尚未实现的功能记录为缺失，不能通过删除其权限掩盖；未选能力记录不适用，允许三项媒体或全部受保护能力均不存在。
2. **补齐必需项并证实生效**：每个实际需要系统授权的 API 必须有正确、非空且符合真实主题用途的英文说明、请求/状态处理及所需配置。按具体 API 区分 `NSCameraUsageDescription`、`NSMicrophoneUsageDescription`、`NSPhotoLibraryUsageDescription` 和 `NSPhotoLibraryAddUsageDescription`，不套用全部用途键。使用 `permission_handler_apple` 且实际调用 PhotoKit library/read-write API 时启用 `PERMISSION_PHOTOS=1`；`PERMISSION_CAMERA=1`、`PERMISSION_MICROPHONE=1` 也只在当前插件/API 需要时启用。必须核对权限插件所属 Pods target 解析后的宏与编译设置，例如该 target 的 `GCC_PREPROCESSOR_DEFINITIONS`、实际编译命令、`xcodebuild -showBuildSettings` 或等价证据，并记录每个实际宏的解析值；只查 Runner 或 `Podfile` 文本不能证明插件编译已启用。缺失、拼写错误、配置错 target 或未生效均为 `Failed`。保留既有 `post_install` 与继承配置，修复后重跑 Pods/构建和受影响路径。
3. **移除无用途项**：逐条反查最终用途键及 `InfoPlist.strings`、启用宏、授权请求/状态/设置引导、插件注册/依赖、entitlements、capabilities、后台模式及隐私声明。仅为不存在功能准备的内容必须删除，不能保留“以后可能用到”的相机/照片/麦克风权限。确需保留的插件应关闭未用受保护功能的编译开关；移除无用宏，插件必须显式禁用时只保留正确的 `=0` 设置，不能误启用。若未用 API 仍被插件默认链接，裁剪、禁用或更换/移除该组件并重验，不能编造用途字符串消除构建检查。保留其他实际功能与依赖依法必需的隐私清单和 Required Reason API 理由，不把所有声明一律删除。
4. **核对无需授权的场景**：仅用 PHPicker/PhotosPicker/等价系统照片选择器取得选中项目且未调用 PhotoKit 整库 API 时，不额外请求整库授权或添加其用途键/启用宏。显示随包图片不需要照片库权限，播放音频不需要麦克风，拍静态照片不自动需要麦克风；按实际插件实现核实。无摄像机、相册、录音功能且没有其他受保护 API 时，最终不存在相关用途键、请求、启用宏或专用权限插件，并以代码、依赖和产物证据确认；不能靠首次启动没有弹窗就判定无多余权限。
5. **追踪保持移除**：按第 0.7 节检查源码、解析依赖/插件注册、原生链接、脚本、实际数据流、最终 `Info.plist` 与 `PrivacyInfo.xcprivacy`，清除 `AppTrackingTransparency` 请求/链接、`ATTrackingManager`/`requestTrackingAuthorization`、`NSUserTrackingUsageDescription`、IDFA 读取、启用的追踪权限宏和追踪初始化。该项只确认移除，不创建 ATT 授权入口、弹窗或四状态测试。仍追踪的组件须禁用、移除或替换，不恢复该流程作为回退；未解决证据如实记录。
6. **检查最终产物与实际行为**：核验所有发布 target 的解析配置及可用 `.app`/Archive 内最终 plist、entitlements、嵌入清单和链接结果，执行 `plutil -lint` 等有效性检查，不只搜索模板。用当前 iPhone 构建走查每个实际受保护功能的首次触发、允许、拒绝/受限、取消及恢复；系统选择器按其实际分支检查。Welcome/Initialization 不集中索权，无权限功能的应用不出现无关授权弹窗。缺真机/系统状态/产物证据时标 `Blocked`/`Not verified`，不编造验证结果，也不要求为未选功能做硬件测试。
7. **材料与重建复核**：将实际权限/数据流与 `aduit/intro.md`、`aduit/review/remarks.md`、公开隐私政策及可用商店隐私答案逐项比对，去除不存在功能和多余权限的声明，补齐实际用途；保持三个 HTTP 模板、三个协议文件名和大小写不变。配置、依赖或资源变化后重新解析、构建并复测受影响路径，按第 10.7.1 节刷新最终构建上受影响图片、图标与启动证据，最后再次核对产物权限矩阵后才交付；配置未改动且证据仍有效时不机械重复构建。
8. **记录与判定**：将功能范围、每项 `Required/Present/Removed/Not applicable`、具体键/宏及解析值、裁剪/移除路径、构建与设备版本、运行结果和残余缺口记录到 `.codex-work/ios-permissions.md`，并从 `.codex-work/quality.md` 链接；记录不得进入 `aduit/` 或 App bundle。Podfile 宏写入/校验失败仍须保留语法有效版本并继续 `pod install` 和 iOS 打包尝试，但与权限运行结果分开报告。遗漏必需权限、残留无用途权限、实际功能不可用或证据不足均不得标记 `Verified`；只将受影响项如实标记，继续其他可执行任务。

#### 11.6.0 主题能力矩阵与权限扩展验收

非游戏项目不再使用“媒体能力未选即可整体跳过”的窄权限门槛。验收前必须从主题工作台的页面与动作建立能力矩阵，至少评估照片/相机、麦克风/语音、通知、定位/地图、日历/提醒事项、联系人/分享、文件/文档选择、蓝牙/NFC、运动与 HealthKit，以及其他能显著改善主题任务的 iOS 能力。每一项记录 `Selected / Implemented / Runtime verified / Declined fallback / Not appropriate`，并附真实入口、API/插件版本、Info.plist 用途键、权限宏、entitlement/capability、授权时机、拒绝后的可用路径和当前 iPhone 证据。适用能力不能只放权限弹窗或占位页；不适用能力必须写主题与平台依据。ATT、IDFA、追踪授权和广告能力继续移除。

#### 11.6.0.1 非游戏高级能力与真实工具验收（硬门槛）

非游戏项目逐项核对能力矩阵中的 `capability`、`real_tool_or_sdk`、`version`、`license/source`、`actual_consumer`、`fallback`、`runtime_evidence` 与 `formula_record`，并核对 `.codex-work/ui-visual-gates.json` 的 `ui_component_contract`。组件目录和供应商均不设白名单，允许使用任何适合主题的 UI/动效/渲染组件；但至少两个选定组件必须有精确版本/来源、许可证、项目内真实消费者、runtime markers 和当前 iPhone 证据。组件包已安装、依赖已解析、源码出现类名或设计稿可见都不能标为 `Verified`；必须在当前 iPhone 构建操作真实入口并观察结果、错误/空态、生命周期和 Reduce Motion。每个页面的 `background.visual_treatment` 必须体现真实图片/插画、纹理/材质、光影或景深层次；纯色背景、简易线条、扁平几何、色块拼接以及只靠渐变/阴影的画面均判定 `Failed`。

地图能力必须加载真实地图 SDK、真实地图瓦片或许可地理数据，例如 MapKit、Google Maps、Mapbox、HERE，或 `flutter_map` 配合许可瓦片；并逐项操作主题适用的缩放、平移、定位、标记、路线和图层。记录数据源、许可证、隐私权限、瓦片失败/离线回退、当前 iPhone 录屏和日志。出现线条地图、色块地图、静态地图截图、假坐标网格、手绘道路或未授权瓦片时判定 `Failed`，不能以静态图片、地图占位或源码关键字替代。

图表检查真实数据绑定、空态、错误态、动态更新、坐标/单位和可读性；3D 检查真实渲染与交互；媒体、时间线、扫描、语音和其他能力检查实际消费者、权限拒绝降级、前后台恢复与资源释放。每个动态任务必须验收六部分 `formula_record`（风格锚定、动画清单、技术手段、数字参数、包/SDK 版本与许可证、约束/Reduce Motion/回退），并保存动画前、进行中、结束状态证据。非游戏项目与游戏项目共享精致视觉和真实运行证据门槛，非游戏不因没有游戏引擎而降低质量。

### 11.6.1 项目完成后的 iOS 配置报错检查与 ATT 清理（硬门槛）

此检查归入第 20 步，在最终截图及报告前执行，不以开发初期的配置记录代替。限定实际目标工程，核对当前 scheme、target、配置、依赖接入方式与最新构建日志；资料包或技能目录没有 `ios/` 不属于 App 配置报错，也不能据此宣称已验证某个 App。按下表分别记录五项结果：

资源复核还必须逐项执行第 10.6 节：核对照片需求表、实际网站搜索与来源页、许可、文件和当前构建截图，报告独立真实照片数量/计划数量与每个展示位的覆盖。没有实际搜索网站、照片仅在磁盘未显示、使用 AI 拟真图/插画替代、许可不明或覆盖缺失时，相应照片要求不能通过；缺少 API Key 本身不能证明公开网页途径不可用。有限尝试后的真实外部阻断按要求记录并继续独立工作，不把这个回退当成照片质量已完成。

### 11.10 Apple 4.3/5.6 审核风险专项

在生成 AppListing、About 和 Review Remarks 后、最终报告前执行一次完整专项，并将结果写入 `.codex-work/app-review-risk.md`。专项必须检查：

1. 产品身份：Bundle ID、显示名称、App Store Connect 记录、截图、Intro、About、Support 与 Remarks 是否描述同一个真实产品；是否误生成地区/品牌/主题克隆或多个应用记录。
2. 实质差异化：对照 `.codex-work/differentiation-brief.md`，逐项确认目标问题、领域模型、主题专属核心动作、任务顺序、首个有用结果和可回访成果都在当前代码、数据和 iPhone 截图中出现。只换 Logo、配色、图片、字体、文案、卡片尺寸或导航外壳时判定为 `4.3 risk: Failed`。
3. 诚实运行：扫描隐藏审核模式、远程动态换功能、虚假账号/计费/服务/权限、假按钮、假统计、死链接、白屏、崩溃、占位图、数据丢失和核心流程失败；普通用户路径与审核路径必须一致。
4. 评价与发现：扫描自定义评分弹窗、诱导或激励好评、非 Apple 评价接口、搜索/榜单/引荐/安装量操纵和垃圾营销内容。发现任一项即阻止发布结论。
5. 材料事实：Intro、About、Support、Remarks、截图和 App Store 字段只能使用已核实功能、设备、服务、地区、权限和开发者信息；未知信息不得用猜测补齐，`Not verified` 不得写成完成。

核心失败项即使不影响其他本地产物，也必须标记 `Release readiness: Blocked`，并列出证据、影响范围、整改动作和复验结果。只有全部适用项有证据且没有关键失败，才能标记 `Release readiness: Ready for submission`。

### 11.11 项目类型、专用实现与独立样式验收

先核对第 9.5、9.6 节的类型判断和实际代码：只有项目类型为游戏或混合且确实存在真实游戏模块时，才必须完成“专用引擎必要性决策”。游戏仍保留 `lib/welcome.dart`，但运行时必须是一屏式沉浸竖屏大厅，首屏只验证 `Play`、`Load`、`Operation`，顶部只验证 `Exit`、`Settings`；普通多章节 Welcome、`Continue`、额外引导卡片不得混入游戏大厅。验证 `Play → Loading/初始化 → Game`、`Load → Save Slot/存档加载 → Game`，并验证 `Operation` 中音量、画质和按 iPhone 性能档位适配。持续世界、实时物理/碰撞、复杂 3D、编辑器导出管线或高频实体更新等项目选择 `implementation_mode: engine`，并提供精确版本与环境证据；回合制、卡牌、问答、轻量棋盘、有限状态解谜等项目可选择 `implementation_mode: flutter_native`，由 Dart/Flutter 原生承担状态、规则、输入、结果和重开。两条路线都必须存在并通过 `.codex-work/game-engine.json`，字段至少覆盖 `project_type`、`game_lobby`、`implementation_mode`、`engine_required`、`visual_mode`、`visual_contract`、`decision_reason`、运行时入口/场景资源/所有权、动态效果目录与 `evidence`；引擎路线再填写 `engine.name`、`engine.version`、`engine.role`、`engine.integration`、`engine.entrypoint`、`engine.scene_assets`、`engine.runtime_owner`、`engine.native_bridge` 和 `engine.build_commands`。非游戏项目的游戏专项验收标记为 Not applicable，不因缺少游戏引擎或游戏场景判失败。不能只检查 pubspec、编辑器安装、动画包安装或空场景。复用当前同一 App/Bundle ID 和一个现有 iPhone，按所选路线验证 iOS 构建、运行时初始化、本地场景/卡面资源、真实触控、完整玩法结果、暂停/继续/重开及适用的碰撞/音频/存档；Flutter 原生路线必须额外核对实际动画/效果包或工具的消费者、动态效果前/中/后状态和 Reduce Motion 回退。检查 Flutter runtime 与专用引擎（如适用）各自的生命周期，前后台/中断/Scene 重连、退出游戏、清除数据及再次进入无重复更新或失效回调。记录真实命令/精确版本/产物、决策依据、操作结果、当前构建录屏和未覆盖项到已有 dependencies.md、逐页执行文档与 quality.md；其他平台运行、图片演示或源码关键字不能证明 iPhone 游戏通过。

游戏视觉另看角色/物体动作、场景层次、材质纹理、相机/视差如有、主题特效、规则反馈和 HUD 的完成度与协调性：引擎路线场景必须有前/中/后景或等价空间层次、主体素材、材质/光影、相机/遮挡关系、动画/粒子反馈和清晰 HUD 层级；Flutter 原生路线的卡面/棋盘/问答场景也必须有等价的层次、材质、状态变化、动态反馈和清晰 HUD，不能因不接入引擎而降级。实际游玩检查输入命中、状态提示、重试/返回及流程结果；不将物理演示、纯色几何块、缺失素材或通用按钮壳作为最终游戏。环境或运行受阻只记录对应缺口并继续独立任务，不伪称引擎已运行或已完成完整玩法。

游戏质量回归还必须逐项搜索和修复以下运行时阻断项：`setState() called during build`、RenderFlex overflow、dispose 后旧回调（stale callbacks after dispose）、重复引擎注册（仅 `implementation_mode: engine` 适用；duplicate engine registration）、引擎超时（仅引擎路线适用；engine timeout）、输入命中错误（input mismatch）、HUD/弹层遮挡玩法（overlay occlusion）、前后台恢复重复更新（lifecycle resume duplication）以及崩溃、白屏或卡死（crash/white-screen/hang）。Flutter 原生路线不以“无引擎”豁免布局、状态、输入、生命周期或视觉阻断项；每项都要在修复后重新 build、安装并重放同一条垂直切片路径；相同命令连续无新输出时必须停止重复调用并转为诊断，不得用静态日志或截图覆盖失败。

非游戏及混合项目的非游戏模块按第 6.10.2 节逐页检查动态图覆盖：主要适用场景有独立、贴题且有信息价值的本地多帧资源，不仅欢迎页一张或同图重复。逐项验证格式兼容、实际播放与循环/结束、离线、暂停/恢复、静态预览、Reduce Motion、离屏/后台恢复和图文裁切；记录真实路径及当前构建录屏/不同帧，不以首帧或静态 fallback 当通过。不适用页面说明实际职责，保留静态原生页、法律/风险和系统界面的边界；动态图不能代替专属转场和 Flutter 实时背景。

全项目独立样式按第 9.5、5.1、6.13 节对照已有规划和可取得历史，用实际领域模块/状态流、核心工作区、导航/返回、各页区域轮廓、媒介关系、字体/材质和交互节奏证明主题专属设计。只换框架、文件名、颜色、文案或图片均不能证明项目架构与样式不同；不要求随机更换状态管理库。发现整套产品同构、架构不服务核心任务或动态图/游戏质量粗糙时实际调整并复验，不以计划已写入结束。五档性能选项的功能/视觉硬门槛、单一安装复用和最后五张截图契约继续有效。

### 11.11.1 游戏首屏可达性与完整一局验收（硬门槛）
游戏首屏可达性专项：游戏大厅的 Play 经过 Loading、Load 经过 Save Slot 后到主游戏目的地；不得混入普通 Welcome 的 Continue 或多章节引导。完整一局必须覆盖真实输入、成功或失败结果和重开。游戏核心路径任一失败时，`.codex-work/quality.md` 必须写入 `Release readiness: Blocked`；垂直切片必须按 `.codex-work/game-engine.json` 选定路线逐项有证据通过：引擎路线为 `引擎环境 → 场景启动 → 已创作资源加载 → 真实输入 → 更新/物理 → 结果 → 反馈 → 重开`，Flutter 原生路线为 `Flutter 运行时 → 场景启动 → 已创作资源加载 → 真实输入 → 规则更新 → 结果 → 反馈 → 重开`。Flutter 原生路线还必须提交动画/效果包或工具目录和六部分效果提示词记录，证明动态反馈真实存在；未通过不得扩展全量内容或进入最终截图阶段。


用户要求游戏或项目含真实游戏模块时，按当前 iPhone 逐项执行并记录：冷启动进入 `lib/welcome.dart` 游戏大厅；点击 `Play` 后经过 Loading 进入主游戏，点击 `Load` 后经过 Save Slot 进入主游戏；大厅主入口不在 Settings、About、二级菜单、隐藏手势或不可见路由。随后完成至少一局真实操作，覆盖输入、引擎更新、主题规则、成功或失败结果、结果反馈、重开；按玩法需要覆盖暂停/继续、碰撞、音频、存档、前后台恢复和退出再进入。每一步保留当前构建录屏/截图、路由或可访问性证据和实际结果。

验收必须在同一 App/Bundle ID、同一 iPhone 和最终交付构建上完成。空场景、彩色块、静态截图、自动播放、点击穿透、无效 CTA、只在浏览器/独立测试工程可玩的场景都判失败。任一核心路径崩溃、卡死、不能开始、不能完成、不能重开或入口不可达，写入 `.codex-work/quality.md` 的 `Release readiness: Blocked`，修复并重新走完整路径后才能继续最终截图和 Git 交接；不能以“页面已生成”“引擎已安装”或“编译成功”替代玩法证据。游戏入口和闭环检查应与不依赖它的素材、About、权限和文案任务并行推进，但最终结论必须等待全部核心步骤实际通过。

### 11.12 删除工作记录后的工程独立性验收（硬门槛）

在第 13 节第 19 步执行第 9.2.1 节契约；只检查 `.codex-work/` 文件数量、忽略打包目录或启动旧安装都不能证明通过。先修复引用，再按以下顺序实际验证：

1. **检查真实消费者**：扫描源码、资源/数据清单、pubspec 及覆盖配置、测试/CI、代码生成、工具、iOS 工程/配置/Build Phase 和最终 HTML 的实际文件依赖；同时解析本地包路径、`.dart_tool/package_config.json`、插件链接、Pods 和构建输入。核对原始引用、相对基准与规范化/真实目标，检查项目链接和自定义路径别名是否直接或经中间链接落入 `.codex-work/`。工作记录自身、说明文档、`.gitignore` 排除项和用于检查禁止引用的规则不因包含这个名字就判失败；但文档不能被用作掩盖真实读取的理由。
2. **实际文件归位并修复根因**：把正式使用的文件独立复制到源码、assets、正式工具或测试目录，同步 import、声明、数据、URL/主题注册表和原生配置；重新生成受影响的访问器/依赖配置，不只手工修改缓存或增加指向工作目录的回退路径。最终 `aduit/` 文件不得通过链接或图片/脚本引用依赖工作记录；必需交付内容不能只保存在备份里。
3. **可逆移出，不删除**：待本任务当前构建和写入完成，暂停向工作目录写入，确认真实工程路径及目录内容后，将整个 `.codex-work/` 临时移到工程外本任务独有的安全位置；记录原位置与恢复位置，用 `try/finally` 或 shell `trap` 保证成功、失败或中断都恢复，恢复冲突不得覆盖任何文件。不要在工程内改个名字代替移出，也不要以符号链接保留入口；验证期间不重新创建原目录，不读取移出记录作为构建/测试输入，日志先写工程外临时位置。目录本来不存在时直接验证并记录，无需制造工作目录。
4. **在目录缺席时实际构建和运行**：从真实工程根目录重新解析依赖，运行项目适用的静态分析、代码生成（如有）、Pods/原生构建和实际交付配置的构建/打包；核对解析后的本地路径与输入不再指向移出位置。让受影响构建步骤实际执行，不以旧 `.app`、已安装包或缓存命中替代。只处理本任务受影响的产物，不全局清理缓存、不另建测试工程或多个安装包。将本次构建按既有规则更新到同一 iPhone/同一 App，检查冷启动、Welcome、核心任务、全部本地图片/字体/动画和适用功能、Initialization/设置流程，断网验证随包资源；使用无网络 stub 核对三个具体项目名 HTTP URL和 App 内 WebView。单独确认最终 `aduit/` 的文件、图片、三页及独立欢迎 HTML 在工作目录缺席时仍可本地读取/展示，不改动三个协议文件名、不探测公开地址。
5. **恢复与如实记录**：恢复原目录后，把扫描范围、迁移文件/引用、目录实际缺席的证据、真实命令/退出码、构建身份、运行结果及恢复结果写入既有 `quality.md` 与执行记录。只有已执行的适用项都通过才标记 `Work directory independence: Verified`；依赖残留或实测失败为 `Failed`，环境缺失导致未执行的项为 `Blocked`/`Not verified`，不得用静态扫描替代运行结论。继续独立交付，但这条门槛未通过不能宣称工程可在删除后正常使用或完整交付。

第 20 步等后续修正若改变源码、资源、依赖或构建输入，重新核对并复验受影响的独立性项，再完成第 21 步最终截图；平台权限校验和最后截图的既有顺序不变。用户之后自行删除工作目录无需再修改任何项目引用；删除的只是开发记录，正式工程和交付材料必须保留。
