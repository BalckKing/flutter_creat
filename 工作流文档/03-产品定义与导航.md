## 4. 根据主题自动生成的产品定义

根据用户创意确定主题后，智能体自动填写以下内容并纳入待确认的思维导图与方案，整体确认后实施。所有新项目默认制作复杂且内容丰富的完整成品，不以阶段划分、演示交付、工期、工具型定位或“以后再做”为由缩减核心模块、页面、任务或内容量；内容单位、数据模型和核心旅程随创意变化，不机械复用示例产品：

- `Working app name`。
- `One-sentence promise`。
- `Primary user and context`。
- `Core user journey`。
- `Content unit and seed-data strategy`。
- `Core success signal`。
- `Differentiation brief`：明确目标用户和触发时刻、具体问题/现有替代做法、独特结果、标志性动作、首个有用结果、可保存并回访的主题成果，以及至少一条影响内容组织或交互顺序的主题规则。证据不足的用户/竞品结论标为假设或未验证，不编造。
- `Signature action and retained artifact`：用一个来自当前创意的实际操作与结果说明 App 的独特性；成果优先复用核心任务已有的本地数据，不为差异化强加社交、登录、收藏、云同步或独立日志模块。
- `Out-of-scope capabilities`：仅记录与用户主题/既有硬性要求无关的能力及排除理由；不得把复杂度基线、已确认功能或核心工作流列入排除项或推迟到后续版本。
- `Open assumptions and their consequences`。

### 4.1 核心旅程

以下流程是通用骨架，不是固定产品方案。核心动作、内容单位、详情页和工具应按用户创意设计为完整而丰富的产品，不得裁剪成单一简化任务；与创意无关的浏览、搜索、阅读、播放等能力不加入实现。

产品必须先定义自己的核心循环，再把它映射到页面和导航：主题任务入口 → 标志性动作 → 清楚可见的有用结果 → 保存/更新一个有意义的成果或延续状态 → 需要时回访并继续任务。不得设置首个结果的时间上限，不得为追求快速演示而减少真实步骤、内容深度或成果能力；应让用户较早看见有价值的进展，同时保留完整探索与进阶路径。核心成果应来自该主题及既有隐私/数据边界，不默认增加社交、账号、云端上传或通用收藏/历史功能；这些边界不构成降低产品规模的理由。

```text
Launch
  -> Show the static native iOS Launch Screen during system cold start
  -> Show the Welcome page on every app launch; render required preparation status inside this same page
  -> When required preparation is ready, tap Continue and open the selected primary task destination directly
  -> Start the theme-specific core task (do not assume browsing/searching is the main activity)
  -> Perform the signature action and show its first useful, observable result
  -> Save/update the named theme-specific artifact or carry-forward state
  -> Reopen or continue from that result when it serves the user's task
  -> Use detail, search, filter, calculation, reading, or playback only when the chosen task needs it
  -> Adjust a theme-related preference if useful and show observable feedback
  -> Tap the project-selected Clear Data or Exit App in Settings and review its truthful confirmation
  -> Cancel and keep using the current page without changing data
     OR confirm the selected action: clear actual user data in clear mode; end current activities without deletion in exit mode
  -> On verified success, clear the navigation stack and show Initialization, Entry; reset preferences only in clear mode
  -> Tap Entry to open the selected primary task destination
  -> On failure, show the remaining work and offer a recoverable retry
```

每个转移都必须产生 UI 反馈。只有数据层变化、页面没有可见状态变化，不算完成。

术语与页面边界固定如下，整个 App 恰好有三个不同的启动/返回页面：

1. **iOS 原生启动页**：系统冷启动期间显示的静态原生画面；随后交给 Flutter，不承担交互、进度或清除后返回。
2. **欢迎页（Welcome，`/welcome`）**：每次启动 App 后必定进入的 Flutter 页面，包含 `Continue`。启动所需准备、当前步骤、百分比、进度条及失败后的 `Try again` 与所选 `Clear Data` / `Exit App` 都是此页面内部状态，不创建独立 Flutter Loading 页面或 `/loading` 路由。准备就绪后 `Continue` 可进入主流程。
3. **初始化页（Initialization，`/entry`）**：只在所选 `Clear Data` / `Exit App` 确认且真实成功后显示的 Flutter 页面，包含 `Entry`；点击 `Entry` 进入主流程。此页是结束操作后的返回目标，不是欢迎页，也不作为正常启动入口。它底部显示通用协议文案；欢迎页不显示该协议文案。

冷启动路径固定为“iOS 原生启动页 → 欢迎页”。结束操作成功路径固定为“初始化页”；不得将任意两页合并、互换或另造第四个启动页面。结束操作返回初始化页不重放原生启动页；下次启动仍先显示欢迎页。详见第 7 节。

最终介绍复用本节的产品定义与任务链作为核对索引，并以实际实现为准：按第 12.1 节说明每个主要模块处理的内容、具体动作、用户结果、实际媒体用途（如有）和成果回访方式，而非只列功能名。全部描述写入现有 `aduit/intro.md` 的 `## Description`；不把计划写成已实现能力；按第 12.1 节清除重复 URL 栏目及多余网址，仅在 `All URL` 保留四个完整原始地址，四值原文不变；Intro/Remarks 的教育类展示标签按第 12.1 节统一为 `Popular Science`（科普），其他类别与事实不变。

### 4.2 内容丰富度与真实使用深度

- 产品方案必须按第 4.3 节填写产品规模与深度表，用同一份记录覆盖用户任务、主页面模块、内容数量、细节深度、交互结果及验收方式，不再另建重复的内容与功能覆盖表。拍摄、导入、录音仅在实际选用时接入有意义的主题流程，例如记录观察、补充素材或添加语音说明；这些只是可选设计方法，不固定主题，也不要求三项出现。
- 每项核心页面和主要目的地都必须映射到差异化 brief 或清楚标为支持职责：说明它服务哪个主题任务、为何需要此页面/目的地、承载什么真实结果。至少一个主要任务需呈现主题专属的数据/内容模型或交互规则；把通用界面换成 Logo、渐变、卡片、Emoji 或插画，不算产品差异。
- 标志性动作应是对当前创意最自然的操作，能尽早给用户一个明确结果；具名成果应可在本地保存并再次打开/继续。相机、相册和麦克风可自由选择任意组合或全部不选。仅已选路径需要连接实际主题成果，说明各自信息价值，不增加无关入口或通用媒体仓库。
- 竞品或市场比较只陈述有来源的事实；没有核验材料时，记录为“未验证”，以产品内可见的任务流程与数据结构评估差异，不把竞品调研设置为继续开发的前提。
- 核心任务的数量、完整路径与成果深度按第 4.3 节结合主题制定并确认；不同流程必须产生有区分的用户结果，覆盖入口、操作、结果、合理的再次查看和错误/取消处理。媒体能力不决定任务数量；已选媒体可共同服务一个核心流程或分布在不同流程，不用重复页面凑数。
- 内容、工具和混合产品一律达到第 4.3 节复杂成品的规模下限。内容浏览型可用分类与条目承载；工具型须以主题相关的案例库、情境集、操作路径、参数组合和结果解释达到等量深度；混合型覆盖两者。产品类型只决定呈现模型，不得降低模块、页面、有效条目、任务、详情或表达形式的最低数量；也不得为凑数加入无关列表。
- 主内容页应有清晰的主任务、多个有区分的内容/工具模块和可继续探索的二级层次；拍摄、录音等聚焦操作页以操作清晰为先，不强行堆卡片。搜索、筛选、排序、说明、详情和本地媒体管理按任务需要组织，所有可见动作必须有真实结果。
- 全页面图文覆盖按第 6.10 节执行：为每个 App 可控制页面及适用状态规划实际信息模块和有意义的非纯文字表达，不能只给首页加图、让详情/搜索/Settings/工具/空态仍是文字堆叠。摄影、图解、真实媒体预览、状态插画与分组控件随页面职责选择；详情有至少三个不同信息价值的模块，重要详情进一步按第 4.3 节确定更深入的结构，不能把通用底线当作完整目标。聚焦操作与确认框保持简洁且完整，不能用无关功能、重复段落或虚构数据凑丰富度。规划项纳入第 3.2 节追踪表并逐页验收。
- 页面清单按唯一 `page_id` 分类，逐项写明页面类别/路由、独立 Dart 页面文件、第 6.11 节背景模式与独立构图、图层位置及验收方式。图片/混合模式登记真实 `assets/backgrounds/<page_id>/<page_id>_background.png` 或实际格式，程序/动画模式登记 scene_id、代码入口/实现及使用的本地动画资源；工具、生成服务和第三方组件合成不限，不为无图片场景补占位文件。各独立页面须有专属页面实现和可区分的背景，不能把页面都堆进一个 Dart 文件，也不能用同一图或同一场景换色冒充差异。
- 对每个主要内容浏览页规划有语义依据的卡片尺寸层级，例如重点精选项使用较大的图文卡片、普通条目使用标准卡片、辅助或快速浏览项使用紧凑行；每个主要内容列表至少呈现两种清楚可见的尺寸，不同主要页面合计覆盖三种层级（内容规模允许时）。多个主要页面都是内容列表时，必须在跨主要页面方案中安排至少两种有意区分的主编排，例如垂直分组列表、双列网格、精选大卡加横向滚动、瀑布流/不规则卡片或分段式复合布局；每个独立页面的整体骨架必须按第 6.13 节区别，不能以仅有两种编排为完成目标；`ListView` 等基础组件可以复用，但不能复用整页构图与区域关系。单个页面可以复合使用多种编排，并允许卡片长短不齐、大小不一、图片比例不同；`featured` / `standard` / `compact` 等尺寸角色必须由内容重要性、任务优先级、信息密度、媒体比例或排序依据决定，并记录原因、顺序、尺寸约束和响应式降级。禁止随机错落、只为装饰改变尺寸、固定高度截断文字、拉伸图片或让不规则布局破坏 VoiceOver/Dynamic Type；Settings、协议、权限和纯选择/比较等扫描型列表继续使用整齐易扫读的统一行样式。
- 复合页面须写明各区域层级、排列顺序和共享/独立滚动边界；小屏或大字号时可降级为单列或更紧凑的流式布局，但保留至少两级内容层次和原有任务/阅读顺序，不将卡片随机重新排序。
- 首次使用即有可浏览的原创或许可明确的示例；若包含用户私有媒体功能，则从空状态起步并引导实际创建；示例媒体清楚标识，不能冒充用户拍摄或录制内容。未选媒体能力时不建私有媒体空库。
- 不得因需要精修 UI 就削减已确认的内容与选定功能，也不得为了填满屏幕重复卡片、插入无关功能或改变用户创意。实际内容覆盖与质量未达标时继续完善，并如实记录未完成项。

### 4.3 产品规模与深度表（硬门槛）

游戏及混合项目同样保留本节复杂成品下限，但按真实玩法映射：模块可对应规则、场景、关卡编排、成长/成果与回访等实际职责；分类/场景记录可对应经核验的关卡、地图、挑战或规则情境，继续探索可采用关卡/章节选择与进度推进。每项必须有实际不同的规则、布局、目标或决策价值；随机种子、微调参数、换皮关卡与重复地图不充数，不为满足数量添加无关文章列表。引擎的早期小闭环只是第 9.6 节集成检查，不能作为完成获批全部玩法与内容的替代。

在展示思维导图并请求第 3.4 节唯一一次整体确认前，先从当前创意建立领域结构，再填写产品规模与深度表。表中是所有新项目的硬性下限，不是可选参考或只针对内容型产品的建议；项目成品必须完整实现获批的复杂规模，不得以阶段划分、工具/聚焦型定位、时间、依赖或后续版本为由缩小。可按主题把分类与条目映射为可核验的场景、案例、任务输入/结果和领域记录，但必须达到同等的有效信息量与任务深度，不得通过改名、拆段或重复模板计数。不得为凑量加入无关功能；本表只约束功能与内容深度，不规定 Tab 或顶层导航入口数量。多个模块、功能页面、分类和层级可以通过同一个主工作区与层级路由访问，不能将其数量一比一转换成 Tab 配额；信息形式必须提供实际理解或操作价值。

| 维度 | 所有新项目的最低交付要求 | 必须说明的深度依据 |
| --- | --- | --- |
| 独立功能页面 | 至少 8 个真实可达且任务/信息结构不同的 App 功能页面；不计原生启动、Welcome、Initialization、单纯确认弹窗、重复数据实例或协议容器 | 每页有独立目的、有效内容/操作及不同骨架；不得拆同一页面状态凑数，也不得全部合并到一个工作区规避页面下限 |

| 内容/任务层级 | 至少 3 层有不同目的的层级 | 各层帮助定位、理解、比较/操作和回访，能从概览进入主题细节、再进入应用/结果；不以重复跳转伪造层级 |
| 分类与场景族 | 至少 8 个有实质差异的主题分类、情境族或领域分支；没有固定上限 | 按领域覆盖与重要性分配，写明各类责任、条目数、相互关系和事实核对依据；不能只改标题 |

| 完整任务 | 至少 8 条产生不同用户结果的端到端任务；没有固定上限 | 每条列出入口、动作、结果、跨模块承接、适用的保存/回访/修改/删除和异常恢复；取消/重试或只换对象不能另算任务 |
| 信息与交互形式 | 至少 5 种适合主题且提供实际价值的表达或操作形式；没有固定上限 | 如图文观察、关系图、时间线、步骤、对比、参数面板、图解、交互画布；说明其如何帮助理解或行动，并在产品中实际使用 |

表中数量是硬下限，超过后仍可按主题价值扩展；不接受低于下限的“替代深度”或不适用理由。只有某种传统内容格式不合主题时，才可映射为等量的主题场景/案例/记录，并保持条目可核验、可达、互不重复。不得通过大量空数据、虚构事实、自动变体、重复流程或近似页面满足门槛。所有核心能力和获批规模必须在完整成品中实际实现并验证；不能把未完成项留作后续计划后宣称成品已完成。主题明确后，在既有规划/追踪记录中维护下表，可按模块或分类展开多行，不新增审批或公开交付文件：

| 深度 ID / 关联需求 | 维度及领域依据 | 计划目标与分类分配 | 页面/路由/模型/资源 ID | 完整任务、用户成果与状态覆盖 | 实际实现 / 实际验证 | 证据、缺口与状态 |

| `D-01 / R-01` | `[theme entities, relationships and coverage rationale]` | `[specific target and counting rule]` | `[screen, model, content and resource IDs]` | `[entry, actions, result, continuation and applicable states]` | `[planned before approval; actual counts after implementation]` | `[test/source/runtime evidence and unresolved gaps]` |

1. **先定义领域，再填内容**：列出核心对象、字段、单位、对象关系、分类边界、内容来源/核对方法及主题专属规则。建立“分类/情境 × 内容/任务”的覆盖矩阵，记录各类条目数、重要详情结构、媒介需求、关联对象和实际展示位置；矩阵可直接展开在上表中，避免重复记录。关系必须指向真实存在且可达的对象；80 条下限中的每一项都需有独立信息价值，不能用通用段落、虚构参数或未经核实的知识凑量。
2. **增加可用动作与连续旅程**：依据主题选择比较、筛选、排序、计算、规划、标注、观察记录、实验或结果解释等有用动作，不全部强加。模块间通过当前对象、已选条件、计划或结果形成有意义的连接，携带相关数据、支持返回和继续；不能只有互不关联的入口与静态介绍。具体结果优先复用已有本地成果，不为每个模块强建一个记录库。
3. **用视觉解释内容**：详情、过程和结果应使用适合的图解、实例、对照、步骤或交互反馈减少文字堆叠。第 6 节的自由配色与可选渐变规则，以及字体、图标、Emoji、粒子、页面背景与图文硬门槛照常实施；装饰丰富不能代替信息深度，数量增加也不能削减既有 UI 效果。Welcome 继续保持单屏不可纵向滚动，用 3–5 张精炼卡片概括实际价值；完整内容通过主流程访问，不把全部条目塞到 Welcome。
4. **完善可执行状态**：对每条任务列出适用的输入校验、执行中、成功结果与解释、修改/重置、保存/重开/编辑/删除、空、失败、取消、重试及恢复路径。只实现该任务确有意义的状态；无持久化需求的计算等流程可以通过输入/结果延续完成，不强增保存功能；已有需保存的主题成果必须验证真实持久化与再次访问。
5. **确认后兑现目标**：上表随完整思维导图在同一轮整体确认中展示，获批的具体目标成为验收契约；确认后的补细节与用户主动修改按原授权处理，不新增确认关卡。不得静默降低数量、详情深度、任务闭环或交互覆盖；不能完成时修复并如实保留差额/阻断，继续其他独立交付，不把缩水或占位标为完成。
6. **以实际质量计数**：批量生成但未经核对、仅换名/改措辞、同图换名、重复对象、空壳或未接入可达页面的内容不计入交付数量；同一实体跨分类展示只计一条实体，分类映射另计。逐项核对全量数据字段/关系/资源映射与事实质量，按分类和详情/任务类型选有代表性的当前 iPhone 运行场景，所有核心任务均须执行；统计实现数量与已验证覆盖，不把抽样展示声称为每条已实测。质量结论记录到已有 `.codex-work/quality.md`，按第 11.1、11.9 节验收并由第 14 节报告计划与实际差额；目录文件数、代码行数、截图数和耗时均不能替代产品深度。

### 4.4 大量有效内容与连续翻页（硬门槛）

用户应能持续翻阅实质不同的内容，不能只有首屏几张卡片。所有项目均须按第 4.3 节达到至少 8 个主题分类/情境族和不少于 80 个有效条目、案例或领域场景记录，并把丰富内容纳入完整成品；工具型、聚焦型或非文章类主题没有减量豁免。可将条目呈现为案例、模拟情境、输入组合与有意义结果，但每项必须对应真实、可解释的领域用途；不把所有产品强做成文章库。不得用长段落、重复标题、同图换名、参数微调或不同措辞的相同事实替代内容量，既有去重、真实素材与事实核验要求继续生效。

- 每个主要内容、案例或场景集合都须有可发现、可操作的继续翻页方式，例如页码/上一页下一页、分章切换、横向翻页或分批加载。连续集合采用分批加载时提供清楚的继续入口及进展/终点，不让用户只能猜测手势；不能只有装饰分页点或第一页数据。完整内容/案例全集至少形成三批有意义且非空的内容，每批数量按领域和编排确定，分类子集按真实数量分页，不机械拆成一条一页凑三页。工具型也须通过完整案例/任务场景序列达到第 4.3 节条目下限，并提供继续探索入口；不得以“工具没有内容库”为由免除数量与翻页要求。
- 对同一查询、筛选和排序快照，使用稳定唯一 ID、明确排序和无重叠的页边界。一次完整前向遍历中，条目 ID 与实质信息不重复、不遗漏、不循环回填；主题事实可以相关但每条必须提供新的信息价值。返回上一页或用户主动再次打开同一条属于正常回访，不当作去重失败。详情中的相关内容排除当前项及已展示的重复推荐。
- 明确展示实际的当前页/章节或已显示数量、下一批入口和末页状态；这些数字来自真实数据。翻页、返回详情、切换分类与搜索/筛选后保持或按规则重置位置，避免重复追加；重复点击、快速切换、取消、空结果和加载失败均有可恢复行为，不跳页、不丢失有效结果。全部图片随包本地可读，不引入联网图片分页依赖。
- 数据验收全量核对分类数量、唯一 ID、关键字段、语义近似条目、资源映射及分页边界；在当前 iPhone 实际走完每个主要集合的首批、中间与末批、前后翻页、详情返回及筛选后翻页，核对总数、页间交集为空及终点不重复。实际语义与图片逐项复核，不能只靠标题/哈希去重；抽样操作范围明确记录在已有 quality.md，不冒称所有条目逐个运行。
- Welcome 的 3–5 张介绍卡片仍是精炼的产品介绍与自动切换，不计入主内容规模，也不替代主内容翻页；欢迎页不可纵向滚动、Initialization 的结束操作成功职责、Settings 和聚焦操作页的清晰性不变。每个 App 功能页面仍须服务自己的场景并通过内容、图解、关系或结果提供足够信息深度；不得把聚焦操作页简化成只有一个按钮的空壳，也不得为给辅助页面凑条目加无关列表。

## 5. 动态信息架构与导航

### 5.1 按主题选择导航模式与 UI 风格

全项目按第 9.5 节同步定制领域架构、任务工作区和视觉样式，不能只改变导航外形；游戏/混合模块按第 9.6 节确定引擎场景、HUD 与 Flutter 页面边界，非游戏按第 6.10.2 节设计动态图叙事。均纳入既有一次整体方案确认及第 11.11 节实际验收。

UI 具体风格与构图由智能体按第 6.1 节自主创作，不从预设外观菜单中机械选型；选定结构后继续用真实素材、排版、配色与交互细节精修成完整成品。方案比较用于选择适合任务的结构，最终美观程度以当前 iPhone 实际页面与动效复核为依据。

Tab 完全可选，没有最低数量，也不要求多个 Tab、顶部标签或底部导航栏；允许零 Tab、单一主工作区配层级路由、目录、菜单或按需面板。只有当前主题和真实任务确实需要时才采用 Tab，数量按实际需求决定，不预设配额。根据内容结构、访问频率、任务连续性和 iPhone 操作方式选择整体 UI 与导航；用户已明确指定的导航/风格优先，缺失部分由智能体自主设计。

用户未明确指定导航时，在内部比较至少两种结构上不同、对当前任务可行的导航方案，再选定最合适的一种，随既有思维导图展示选择依据与关键路径，不让用户额外选择导航菜单、不新增审批。比较应涉及如何进入主要任务、切换目的地及返回，不只比较底栏外观。至少包含一个无固定底部导航栏的可行方案；若确实不适用，说明具体任务原因。底部导航可以被选用，但须有多个高频、平级目的地及切换需求的具体依据，不能以“移动 App 通常如此”作为理由，也不为追求差异随机选择难用的结构。

可采用任何适合主题的视觉表达与组合，以下仅为参考，不是固定菜单或主题到样式的一对一模板：

| 核心组织需求 | 可考虑的导航与界面组织 |
| --- | --- |
| 围绕一个主要任务创建/处理成果 | 单一工作台、画布或工具界面，配上下文工具栏与按需 Sheet |
| 按章节或专题理解内容 | 可浏览的目录、顶部栏目、分段切换、杂志式编排与层级返回 |
| 按先后步骤完成实际任务 | 步骤式流程、阶段路径、可返回的任务面板，不强加全局 Tab |
| 从主题对象或空间关系开始 | 对象总览、关系图、地图或展陈式入口，选中对象后进入详情/操作；仅在主题真实需要时采用 |
| 多个需要频繁切换的平级任务 | 有明确文字标签的顶部/底部导航、紧凑悬浮 Dock 或混合导航，依实际触达与可用性选择 |
| 多个低频辅助目的地 | 清晰的菜单、目录入口或按需面板，与主任务层级区分，不把所有入口堆进持久底栏 |

导航形式、首屏构图、内容组织、排版、图片比例、材质/边框、控件与动效共同形成贴合主题的视觉语言，可以采用编辑式、展陈式、仪表/工具式、手工/艺术式等有依据的组合；不固定为“渐变卡片墙”，也不把底栏换成悬浮胶囊就当作产品结构创新。自由选定主题色彩、按创意选用的渐变、圆角、真实本地图片和内容丰富度仍按当前要求落实，但不据此强制同一布局；第 6.9 节的列表尺寸规则仅用于实际存在的内容列表，不为满足它凭空增加浏览页或卡片列表。

- 每个主要目的地承担明确的主题任务，命名、入口位置、首屏与返回路径可理解；可以只有一个顶层主工作区，但其内部仍须实现第 4.3 节要求的至少 8 个独立功能页面。不得以单一工作区、单页工具或不使用 Tab 为由合并、隐藏或削减功能页面；也不得为凑 Tab 添加空壳页面。
- Settings、协议及实际选定的媒体功能保持完整与可达性，可以通过标题栏、上下文操作、目录或按需面板进入，不强制独立 Tab；不新增账户/个人资料功能。
- Welcome 的 `Continue` 与所选结束操作成功后 Initialization 的 `Entry` 都进入选定的主任务入口；其目标可以是工作台、目录、画布或选定目的地，无需先进入 Tab 容器。三种启动/返回页面和协议文案边界不变。
- 自定义导航提供明确可点击的文字/图标与选中状态；不只依赖手势、装饰或不可见热点。验证 iPhone 单手触达、至少 44×44pt 操作区域、SafeArea、Dynamic Type、VoiceOver 顺序、减少动态与 Light/Dark。
- 每个目的地记录入口、路由、返回栈、选中/恢复规则及适用的滚动、查询/筛选、任务草稿状态；Sheet 关闭、详情返回、清除数据和系统返回不能丢失有效状态或重建重复页面。按实际功能维护状态，不为无 Tab 的项目添加无用 selectedTab 状态。
- 信息架构和导航壳层由主题方案装配；只有选用 Tab 时才使用 `BottomNavigationBar`、`NavigationBar`、`CupertinoTabScaffold` 等相应组件，不在通用根 App 中预装。仅制作 iPhone 布局，允许适合 iPhone 的菜单/抽屉与窄屏面板，不引入其他设备的侧栏/分栏版本。
- 在 `.codex-work/navigation-design.md` 记录方案比较、选定模式、主题依据、视觉构图、入口/返回映射与实际截图/交互证据；最终核对成品是否真正落实所选结构，不能只改方案文字或隐藏底栏但保留空白占位。

### 5.2 中央路由注册表

路由根据用户创意、选定导航模式和实际目的地生成，并纳入思维导图整体确认；用户已明确给出的导航要求优先，不再单独要求用户选择或确认 Tab。确认后建立路由注册表。以下仅为路由示例，与创意无关的路由不创建；`/tab/<tab-id>` 仅在实际选用 Tab 时适用，不要求所有项目使用 Tab 命名或容器：

```text
/welcome
/entry
/workspace
/destination/<destination-id>
/detail/<content-id>
/player/<content-id>
/capture/camera
/import/photos
/record/audio
/media/<local-media-id>
/search
/filter
/settings
/about
/support
/policy/privacy
/policy/terms
/policy/disclaimer
/policy/content-copyright
/webview/<document-id>
```

统一注册页面路由 ID、参数解析、访问边界、返回规则及第 6.14.1 节逐目标页的 `transition_id` 与进入/退出编排，以及会影响 App 导航/生命周期的 Dialog、Sheet 和 Tab 动作；`rt.dart` 为默认注册入口，已有项目可复用符合第 9.3.1 节命名的等价路由模块。`/welcome` 是每次启动入口，承载启动准备状态及 `Continue`；`/entry` 专指结束操作成功后出现、带 `Entry` 动作和底部协议文案的初始化页。二者不得复用同一页面实例或改名互换。页面通过统一导航接口发出动作，不重复拼接路径或自行重建 Continue、所选结束操作确认和成功后到 `/entry` 的规则。局部、无导航副作用的提示可由共享组件承载，不强迫所有 UI 代码堆到一个文件。`/about`、`/support`、`/policy/*` 和 `/webview/<document-id>` 均由同一个 `policy_webview_page` 加载注册文档；未知 ID、失效参数和不存在的内容必须有安全的错误/返回路径，不能解释成任意 URL 或本机文件路径。

最终 AppListing 改名为 `aduit/` 后、Review Remarks 前，按第 12.1 节保留四个站点页，将按第 6.13 节选定的独有欢迎构图实现为 `lib/welcome.dart` 的 `WelcomePage`，实际 `/welcome` 使用 Flutter Widget、本地 assets 和 Dart Continue callback，防重复导航。原 HTML 保留为独立 `aduit/welcome.html`、不使用或打包；它仍自包含 Base64 图片，其他原 HTML 约束不变。两者均无协议页脚。完成验收并记录后，将 `All URL` 四值逐字保存到固定注册表；仅 `/entry` 底部显示 Terms/Privacy，Settings 仅 Privacy Policy/Terms of Use/Support 三个入口。入口仅接受固定文档 ID，协议仍用原 WebView，不能规范化/补全/替换/探测或跳过异常 URL。无网络 stub 验证映射/失败/返回，实际用户点击才请求目标；失败给可读错误与有限重试，主流程继续。

### 5.3 返回行为

- 从详情或播放器返回时，保留来源目的地及其导航/任务状态、搜索词、筛选、排序、视图模式和滚动位置。
- 从 Support 或协议内容返回时，保留 Settings 滚动位置和主题状态。
- 从协议 WebView 返回时，保留来源页面、主题状态和滚动位置；协议查看不改变 App 访问状态。
- 从 Welcome 点击 `Continue` 后（仅改名前开发预览可用 `Enter`），以及结束操作成功后从 Initialization 点击 `Entry`，均通过各自原有进入逻辑打开选定主任务目的地；防止重复点击堆叠路由，不强制创建 Tab 容器。
- 从 Settings 或 Welcome 错误态点击项目选定的 `Clear Data` / `Exit App`，只打开第 7.7 节同一确认框；取消保留实际来源页面、主题和所有数据。确认后按模式执行，真实成功才清空返回栈并到 Initialization/Entry；clear 按第 8.5 节清理并恢复默认偏好，exit 只结束当前会话并保留偏好/随包内容。执行中或失败不得提前进主流程，重试不重复导航，也不强制关闭 iOS App。
- 页面销毁时取消异步任务，或忽略其过期结果。
