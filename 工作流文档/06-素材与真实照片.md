## 10. 素材、许可和凭据规则

### 10.1 资源清单

类型专用素材同时纳入本清单与逐页执行文档：非游戏按第 6.10.2 节安排独立、贴题的本地多帧动态图及静态预览，存入 `assets/media/anim/<page_id>/`；游戏按第 9.6 节为所选引擎准备角色帧序列、场景/地图、纹理及实际需要的音频等资源，按用途和短名分类。核对来源许可、格式/解码或引擎导入、资源声明、实际消费者和当前 iPhone 播放/玩法证据；不能拿静态首帧或文件存在当验收。既有第三方真实照片、本地离线、去重与下载隔离规则保留，不扩大 Stargate 的 Logo/页面背景装饰用途。

维护 `assets/media/resource_manifest.json`。每个随包资源记录：

`provider`、`providerAssetId`、`mediaType`、`localAssetPath`、`sourcePageUrl`、`mediaUrl`、`creator`、`attribution`、`license`、`licenseUrl`、`query`、`retrievedAt`、`sha256`、`dimensions`、`duration`、`reviewStatus` 和 `consumerScreens`。公开或随包 URL 不含密钥、临时签名或私有访问令牌；下载地址无法安全持久化时留空并说明原因，保留非敏感来源页与资源 ID，不能用虚构 URL 补字段。

使用 `provider + providerAssetId + sha256` 去重。文件路径、MIME、扩展名和清单值必须一致。

在最终资源整理后，将同一资源的文件哈希、字节数、图片体积上限、解码/视觉检查、实际消费者、展示位置和许可证摘要汇总到 `.codex-work/quality-matrix.json`，运行 `python3 <skill-root>/scripts/validate_quality_records.py --project-root <target-project-root>`。资源存在或清单完整不能替代当前构建中的真实展示证据；缺少工程、证据或密钥扫描结果时保留 `Not verified`。

第 6.10.1 节用于缓解文字拥挤的图片/GIF 同样进入本清单。静态内容图按实际题材存入 `assets/media/img/<page_id>/`，GIF 存入 `assets/media/anim/<page_id>/`，使用准确简写的主题/用途名；静态预览使用对应短名并由 `posterAssetId` 关联，沿用现有等价分类时保持全项目一致并同步所有引用。文件须随项目打包，不引用 Downloads、临时文件或网络地址。GIF 另记录真实帧数、时长、循环方式、预览和原图/原片派生关系；格式不决定来源类别，真实拍摄与插画分别准确标记。可从既定第三方来源取得许可明确的素材，或用有权使用的图解/原片制作过程演示；不新增 Stargate 的用途，不把 AI 动图冒充真实摄影。不同独立内容位继续遵守不重复用同一素材的规则。

另记录 `sourceIdentity`、`derivedFrom`、`visualDuplicateGroup`、`posterAssetId`、`consumerPlacements` 与 `reuseReason`，用于追踪原始内容、裁切/转码派生版本、近似重复组、视频封面及每次实际展示位置；视频片段同时记录原片 ID 与时间范围。没有适用值时明确标记原因，不能编造供应商 ID、许可或检测结果。用户私有拍摄/导入/录音仍只进入独立的私有媒体索引，不进入此随包资源清单。

另记录 `contentKind`（`photograph`、`video`、`illustration`、`icon` 等）、`captureOrigin`（`real_capture`、`generated` 或 `unverified`）、`subject`、`requirementIds` 与 `searchEvidenceId`。真实照片分类须有来源信息与实际查看依据，不能将网站收录的 AI 图、插画或来源不明图片自动归为真实摄影。来源页没有供应商 ID 时使用可追溯的来源标识并说明，不能为了填字段捏造 ID。照片需求与最终文件、页面消费位置必须能相互追溯。

按第 6.10 节从全部页面的图文计划反推资源需求，覆盖详情、搜索、工具、Settings、媒体流程与状态，不只为首页找图；资源关联第 3.2 节页面 ID 和展示位置。明确区分真实摄影、解释性图解、语义图标、状态插画、按第 6.11 节自由制作的图片/程序/动画/混合背景与用户私有媒体；图解与实际正文/数据一致，无适用照片的控件或状态可使用代码绘制图形，不为每个确认框下载无关图片。逐页核对文件已经被真实组件消费、显示清晰且无无理由重复；资源落盘或清单存在不能替代页面证据。Logo 生图来源不要求统一，按第 2.5 节质量契约自由选择；页面背景装饰需要生图时可用 Stargate 或合规原创/许可素材，复杂场景可直接动画生成或第三方组件合成，工具与服务不限且不强制为动画另行生成图片，但每页半透明主题图片点缀必须实际取得并接入。程序场景在页面清单登记代码/入口，半透明图片另以 background.asset、opacity、placement 登记，不编造资源记录；实际动画成品及所用资源按用途本地分类并登记。真实照片仍须经第三方许可核验；有限失败回退、站点白名单和引导 HTML 图片内嵌/体积限制保持不变。

**素材稀缺时的风格匹配生图回退**：当已拉取、许可核验并适合当前展示位的图片资源不足时，可以使用实际可用的生图软件、模型或网站补充插画、页面背景、装饰图或状态图。启用回退前，先从已拉取素材建立 `style_reference` 记录，至少包含主体处理、构图/留白、画幅与裁切、明暗和光源方向、色彩关系、材质/笔触、颗粒或清晰度、透明度和视觉密度；生图提示词、参考图和输出验收必须明确引用这组特征。补充图应与已拉取素材形成同一视觉语言，逐张并排比较后才可接入；只相似于主题、不相似于已拉取素材风格的结果淘汰。资源清单将其标记为 `captureOrigin: generated`，记录工具、模型、提示词、参考素材哈希、派生关系、许可/使用条件和实际消费者；不得把生成图标作 `photograph`，不得用它替代第 10.6 节要求的许可真实摄影、实景封面或用户媒体。生成来源可以不同，不要求统一网站，但质量、主体、材质、光影、画幅和明亮视觉方向必须与参考素材一致。

#### 10.1.1 素材来源记录与公开展示分离

图片、视频及其封面默认不在 App 页面或生成站点中列举图库、作者、下载地址、来源链接和素材许可。Detail、Player、Settings、About/Support、欢迎引导页及现有法律页均不自动增加 `Image Sources`、`Video Sources`、`Media Credits` 等来源列表、徽标、脚注或额外入口；已有不必要展示须连同对应导航引用一并移除，不影响媒体实际加载与播放。

- **许可无公开署名要求**：仅保留内部核验记录，不展示自愿性来源声明。选材时优先选择实际许可及下载/API 条款允许相应用途且无需公开署名的素材，不凭网站名称认定免署名。
- **许可明确要求公开声明**：只保留满足该项条款的最小必要作者、来源、许可链接及修改说明，并遵守其位置要求；若不适合产品展示，自主更换为主题相符、许可允许且无需公开署名的资源。替换并解除旧素材全部引用后再移除其声明，不能继续使用素材却隐藏必需署名。无法取得可用替代时保留必要声明并记录限制，不伪称已免除义务。
- **内部证据照常保留**：第 10.1、10.5、10.6 节要求的来源、许可、下载与派生关系仍在资源清单及 `.codex-work/` 留存，用于授权、去重与质量核验；模型中的 `source`、`license`、`attribution` 字段不自动绑定为 UI 文案。清单随包存在不等于需要创建公开来源页，也不因此把素材审核证据批量写入 HTML、Review Remarks 或用户可见内容。

该规则仅取消不必要的图片/视频来源展示，不删除第三方软件依法须保留的许可通知，不删改隐私政策中的真实数据处理或外部服务披露，不把图库来源声明与知识内容本身必要的事实引用混为一谈。AppListing/About 生成后及最终验收时均按此规则复查，不增加站点白名单外文件。

#### 10.1.2 assets 资源短名与来源文件名清理

全项目自有文件和文件夹同时执行第 9.3.1 节短名硬门槛，本节补充素材来源命名清理；重命名必须同步全部引用并完成加载复验，不能只移动或改名文件。

项目自有 `assets/` 内的图片、视频、音频、插画、封面、背景及字体等资源，导入时即按主题和用途命名；目录名同样不沿用下载来源的长名。采用小写英文 `lower_snake_case`，通常为 `<主体短名>_<用途>[_序号].<真实扩展名>`；同类资源放在既定分类目录中，扩展名必须与真实格式一致。

- **去掉下载附带信息**：不保留网站/图库/供应商名及其缩写、作者账号、下载或导出日期/时间戳、供应商资源 ID、URL 片段、随机下载串及 `download` 等自动附加词。不能仅把 `pexels` 改为 `pxl` 而继续编码来源；实际主题需要的年份、型号、规格不属于下载时间，不机械删掉所有数字。不同资源重名时使用语义区分词或稳定的两位序号，不用时间戳解决碰撞，不覆盖已有不同素材，也不因短名而改变原有去重依据。
- **专有名词统一简写**：资源路径中的地名、建筑名、机构名和主题专名优先用公认缩写；没有公认缩写时确定一个简短、可辨认的英文缩写，并在当前工程保持同一含义同一写法。相同缩写对应不同主体时补充简短区别词。在 `.codex-work/asset-names.md` 留存“完整专名 → 缩写 → 原文件名/旧路径 → 最终路径 → 消费位置”映射；不把该映射作为运行资源打包，不因此缩写 App 可见名称、正文、真实作者名或许可要求的署名。
- **文件名示例**：`pexels-central-business-district-123456-20261027.jpg` 导入为 `assets/media/city/cbd_cover.jpg`；`unsplash-empire-state-building-20261027T103000.jpg` 导入为 `assets/media/city/esb_detail.jpg`。其中 `cbd` 和 `esb` 分别在内部映射到完整主体名；有独立同主体素材时使用 `cbd_cover_01.jpg`、`cbd_cover_02.jpg`，不能把同一原图改名冒充独立照片。
- **同步引用并复验**：既有项目只迁移当前项目自有资源，先保存旧路径映射，再同步 `pubspec.yaml`、Dart asset key、生成资源访问器、JSON/种子数据、资源清单 `localAssetPath`、视频封面、原生引用与实际页面映射。核对大小写、唯一性、文件内容/解码及重建后实际加载，不能只改文件名导致占位图。源站网址、`provider`、`providerAssetId`、`retrievedAt`、作者、许可及哈希等核验信息按第 10.1 节原样保留在相应记录中，不因清理文件名删除或缩写来源事实，也不改写 App 的三个固定 HTTP 协议模板或三个协议文件名。

固定路径继续使用 `assets/logo.png`、`assets/media/resource_manifest.json`、`assets/backgrounds/<page_id>/<page_id>_background.png` 及既定插画目录规则；背景中的 `<page_id>` 与页面真实 ID 一致，新建 ID 涉及专名时使用统一短名，不为缩短 `background` 等用途词随意破坏路径契约。Logo 下载/导出阶段仍按第 2.5 节使用用户项目名，导入后最终为 `logo.png`。第三方依赖或工具强制要求的文件名、许可文件和系统资源名保持其契约，不批量重命名依赖目录或用户私有媒体；字体改文件名时保留其内部名称、许可及正确配置。清理命名不会免除任何许可/署名义务。

#### 10.1.3 项目名称隔离的图片下载暂存

在任何图片生成、下载或导出开始前，先用用户提供的项目名称创建项目专属暂存根目录 `~/Downloads/<sanitized-project-name>/`；本机默认绝对路径为 `/Users/admin/Downloads/<sanitized-project-name>/`。仅对文件系统不安全字符做稳定替换，并在 `.codex-work/asset-names.md` 记录原项目名与实际目录名；不得使用 Flutter 内部标识代替用户项目名。预先创建 `logo-candidates/`、`backgrounds/`、`content/` 和 `exports/` 子目录，所有本项目生成图、图库下载图、浏览器导出图和中间转码文件先落在对应子目录，不能直接落在公共 Downloads 根目录，也不能写入其他项目的暂存目录。

统一资源根目录必须实际创建并留证：运行 `python3 <skill-root>/scripts/prepare_asset_staging.py --project-root <target-project-root> --project-name "<用户项目名>" --downloads-root /Users/admin/Downloads`，将根目录固定为 `/Users/admin/Downloads/<sanitized-project-name>/`，并写入项目 `.codex-work/asset-staging.json`。所有生成、拉取、浏览器导出和转码图片先落入这一个根目录的四个分类目录；公共 `/Users/admin/Downloads` 根目录、其他项目目录、工程内伪 Downloads 目录、未登记子目录和符号链接均禁止。复制进工程 `assets/` 前后运行 `validate_asset_staging.py`，发现散落文件或跨项目路径就阻断，不按时间或通配符搬运公共 Downloads。

下载/生成文件经 MIME、文件签名、尺寸、哈希、许可和去重核验后，复制到当前工程的 `assets/` 分类目录并更新资源清单、来源证据和旧路径→新路径映射；运行时代码只能引用工程内 asset key，不能引用 Downloads 绝对路径。项目专属暂存目录可保留供复核，但不得打包进 App、`aduit/` 或 Flutter 依赖，不扫描、移动、覆盖或删除其他项目的文件。浏览器无法改变默认下载位置时，只追踪本任务确切输出并立即迁入该项目目录，严禁按时间或通配符批量搬移公共 Downloads。

### 10.2 仅开发期访问第三方供应商

Pexels 和 Pixabay 仅用于开发/CI 发现资源，已发布 iOS App 不得调用它们的搜索、刷新、埋点或媒体 API。

曾经出现在文档中的真实凭据视为已暴露，不继续使用或传播。先核实其属于本项目及受影响消费者，只在已有授权与供应商管理能力均可用时撤销和轮换对应凭据，不撤销无关或范围不明的共享密钥；无法完成时记录该项 `Blocked`，使用无需该凭据的素材方案继续，不以轮换阻断整个项目。真实密钥不得写入源码、Dart defines、plist、xcconfig、assets、fixture、共享 URL、日志、崩溃报告或二进制。

只能使用未跟踪的环境变量或 CI Secret：

```text
PEXELS_API_KEY=<configure-locally-never-commit>
PIXABAY_API_KEY=<configure-locally-never-commit>
```

采集工具必须使用 HTTPS 主机白名单、有限重定向、MIME 和文件签名校验、文件大小限制、安全文件名、SHA-256、缓存、去重和许可核对。Logo 开发生成入口 http://stargate.local:3100/ 是本规格明确允许的本地 HTTP 服务，仅用于开发生成，不因上述 HTTPS 规则被拒绝，也不进入已发布 App 的运行时请求。供应商必须通过查询参数接收凭据时，仅在采集工具内即时构造请求并对日志脱敏，不写入文档或公开链接。遵守供应商限流和 `Retry-After`；认证错误和参数错误不得自动重试。

### 10.3 品牌资源

选择 Stargate 时，生成界面返回 HTML 属于生成界面的正常响应，不能仅凭这次 GET 就判断生图服务失败。使用可用浏览器打开该界面，读取当前实际模型/连接配置并提交生成，再从结果中的图片下载、`url`、`dataUrl` 或 `b64_json` 取得图片字节。选择其他工具时按其真实支持的生成与导出方式取得成品。确需调用接口时，必须以该工具的实际请求或官方接口说明为依据，不把页面路径当接口、不猜测 API 路径或模型，也不从网页脚本示例推断已配置的服务。沿用已有会话授权，不输出凭据；没有可用配置/操作工具时记录具体限制后走有界回退。图片先下载至临时文件，成功解码并完成规格核验后才替换正式 Logo；错误响应不能覆盖已有有效图片。

生图批次完成且全部结果已下载、验收并复制后，必须清理 Stargate 生成记录。删除记录必须在下载完成后执行。使用 Stargate 页面本身或其官方/明确记录的删除动作，逐个删除本批实际 `generation_task_id`；不能猜接口、不能删除其他项目或不属于本批的记录。清理结果写入 `.codex-work/generation-cleanup.json`，至少包含 provider URL `http://stargate.local:3100/`、task IDs、下载文件路径、`trigger: after_download`、`download_status: completed`、精确 `deleted_task_ids`、删除时间、执行方式和证据。运行 `python3 <skill-root>/scripts/cleanup_generation_history.py --project-root <target-project-root>`；待处理、只删了一部分、下载前删除、执行方式不明或没有证据都标为 `Blocked`/`Not verified`，不能当作完成。该检查只验证用户明确执行过的删除结果，不会猜测或自动删除网站历史。

**Logo 提示词的主题级概括**：只保留大致行业/对象、一个主轮廓或关系、画风、克制的材质/光线提示和明亮方向，不把创意中的每个细节复制进 Logo prompt。大楼建造主题使用一个建筑主体加一个施工提示即可；楼层、设备、人物、施工步骤和业务模块交给 App 页面。最多一个主主体和两个辅助线索，缩小到 60–120 像素仍要一眼可辨；细节堆叠、拼贴拥挤、文字化标签和小元素墙即使主题覆盖完整也淘汰。

下载/导出成品按第 2.5 节先命名为 `<用户提供的项目名称>.png`；验收后以该名称导入目标工程 `assets/`，再改名为 `logo.png`。在 `.codex-work/brand-assets.md` 记录实际下载/导出路径 → 工程内项目名路径 → 最终 `assets/logo.png`，关联同一图片的哈希与必要后处理；不把项目名版本额外声明为运行资源。可选的 Logo 取色、AppIcon、原生启动图及 HTML 的 Logo 继续从 `assets/logo.png` 派生；其他成图按第 6.12 节另起用途名供 Flutter 使用，文件名要求不改变 Logo 图像无文字的要求。

Logo 的视觉验收遵循第 2.5 节：根据主题元素在模拟现实、手绘、油画、艺术四种画风中选择并实际核对，记录所选主画风及元素依据；模拟现实须结构、比例、材质与光影可信，手绘须线条精细且有层次，油画须笔触细腻、颜料层次丰富且主体清晰，艺术画风须表现手法、构图和色彩语言明确并保持主题辨识。实际查看原尺寸与图标尺寸，按所选画风检查造型与视觉逻辑、材质和光影的协调性及小尺寸辨识。另逐张检查 AI 风格风险和现实逻辑：比例、透视、连接、遮挡/接触、重力支撑、反射/阴影方向、材质纹理、边界闭合和物体结构必须能够解释；伪文字、随机碎片、重复部件、融化边缘、不可能反射、重复纹理或明显模型生成感直接淘汰。Logo 与页面统一采用明亮色调，明亮冷暖色和白底均可使用；保留必要阴影和材质层次，避免整体灰暗或压黑，不设色系或渐变数量配额，但页面视觉表面必须消费渐变令牌。几何色块堆叠拼贴、粗糙简笔、简陋通用图案、禁止 3D，以及融化/断裂细节、重复纹理、随机碎片、伪文字、明显 AI 生成感、无依据塑料感或强光效等不得通过。Logo 是品牌图形，允许与画风一致的笔触和艺术化提炼，不要求照片写实；文件规格与可选取色记录正确不能代替视觉验收。

所有由 AI 生成并进入项目的图像都须满足工作流文档第 6.1 节：禁止以简约线条/细轮廓、扁平几何或纯色块堆叠作为整体风格或主要主体，须根据主题做出细节充分、层次丰富、质感明确、色彩协调的完整画面。该规则适用于 Logo、插画和其他 AI 视觉素材；不是要求每处堆满细节，次要装饰可以使用线条或色块。AI 图不计作真实照片，也不得取代第 10.6 节所需的第三方许可摄影。

实际生成失败或最终图片无效时，先核对原任务状态，再按第 2.5 节选择实际可用且支持相同规格的其他模型、工具或网站；无需为了选用其他来源先等待 Stargate 失败。切换模型时核对页面选择值或真实请求的 `model` 字段已经改变，再在原预算内提交。按四种画风各 3 张、每任务一张的 12 张独立候选流程保留高质量与 `1024x1024`，最多 24 次提交与整组 30 分钟预算内补齐失败候选并重新验收；只改提示词不算切换模型，切换来源不重置预算。无可用替代来源或预算内仍无法取得合格成品时再记录正式 Logo 阻断，继续本地页面、Listing 和 Remarks。

正式品牌按第 2.5 节从合适生图网站/工具以高质量生成 12 张独立候选；来源不要求统一，Stargate（http://stargate.local:3100/）为可选入口；模拟现实/手绘/油画/艺术表现四组各 3 张，经第 2.5 节逐张比较后从全部候选中选出可见生成痕迹最少且合格的那一张，再经过必要本地后处理导入为 `assets/logo.png`，作为唯一源。在 `.codex-work/logo-selection.md` 保存 12 份主题与画风简报、完整提示词、实际参数、成图及原图/图标尺寸比较。各候选统一明亮色调，不按色系覆盖、候选配色差异或渐变数量淘汰或补图；页面渐变实际消费是硬门槛，数量不设配额。不要把所有主题默认套成橙黄夕阳，具体主体、光照、构图和色彩应有主题依据，橙黄与夕阳本身不被禁止。验证图像质量、背景满幅、主题意象、完全不含文字或项目名称、比例、无 Alpha 通道、AppIcon 尺寸、原生启动页、欢迎页、初始化页和平台引用；App 内展示 Logo 时同样使用圆角容器。Logo 必须为 `1024x1024` RGB PNG，由智能体自主校验，不等待用户审批。正常路径的首次 Logo 生成、选择与校验是 App 开发前置步骤，主题色统一明亮，Logo 取色仅作可选参考；只有第 2.5 节真实失败回退时才先做暂定品牌的本地开发，正式品牌发布仍依赖合格 Logo。最终 AppListing 的生成与 About 配色复验在第 12.1 节完成，随后按第 12.2 节生成英文审核备注。
主题实现的证据链为 `common_module/theme/app_theme.dart → real screen/component → iPhone screenshot`。`app_theme.dart` 是 AppPalette/AppTheme 的全局色彩与渐变 API，App、引导页和 About 使用项目选定的明亮色彩。若选择从 Logo 取色，另行记录 `assets/logo.png → raw HEX → theme token` 的真实来源；没有取色时不虚报已经提取。实际检查整体明亮、主题契合度、主体辨识与文字/控件对比度，不按特定色名或色相数量重生或重选。

主题色落地须核对实际主题令牌、页面/组件消费和当前 iPhone 截图，可在 `.codex-work/brand-palette.md` 保存所选色值、用途、源码引用与截图位置；若使用 Logo 取色，补充原始 HEX 与派生关系。没有 Logo 取色仍可继续，但每个视觉表面必须有实际消费的渐变令牌；不要求页面数量、色彩来源或渐变令牌数量，不以已定义色值或 About 页着色单独作为实际展示证明。

### 10.4 Logo 实际替换、品牌封面与图标核验

生成或下载 Logo 不等于完成替换。工程建立后必须实际更新引用、派生资源与构建配置；交付前再核验最终构建，不能仅保存 `assets/logo.png` 或只替换其中一个页面。所有项目操作均限定在当前目标工程内。

本节区分正式 Logo 与主题插画：AppIcon、原生启动页/同款承接层用正式 Logo；`lib/welcome.dart` 仅保留一处 Logo，位置按本次独有构图确定，不额外重复；独立 `aduit/welcome.html` 和三个协议 HTML 保持原 Logo 安排。Initialization、Settings、内容页按第 6.12 节用其他已改名合格插画。三页职责不变，内容摄影仍用真实第三方素材，生成插画不冒充照片。

1. **列出全部替换位置**：扫描旧 Logo、默认 Flutter 图标、开发临时品牌图、旧封面及其引用，结合实际页面查看，建立 `.codex-work/brand-assets.md` 映射表，记录展示位置、旧资源/引用、最终源/派生文件、消费组件或平台配置及验收证据。检查 Dart 页面、`pubspec.yaml`、iOS 资源目录、`Contents.json`、启动 storyboard/配置和 About HTML，不能只按文件名中是否含 logo 搜索。
2. **分别接入正式 Logo 与转用素材**：正式 Logo 的必要展示与派生只从 `assets/logo.png` 取得，更新 AppIcon、原生启动页及同款承接层。HTML 保持原 Logo 规则。取消旧版“Welcome 与 Initialization 都必须贴 Logo”的要求；按第 6.12 节评估每张非选中成图，合适者另起主题/用途短名，落在 `assets/illustrations/<feature_or_page_id>/` 并接入对应 Flutter 页面，替换跨页重复 Logo。保持图像完整、不拉伸，记录源候选/哈希、导入新名、实际消费者与截图；不能只改名或只登记资源。
3. **复验唯一品牌源**：校验 `assets/logo.png` 为 `1024x1024`、`image/png`、RGB 且无 Alpha 通道/透明度数据，并按第 2.5 节查看实际画质、主体辨识、满幅背景与无文字图形；记录源文件 SHA-256。正式品牌派生追溯到该文件，其他插画追溯到各自原始成图；主题色可自由选择，只有声称取自 Logo 的色值才需证明像素来源，不能用预设主题色反向改图后声称已取色。
4. **实际生成并启用 iOS 图标**：从正式 Logo 导出当前 Xcode 所需的 iPhone/App Store 图标，写入 `ios/Runner/Assets.xcassets/AppIcon.appiconset` 并更新 `Contents.json`；检查实际构建配置选中的 AppIcon 集合。使用项目已有且适用的图标生成工具时须实际执行并核对产物，仅添加工具配置不算完成。同步并实际更新 iOS 原生 `LaunchScreen.storyboard`/对应资源：静态显示放大的 Logo、独立 `PRYRIN` 字标、来自创意的品牌定位文案及品牌装饰线；按第 7.1 节完成全屏静态品牌背景、主题图片叠层与主次排版，禁止纯白/近白底配居中小方图、单图留白屏或孤立文本。启动页必须记录全屏背景、主题图、品牌、文案和装饰五类视觉层；至少两种明亮渐变/光照令牌参与背景，白底不能作为唯一背景。不得在原生启动页加入动画、进度条或伪造加载步骤，不得把 `PRYRIN` 或定位文案合并进 Logo 图片。此静态原生启动资源之后，非游戏项目进入含 `Continue` 的 Flutter Welcome；游戏/混合项目进入 `lib/welcome.dart` 的沉浸式游戏大厅（Play、Load、Operation，顶部 Exit、Settings），不显示普通 Continue 或引导卡片；只有 Clear Data 成功后才进入 Initialization（Enter）。不生成其他设备或平台的图标、样机图与截图。
5. **同步 About 的实际图片**：最终生成 AppListing 并整理为 `aduit/` 后，按第 12.1 节从正式 `assets/logo.png` 生成网页小体积派生图，保存为 `aduit/site/img/logo.png`，记录源/派生哈希并核对视觉身份与配色（不要求二者字节相同），修正三个协议 HTML 页面的 Logo/品牌封面引用并实际查看本地渲染。站点品牌封面通过该图片与内联样式实现，继续保持 `site/img/` 只有 `logo.png`，不新增 cover 文件或其他白名单外资源；生成器不得把旧 AppIcon 或旧品牌图覆盖回来。
6. **检查实际构建与显示**：重新构建并安装当前 iPhone 版本，检查构建资源、桌面 App 图标、iOS 静态冷启动页（Logo 尺寸、`PRYRIN`、定位文案、装饰线）以及按项目类型分流的唯一 Flutter 首屏：非游戏为 Welcome（`Continue`、真实步骤/百分比/进度条、减少动态状态和错误恢复），游戏/混合为沉浸式游戏大厅（Play、Load、Operation，顶部 Exit、Settings），并检查所选结束操作成功后 Initialization（`Enter` 与底部协议文案）及其他现有品牌位置；保存对应截图。按第 7.1 节核对非游戏 Welcome 或游戏大厅的背景、功能/入口布局、内嵌加载状态和排版，按第 7.2 节核对 Initialization 内容及唯一协议文案；同时确认运行首屏与独立 HTML 交付页无协议文案。分别保留原生冷启动、非游戏 Welcome 首帧或游戏大厅首帧、受控加载/错误态、结束操作后 Initialization 的证据。仅有居中 Logo、少量文字和大片无目的空白不能通过。不得为截图延迟生产启动，受控慢准备只用于测试。原生图标和启动资源不能仅凭热重载验收；若仍显示旧图，先核对实际源、构建目标、资源集及安装版本，再进行有针对性的重新导出/构建与复验，不自动卸载含用户数据的 App，也不盲目反复清理。
7. **清理旧引用并完成交付核验**：确认新资源已实际使用后，移出不再使用的旧品牌文件；必要恢复副本保存在 `.codex-work/`，不混入运行资源或发布包。重新扫描源码、资源声明与构建产物，并对照映射表逐项核验，不误删仍使用的内容封面或必要派生图标。最后的第 10.7 节必须再次检查品牌封面与平台图标；有旧图、默认图标或临时封面残留时修复并复验，不标记完成。
8. **记录真实结果**：报告生成参数/时间、提示词、源哈希、派生关系、主题映射、实际替换文件/引用、构建版本、桌面图标与封面截图。已有品牌展示位不得以“文件已存在”标为 `Verified`；没有对应位置时说明事实，缺少 iPhone 运行环境时将显示验证记为 `Blocked`/`Not verified`，继续可执行的文件与配置校验，不改用其他设备。

#### 10.4.1 iOS 原生 AppIcon 独立闭环

`assets/logo.png` 属于 Flutter 图片资源；iPhone 桌面图标来自 Xcode 编译的 AppIcon 资源集。替换 App 内 Logo、启动图或 About 图片不会自动更新桌面图标，必须分别验收。Flutter 工程创建/原生目录恢复完成后立即生成并接入 AppIcon；后续 Logo、图标工具、原生配置或资源生成步骤改变图标输入时，重新生成并复验，不能让模板图标覆盖回来。

1. **实际导出，不只配工具**：以正式 `assets/logo.png` 为源，实际执行适用的图标生成工具或可靠本地缩放，核对退出结果和真实产物。覆盖实际使用的 `ios/Runner/Assets.xcassets/AppIcon.appiconset`（自定义集合则使用其真实路径）及 `Contents.json`；按当前 Xcode、最低 iOS 与 iPhone 目标检查所需规格和 App Store 图标。接受当前 Xcode 有效的单一 1024 图标/通用资源集模式，不机械补过时槽位或其他设备图标。逐个核对声明文件的精确大小写、存在性、可解码性、像素尺寸与无 Alpha；已声明的深色/着色等变体也不能残留默认图。图标保持满幅正方形，由 iOS 加系统圆角蒙版，不预先挖透明圆角。
2. **核对解析后的选择**：列出本项目实际开发、测试和交付使用的 scheme、App target、configuration/flavor 与 SDK。对每个实际使用组合，以 `xcodebuild -showBuildSettings` 或等价工具读取解析后的 `ASSETCATALOG_COMPILER_APPICON_NAME`、`PRODUCT_BUNDLE_IDENTIFIER` 和资源编译输入，追溯 project、target、xcconfig/继承覆盖及构建脚本。选中的图标集合必须真实存在并含正式 Logo 派生图，不能只查默认 Debug 的 `AppIcon`，也不能只改未被选中的集合；不新增无关配置或设备目标。
3. **启动页视觉契约预检**：在提交当前 iPhone 冷启动证据前，运行 `python3 <Skill 根目录>/scripts/validate_launch_screen_visual.py --project-root <实际 App 根目录>`。该检查要求真实启用的 Launch Screen storyboard、全屏渐变/混合背景、至少两种明亮背景令牌、存在且可解码的主题图层、品牌/项目名/定位文案、装饰层、非居中的复合布局和 `.codex-work/launch-screen-current-build.*` 证据；拒绝纯白/近白单图屏、居中小方图、大面积空白和缺少任何视觉层的配置。预检通过仍必须在当前 iPhone 实际冷启动复核。

3. **核对最终产物，不只查源目录**：在最后一次相关变更后，用实际配置完整构建；交付包含 archive/导出时也检查其中真实的 `.app`。读取产物 `Info.plist` 的 `CFBundleIcons`/`CFBundlePrimaryIcon`、`CFBundleIconName`/`CFBundleIconFiles` 等当前产物适用信息，结合实际图标 PNG、`Assets.car` 的可用检查工具及资源编译日志确认图标已编译，缺失/未分配图标警告须定位。不能假定每版 Xcode 都输出相同 PNG 文件名；也不靠手改已签名产物或 plist 伪造通过。记录源哈希、派生命令/工具版本、输出规格与文件哈希，并实际查看图标尺寸画面。缩放/编码后的图标哈希不要求等于源 Logo；保留同尺寸派生关系和可解码视觉对照。发现 Flutter 默认图形时，可用当前 Flutter SDK 的模板图作参照，核对图像内容而非仅按文件名、数量或生成工具成功退出判断。
4. **验证实际安装与桌面显示**：在既有的唯一 iPhone 测试目标上安装对应的新构建，核对 bundle ID、版本/构建号、产物路径/构建标识和 iPhone UDID。目标尚无该 App 时正常首次安装；目标已有该 App 时，只有 bundle ID、签名和安装配置兼容且可原位升级才执行更新。若更新要求先卸载、无法确认数据可保留或安装身份不匹配，停止该更新动作并记为 `Not verified`，不尝试卸载重装。回到系统主屏幕实际查看 App 图标并保存可辨认截图，再分别验证原生冷启动与 App 内品牌位置。模拟器构建与 `iphoneos` 归档分开取证，模拟器桌面截图不冒充真机或已安装归档证据；只验证 Debug 不能证明 Release/flavor 正确。App 内图片截图、Xcode 资源预览、热重载或热重启均不代替桌面图标验收。
5. **默认图标按断点修复**：依次检查正式源 → 实际选中集合 → 编译产物 → 对应安装 → 桌面显示。优先修复未执行生成、错误集合/配置、脚本覆盖、漏编译或装错构建；上游已正确时不盲目重复生图。只有正确产物与正确安装均已证实时才调查图标显示缓存，且只在确认身份/签名兼容、可原位升级并保留数据时刷新。不得自动卸载有真实数据的 App、调用 `Clear Data`、删除数据容器、抹除/新建模拟器或重置设备来刷新图标；无法安全刷新时仅保留该显示验证缺口，继续其他独立任务。
6. **必填证据与完成条件**：在既有 `.codex-work/brand-assets.md` 中，为每个实际构建组合填写：源 Logo/哈希、生成命令/版本与派生文件、资源集/规格检查、scheme/target/configuration/SDK、解析后的图标集合与 bundle ID、最终产物路径/构建标识及编译图标证据、实际安装身份、iPhone 桌面截图、缺陷/修复/复验和状态。源图、配置、产物、桌面显示分别记录结果；所用图标仍含 Flutter 默认图、旧图或临时品牌即为 `Failed`，缺运行证据为 `Not verified`。只有正式源派生正确、实际配置选中正确、最终产物图标正确且对应 iPhone 桌面显示正确，才将原生 AppIcon 标为 `Verified`。后续图标输入或交付产物变更使相应旧证据失效，须在第 10.7 节最终检查时更新，不沿用早期 Debug 截图。图标缺口不取消独立的 AppListing/About/Remarks 生成，也不允许报告正式品牌或整体发布已就绪。

#### 10.4.2 iOS 原生 Launch Screen 实际接入与验收

原生启动页必须完成“正式设计 → 实际启动配置 → 编译产物 → 对应安装 → 冷启动显示”的独立闭环。新图已生成、storyboard 预览正确、AppIcon 已替换或 Flutter 页面已美化都不能证明原生页已启用。本节对原生接入和验收优先适用；旧文中的 Loading/Enter 称呼不能改变三页职责：原生静态 Launch Screen 之后进入每次启动的 Welcome（`Continue`），只有确认的结束操作成功后才进入 Initialization（`Enter`）。

1. **先完成可落地的静态设计**：按第 7.1 节实际制作并接入整屏品牌背景、明显放大的圆角 Logo、用户项目名、独立 `PRYRIN` 字标、真实定位文案与品牌装饰线。背景统一明亮，必须使用全屏渐变/混合背景与主题图片叠层，配合精细主题装饰，保持安全区、可读性和主次；禁止纯白/近白底、居中小方图、单图留白屏或孤立文本，不能只放小方图加名称而缺少完整构图。背景与品牌派生图保存到工程内按用途命名的资源目录，实际供 iOS asset catalog/启动 storyboard 使用，记录与 `assets/logo.png` 的关系；只写入 Flutter assets 不算原生接入。用静态图像合成实现必要的圆角和实际消费的渐变令牌，不依赖自定义运行时代码、动画、网络、进度或按钮；原始 Logo 仍为无 Alpha 的完整 PNG。布局延展到屏幕边缘，品牌文字与主体避开刘海、安全区和裁切。
2. **解析真正启用的启动入口**：对每个实际使用的 scheme、App target、configuration/flavor、SDK，读取 `xcodebuild -showBuildSettings` 或等价解析结果，核对 `INFOPLIST_FILE`、`GENERATE_INFOPLIST_FILE`、适用的 `INFOPLIST_KEY_UILaunch*` 设置及来源覆盖。在实际生效的 plist 中检查 `UILaunchStoryboardName`、`UILaunchScreen` 和适用的设备后缀/多 storyboard 配置，确认当前 iPhone 真正选择本次制作的 storyboard；处理自动生成入口、旧资源入口与自定义入口的冲突，不盲目同时追加多组键。检查 storyboard 的实际路径、Base/其他本地化版本、资源成员关系或同步目录规则、资源编译输入，以及图片/颜色资源名的精确大小写与外观变体。不能只编辑一个名为 `LaunchScreen.storyboard` 的未使用文件，也不能只检查默认 Debug 配置。
3. **防止生成器再次覆盖**：检查 `flutter_native_splash` 等已用工具的配置、实际命令、脚本和 Build Phases 对启动 plist、storyboard 与图片的修改。明确唯一维护来源：工具能表达设计时更新其配置并实际生成；否则将完整静态设计通过可重复的资源接入/后处理步骤保留。最后一次生成后重新检查关键文件及派生关系，再构建验收；后续生成命令仍能保留新设计才算稳定。不要为修复而盲目添加新的 splash 依赖，也不能修改完资源后再运行旧配置把它覆盖。仅看到文件存在或生成命令成功退出不能通过。
4. **检查最终包及安装身份**：使用实际配置重新完整构建，读取最终 `.app/Info.plist` 的生效启动入口，结合编译日志检查对应 `.storyboardc`、资源及可用的 `Assets.car` 检查结果，确认新设计真实进入产物；不能只看源码目录或要求所有 Xcode 版本生成相同文件名。交付涉及 archive/导出时单独核对其中真实 `.app`，模拟器 Debug 结果不替代它。记录产物路径、构建标识、bundle ID、版本/构建号、配置和 iPhone UDID，并确认安装的正是该产物。已有 App 只在身份、签名兼容且可保留数据时原位更新；否则将安装/显示记为 `Not verified`，继续独立工作，不手改已签名包或卸载重装。
5. **验收真实原生帧及衔接**：在同一现有 iPhone 测试目标上，终止该 App 后从启动前开始连续录屏，再启动对应版本；从录像中分别识别系统原生帧、Flutter 首帧和 Welcome。检查本次静态设计确实出现，随后直接进入 Welcome，无旧小方图页面、白屏闪烁或额外 Flutter Splash/Loading。结合启动配置、首帧日志/时间与路由确认旧画面究竟属于原生还是 Flutter，不凭单张截图猜测。原生帧过短未捕获或缺运行条件时，文件/配置/产物可分别记录结果，但原生显示仍为 `Not verified`；不拿设计稿、预览、热重载/热重启或 Welcome 截图替代。必须按第 10.4.3 节保留同款原生承接层，在 Welcome 实际就绪后继续保持 250 毫秒再淡出；不得为取证额外加时、另建 Splash 页面，或用 `deferFirstFrame`、`FlutterNativeSplash.preserve()` 长时间扣住系统启动页等待业务数据；真实准备状态仍在同一个 Welcome 内。
6. **按断点修复并复验**：仍见旧画面时按源与生成结果 → 生效入口/本地化/资源集 → 编译产物 → 安装身份 → 冷启动帧逐层定位，修复有证据的断点后重建复验。只有产物和安装均已证实时才调查系统启动快照/缓存，不把缓存当默认原因。不得自动卸载有数据的 App、调用 Clear Data、删除数据容器、抹除或新建模拟器，也不以全局清缓存或反复 clean 掩盖未接入问题。Clear Data 的测试仅按既有用户确认流程执行，不能用它刷新启动页。
7. **填写独立证据并在最终构建复查**：在 `.codex-work/brand-assets.md` 为每个实际构建组合记录源/派生资源及哈希、生成或后处理命令、解析后的启动入口、实际 storyboard/图片资源、最终编译产物、安装身份、连续冷启动录像/对应帧、系统外观变化后的明亮显示与 iPhone 布局检查、断点修复和状态。源、配置、产物、原生显示分别有证据且新设计确实显示后，才标为 `Verified`；仍是缺乏设计的小方图加名称或旧启动页则为 `Failed`，不以白色背景本身判失败。后续 Logo、生成器、启动配置、资源或最终包变化使受影响证据失效，须在第 10.7 节和实施第 19 步更新，不沿用早期截图。缺口只影响对应质量/发布结论，不阻断独立 AppListing、About 和 Review Remarks，也不得据此声称整个项目已验证完成。

#### 10.4.3 启动黑白屏与原生画面到 Welcome 的无缝衔接（硬门槛）

本节必须与第 9.1.1 节的最新稳定 iOS／UIScene 生命周期一起实施：承接层挂在当前有效 UIWindowScene 的真实窗口，engine/插件及就绪通道在正确回调注册一次，不能在 AppDelegate 启动回调强转尚未建立的 FlutterViewController。Scene 断开/重连、窗口替换及前后台恢复时核对窗口与操作代次并清理旧回调；仍保留以下前台连续 250 毫秒规则。按第 11.1.1 节在实际最终构建验证，不能只修颜色和遮罩而保留旧生命周期入口。

每次进程冷启动，必须保持原生启动视觉，直到 Welcome 完成首屏加载和实际绘制；从该就绪时刻起继续完整保留 0.25 秒（250 毫秒），再淡出到 Welcome。此项为硬性规定，不是可选美化，覆盖正常启动、离线和首屏加载较慢的情况。交接中出现属于 App 的整屏黑帧、白帧、空容器、旧启动图，或提前移除承接层，均判定失败。仅改背景色、加一个从启动时刻开始的 250 毫秒计时器，不能满足此规定。

iOS 系统 Launch Screen 的撤下时机由系统控制，不能宣称直接延长或动画化系统启动快照。实现时保留静态系统 Launch Screen，并在应用原生窗口/控制器可见前放置与其构图一致的原生承接遮罩（native launch cover），覆盖在 Flutter/Welcome 之上；系统画面撤下后由此层连续承接，最终仅淡出该原生层。它是同一次启动的呈现过渡，不是第四个页面、Flutter Loading 路由或第二次启动页。不得通过阻塞主线程、sleep、迟迟不调用 runApp、长期 deferFirstFrame 或 splash preserve 等待业务来制造停留；底层 Flutter 与 lib/welcome.dart 必须持续构建、布局和绘制，不能被设为隐藏或零尺寸。

1. **先实现连续的原生承接**：按第 10.4.2 节核对生效的系统启动入口与最终产物。承接层复用同一正式品牌资源、背景、Logo 尺寸/位置、文字、安全区和 统一明亮外观，铺满窗口，在任何 Flutter 空白表面露出之前安装；同时设置窗口、Flutter 根层及 Welcome Widget 的首帧背景。不要盲改透明度、重建窗口或重复挂载控制器。除退出时透明度淡出外，承接画面保持静态；不同层品牌位置须协调，淡出时不能出现双 Logo 错位、闪动或比例跳变。
2. **以实际 Welcome 就绪驱动**：定义同一操作的 welcome_ready，要求必要配置/最小导航准备完成、`lib/welcome.dart` 首屏已布局、首卡及首屏必需图片已解码且可绘制、Flutter 帧已提交呈现、Continue 的 Dart callback 可用。结合当前引擎实际支持的呈现证据与连续画面确认，单独 postFrameCallback 或启动计时器不能证明完整就绪。就绪回调绑定操作 ID/导航版本并防迟到/重复触发，与 Continue 分离；不等 HTML、DOM、网页消息或任何桥通道。非首屏媒体和非关键装饰不阻断启动。
3. **就绪后完整保持 250 毫秒，再淡出**：确认 welcome_ready 后才启动单调时钟计时，原生承接层以不透明状态再保留 0.25 秒；fade_started - welcome_ready 必须至少为 250 毫秒，不能从进程启动、路由创建开始或仅完成数据 Future 时提前计时。将保持时长定义为唯一常量，例如 launchHold = 0.25，不能因启动快、减少动态或某个页面配置改为 0。计时结束在主线程执行透明度从 1 到 0 的淡出，淡出时长为明确的短常量（默认约 0.20 秒，可按视觉核验微调，不能替代或抵扣前面的 0.25 秒）。完成回调后才移除承接层并恢复 Welcome 的点击/无障碍操作，保证底层已经是完整首屏。期间不自动执行 Continue、不跳过欢迎页、不伪造进度；系统减少动态时保留同样的 250 毫秒保持和短透明度过渡，关闭缩放、位移、呼吸等非必要运动。
4. **保持有界失败恢复**：启动必需准备与本地 Welcome 首屏沿用第 7.1 节同一总预算 10 秒，不为独立 HTML 叠加等待预算或将其纳入启动。就绪后停止该准备超时计时，再执行强制的 250 毫秒保持和淡出；这段过渡不属于虚构加载工作，不计入百分比。准备超时或首屏失败时，取消本操作的成功就绪/淡出回调，在同一 Welcome 渲染可操作的错误恢复界面；确认该恢复首帧已绘制后，同样保持 250 毫秒再淡出承接层，露出 Try again 与 Clear Data，不能无限遮住错误按钮或把错误标成正常加载成功。Retry 使用新操作 ID，不重放系统 Launch Screen；所选结束操作沿用第 7.7 节同一二次确认与恢复流程；只有 Clear Data 真实清除成功才进入 Initialization，Exit App 成功留在当前可恢复边界。非关键图片失败不得无限阻断启动，但其资源质量仍按失败记录。
5. **处理生命周期与迟到回调**：保持/淡出任务与当前窗口、启动操作和 Welcome 实例绑定；取消、重试、清除或控制器释放后旧任务不得移除新遮罩。未完成启动时退到后台，暂停/取消当前过渡，回前台重新确认实际首屏并满足前台连续 250 毫秒保持后再淡出，不让后台计时造成回前台闪黑。已经进入可用页面后的普通前后台恢复保留当前页面，不重新挂原生承接层；结束操作成功返回 Initialization 也不重播原生页或此冷启动遮罩。完成后释放计时器/动画和就绪订阅，不能留下挡点击的透明层。
6. **记录时间顺序与真实画面**：在既有 .codex-work/brand-assets.md 记录构建/安装身份、iPhone/iOS、启动操作 ID、单调时钟及 native_cover_attached、flutter_first_frame、welcome_ready、hold_started、fade_started、fade_completed、cover_removed 时间；注明 250 毫秒常量、实际保持时长、淡出时长及最终层级。用当前交付构建从启动前开始连续录屏并逐帧检查，证明原生画面连续承接、Welcome 已绘制、保持满 250 毫秒后才淡出且结束后可操作。时间日志不能代替画面，录像帧数也不能代替单调时钟的时序核验；不拿设计预览、热重载或一张正常截图替代。
7. **冷启动与回归判定**：同一现有 iPhone 上 系统明暗设置下保持明亮，各至少 3 次终止进程后的冷启动；另覆盖快速完成、受控慢准备、Flutter 欢迎首屏就绪延迟/失败、首屏必需图片解码失败、离线、重复就绪、重试、后台/前台、减少动态及 所选结束操作后 Initialization 不重播。受控慢/失败注入只用于测试，不进入正式行为；正式行为必须保留上述 250 毫秒过渡。黑/白空帧、未就绪就淡出、保持不足、Logo 跳变、透明层残留或不可操作恢复均为 Failed；缺运行环境或时序/录像证据为 Not verified。修复后重建并在第 10.7 节刷新受影响证据，不能以单次成功或仅存在遮罩代码宣称无缝衔接。沿用第 10.4.2 节的非破坏排查，不卸载清数据或重置模拟器来消除现象；未通过不阻断独立 Listing/About/Remarks，但不得报告启动质量或发布就绪通过。

### 10.5 图片、视频多样性与资源精修

**独立展示位不复用同图，运行时不联网取图**：项目自有的内容照片、卡片封面、插画、装饰与背景，按“页面/内容 ID/展示位置 → 独立原始素材 → 本地路径”分配。不同页面、主要模块、条目及列表/详情等独立展示位使用不同内容图；不把同一原图换名、裁剪、镜像、滤镜或压缩后当成新图。资源不足时继续搜索/绘制符合用途的新素材，不用 Logo 或占位图反复填满页面；未补齐的展示位如实记为失败，不伪报完成。同一展示位置的重绘/状态恢复不算新展示位；必要品牌 Logo、语义控件图标及用户自己拍摄/选择媒体的准确预览仍保持其真实身份，不擅自改造用户原件或用无关照片替代。

所有 App 自有显示图片在制作阶段下载/生成到当前项目相应 `assets/` 分类目录并打包；运行时使用真实本地 asset key（用户媒体使用其有效私有文件）。不得使用 `Image.network`、网络缓存图片组件、远程封面/背景 URL、热链或“首次打开再下载后缓存”作为正式显示方案；About 的品牌图使用站点内优化副本，实际 Welcome 使用项目 assets，独立 aduit/welcome.html 使用规定的 Base64 内嵌图片。开发阶段用于搜索/下载的 URL 只留素材记录，不能误接到 UI 图片字段。三条生成阶段写入具体项目名的 HTTP 协议 URL与用户主动在 App 内打开协议的既定行为保持不变；本条约束图片数据来源，不改写协议 URL。

本地资源仍须按实际显示尺寸压缩、制作缩略图并限制解码尺寸；按需加载当前可见区域，限制并发解码，不在首帧同步读取/解码全部图片或等待所有媒体预热。图片失败提供有边界的恢复操作，保留页面正文与导航；不能无限重试、抛出未处理异常、用长期占位图假装加载成功，或将装饰图解码作为进入 App 的前置条件。按第 10.7.1 节用最终构建断网冷启动并逐位验证，文件存在不等于不会崩溃。

图片和视频是内容与视觉质量的一部分，必须投入充分的实际筛选、替换与适配工作，优先为不同内容、分类和主页面使用不同的真实素材。按以下规则验收，不靠重复素材、无关视频或大量下载凑丰富度：

1. **先分配再采集**：根据用户创意与页面模块建立资源需求表，记录展示用途、主题对象、构图/色调、比例、最低清晰度、计划独立素材数量与文件规格；按第 10.6 节明确需要真实照片的展示位和跨网站搜索计划。优先区分各主要模块、分类与主要内容的封面和重点展示位；实际包含视频的页面须有与其内容相符的独立片段。没有视频用途的产品不强加视频模块；拍摄、相册和录音以及其他主题能力按能力矩阵评估并接入适用任务。展示随包照片/视频不代表访问系统相册、相机或麦克风，权限仍由真实 API 与能力矩阵核定。
2. **检查完全重复与近似重复**：联合检查原始来源 ID、原片/派生关系、文件 SHA-256，并通过接触表逐张比较图片与视频封面；对视频抽取多个代表帧并实际播放检查。工具可用时补充感知哈希或相似度检查，人工复核候选重复；不可用时继续来源、哈希与视觉核验并记录方法，不伪称已执行算法。不同供应商收录的同一内容也视为重复候选。
3. **禁止伪造独立素材**：同一原图仅改文件名、尺寸、裁剪、滤镜、镜像或压缩仍计作同一来源内容；同一原片的重叠截段、循环拼接、调速、改色或换封面也不能冒充多个独立视频。统计独立素材时按原始内容和确认的视觉重复组计数，不能仅按路径或文件哈希计数。
4. **控制可见复用**：同一首屏、网格、相邻卡片和推荐列表中，不得让不同内容无理由共用同一张图、同一段视频或明显近似封面；主要模块、不同分类及列表/详情等独立内容展示位必须使用不同独立图片。Logo 仅按第 6.12 节保留必要品牌位置，同屏原则上只出现一处，不作为通用卡片封面、状态插画或背景水印；内部 UI 可自主绘制与主题和用途对应的原创图片，分类放入 `assets/illustrations/`。统一语义控件图标、必要品牌标识和用户私有媒体的准确预览可保留并注明用途；项目自有内容图按独立展示位分配，不因同一内容跨页面出现就复用原图，视频封面须准确对应片段且各独立展示位使用不同的真实画面；Logo 的换色、裁剪、镜像和改名不计为独立插画。用户自行导入的重复私有媒体不因这些随包资源规则被擅自删除。
5. **逐屏适配与真实播放**：检查图片的主体、来源真实性/主题准确性、实际列表尺寸下的焦点裁切、比例、圆角、清晰度、叠字对比度与明亮表现；按第 6.9 节分别查看 `featured`、`standard`、`compact` 尺寸下的关键对象是否完整可辨。不能只在单一原始尺寸或单张接触表中检查；不同尺寸应使用合适比例和裁切，不拉伸、不误导内容，也不借变尺寸反复复用同一图片。视频封面必须来自对应片段或准确表达该片段，核验解码、方向、播放/暂停、首帧、时长、音量、中断和控制器释放。缩略图与原图合理分层，视频按用途裁切与选择格式，保留既定画面质量，不设安装体积、内存或加载时间的性能预算；主题确需字幕时同步检查字幕。
6. **至少两轮实际调整**：按第 6.7 节执行候选筛选和页面适配两轮，记录淘汰、替换、裁切、封面与压缩决策及前后证据。若复查仍有明显重复、模糊、错题或错误播放，继续修正；不把“轮次已满”视为资源质量通过。
7. **许可和离线保证**：每个最终随包资源有可核对来源、许可、归因和清单引用，发布 App 使用审核后的本地资源。某供应商不可用时按第 10.6 节切换其他合规来源，不直接取消真实照片需求；有限尝试仍失败时仅以明确标记的开发资源继续其他工作，受影响照片要求保持 `Blocked`。不得用版权不明、损坏素材或未标注占位图充当正式成果，不复用一张图填满所有内容，也不把媒体上传给 Stargate。
8. **交付去重结果**：分别报告图片数、视频数、独立来源内容数、展示次数、完全重复组、近似重复组、已替换项、必要复用位置/理由、许可与实际显示/播放检查结果。重复率的分母和排除项须说明，未执行的检查如实记录；无理由的可见重复必须修正后才能标记对应资源验收 `Verified`。

#### 10.5.1 欢迎页主视觉质量与 256KB 压缩交付（硬门槛）

欢迎页按第 7.1 节自由构图，图片资源须先达到成图质量，再适配布局和压缩。此处适用于实际 Dart Welcome 与独立欢迎 HTML 的主图、插画、场景及主要背景图片，不能只验 Logo 或背景动画：

- **选图看内容与质感**：逐张查看原图及实际展示尺寸，确认主题对象准确、结构可信、细节清楚，材质/笔触、光影与色彩层次协调，主体与环境有完整关系；有意留白服务排版，不靠空背景和孤立小图填版。可采用许可摄影、精细原创插画、许可艺术素材或第 6.12 节符合当前用途的合格成图，具体画风由主题决定。真实照片仍按第 10.6 节取得；Stargate 仍限既定 Logo/页面背景装饰用途，不因欢迎主图新增生图批次或冒充内容摄影。
- **简图不能充当主视觉**：禁止把简单线条、轮廓、圆/矩形等几何形状或纯色块拼接当作精致图片，覆盖 AI、手工、SVG、Canvas/CustomPainter、代码绘图及转存的位图。给简图叠渐变、投影、模糊、纹理噪点或动画也不能替代主体造型与细节。语义图标、数据/步骤图解及辅助装饰按原职责保留，不计作主视觉图片完成。自绘插画也须达到同样的主体、材质与构图质量，不能以“原创”豁免。
- **先分配素材再合成页面**：在现有资源记录和 Welcome 逐页执行文档中对应章节、主题主体、原图、最终文件、裁切焦点与实际展示位置；同一原图的改色/镜像/裁剪不算独立素材。按其自身内容安排不同章节的图文关系，不把所有图片硬塞进同规格卡片。`lib/welcome.dart` 是唯一运行 Welcome；`aduit/welcome.html` 只是同一设计的独立交付表示，可从同一合格原图导出不同尺寸/压缩版本，保留派生关系；正式 Logo 仍只取自唯一品牌源。
- **256KB 按完整 HTML 计算**：`aduit/welcome.html` 完整 UTF-8 文件必须严格小于 262,144 字节，包含 HTML、内联样式/脚本与所有 Base64 图片。先测非图片内容及 Logo 占用，再从余量分配各图预算；Base64 正文长度为 `4 × ceil(图片字节数 / 3)`，另计 data URI 前缀与标记，不能仅将原始图片字节相加或按磁盘显示的四舍五入值验收。不预设所有图片同尺寸或同质量，主视觉优先保留有效细节。
- **允许图片压缩，并复验结果**：按实际可见尺寸裁切/缩放，依据透明度及目标浏览器解码能力选择合适的 JPEG、WebP 或 PNG，清除无用元数据并调整质量。保留原图与派生记录，每轮压缩后解码查看主体、细节、渐变色带、边缘和文字叠层可读性；将最终字节嵌回 HTML 后重新测整个文件。超限则继续优化图片尺寸、编码及冗余代码，不能改用网络请求、删除必需章节/行为或换成线条/色块拼图；不能把压缩后的马赛克、模糊或严重色带当成合格成图。
- **交付分别取证**：在现有资源/精修记录保存各最终图片的格式、尺寸、压缩前后字节、原图关系，以及最终 HTML 精确字节数和完整性检查结果；按第 12.1 节在四指定视口离线查看全部章节和解码图片。Dart 使用独立适配的随包 assets，不受 HTML 的 256KB 文件预算约束，仍须检查画质、圆角、实际加载和当前 iPhone 构建；不得因 HTML 压缩而把 App 主图也降成低质缩略图。

### 10.6 必须搜索、下载并展示第三方真实照片

允许直接使用 Google 图片搜索，按主题、真实对象与使用场景发现并拉取素材；查看对应原图及来源页，确认许可与可用下载方式后，将原文件保存到当前项目 `assets/media/<module>/`。搜索结果可用于快速获取原图地址，但不能把“Google 搜到/可下载”当作授权，也不把无来源的搜索缩略图、水印预览或失效临时链接当成成品。记录 Google 查询与原始权利来源；Google 不可用时继续既有合规来源，不以某一搜索入口失败阻断任务。正式 App 不请求 Google 图片或来源网站加载图片。

本项目必须从第三方网站或其正式资源 API 搜索、核验许可并下载 App 内容区随包展示的真实摄影与主题照片，展示与用户主题有关的实物、人物、场景或实际活动。Stargate `http://stargate.local:3100/` 用于生成 Logo，以及第 6.11 节选择生图路线的页面背景装饰（背景场景也可直接动画生成、程序制作或第三方组件合成，工具不限，但每页另保留真实半透明装饰图片）；绝不可用于生成或替代 App 内容照片、摄影封面、内容背景摄影、视频帧或其他本地主题照片。内容照片必须来自第三方来源页并留存许可证据。真实实物图指实际摄影，不是“看起来像照片”的 AI 图、矢量图、Emoji、渐变色块、占位图或 App 界面截图。Logo、页面装饰与内容照片的用途及来源不可混淆；插画、原生图标、代码绘制的矢量符号、主题渐变和 Emoji 可按视觉规格用于界面，不要求从照片网站取得，也不能计作真实照片或替代必需照片。

1. **规划明确照片需求**：将此要求纳入完整思维导图与需求覆盖表。为首页重点展示、内容分类、主要列表/卡片、详情或真实任务示例中需要说明主题对象的位置建立下表，每个选定的主题内容类别必须有贴题的真实照片；Settings、协议和纯操作控件不强加装饰照片。工具型产品也要在适用的主题说明或任务示例中实际展示真实场景，不能把全部照片需求记为 `N/A`，也不为凑图增加无关业务模块。根据内容规模确定独立照片数量并随方案一并确认，不以只下载一张无关图片算完成。

   | 需求 ID | 页面/展示位 | 真实主题对象 | 必需独立照片数量 | 英文查询词/目标网站 | 比例/清晰度/预算 | 许可/归因方式 | 最终资源 ID/实际截图/状态 |
   | --- | --- | --- | --- | --- | --- | --- | --- |
   | `[R-photo]` | `[screen + placement]` | `[actual object or scene]` | `[count based on distinct content]` | `[query + source]` | `[display requirements]` | `[verify from source]` | `[planned before approval; actual evidence after implementation]` |

2. **真正执行网站搜索**：思维导图确认、Logo 优先阶段结束后，根据实际主题对象、用途、拍摄视角和构图生成英语关键词，使用可用搜索工具、浏览器或网站正式 API 查询 Pexels、Pixabay、Unsplash、Wikimedia Commons 等合规来源。选择摄影分类，查看候选来源页与图像本身；搜索结果摘要、首页链接、网站列表或写下查询词不等于完成搜索与素材使用。无关风景、错误物种/商品、带无授权品牌/肖像、明确标注 AI 生成、插画和水印预览均淘汰。图片必须准确对应所展示的内容，不能凭相似外观给无依据的对象贴标签。
3. **没有 API Key 也不能跳过**：只检查凭据是否存在，不输出密钥；可用时使用正式 API，不可用时继续用公开网页发现素材、核对来源页并按网站许可和允许的下载方式取得文件。一个来源失败、限流、无结果或素材不适用时，尝试其他独立来源；宣布网站照片不可取得前至少实际尝试两个独立的合规来源，并记录其查询和可观察结果。403、429、超时、登录墙、验证码或许可证据缺失时切换来源或同主题英语同义查询，不绕过访问限制、不反复请求同一失败地址，不用来源不明的搜索缩略图替代。完全没有可用网络/浏览工具时，记录该能力缺失证据，不虚构已经搜索过两个网站。沿用第 0.6 节的请求与重试上限，失败后继续独立开发，不无限等待。
4. **先核许可，再下载原始文件**：搜索引擎仅用于定位来源，图片公开可见不代表可用于 App。逐项核对源文件的使用许可、App 随包再分发、商业使用、修改与归因条件以及适用肖像/商标限制；不能只引用网站首页的一句“免费”。不允许相应用途或无法确认许可时换候选。取得正式允许下载的图片，检查 MIME/签名、尺寸、文件完整性和哈希，按比例裁切/压缩并保留来源关系；按第 10.1 节登记，许可要求署名时用符合自然英语策略的准确署名兑现义务。
5. **落盘并实际接入 App**：图片先保存到项目专属 `~/Downloads/<sanitized-project-name>/content/<module>/`（本机为 `/Users/admin/Downloads/<sanitized-project-name>/content/<module>/`），核验后复制到 `Target project root/assets/media/<module>/`，更新 `pubspec.yaml`、资源清单、种子数据与页面资源映射，让确认方案中的真实照片展示位真正加载这些文件。不能只把图下载进公共临时目录、写入 JSON 却不绑定页面，或仍用旧插画/色块覆盖照片；不以运行时外链热链代替随包资源。首装且未拍摄/导入任何内容时，核心内容页面也须可看到主题照片；样例与用户私有媒体保持明确区分。
6. **保存搜索到展示的证据**：在目标工程 `.codex-work/resource-search.md` 或等价非公开记录中保存真实查询词、网站与访问方式、查询/下载时间、候选来源页、许可依据、选用/淘汰原因和失败结果；不存密钥或私有令牌。记录照片需求→来源资源→实际文件→页面/展示位→当前构建截图的映射，使用接触表检查来源与重复。搜索记录不放进 `aduit/`；内容照片也不放进 `aduit/site/img/`，该目录继续只保留 `logo.png`。
7. **在真实页面验收**：对照照片需求表检查已下载的独立真实照片、语义匹配和页面实际消费；按第 10.5 节完成两轮筛选/适配、去重、裁切、清晰度、文字对比度与明亮检查。在可运行环境中逐项打开主要展示位，保存能看到照片的截图，并断网检查随包加载；模拟器不可用时继续文件、配置和引用核验，但运行展示验证保持 `Blocked`，不得用接触表冒充 App 截图。下载数量、文件存在、图片 Widget 存在或漂亮渐变都不能单独证明通过。

#### 10.7.1 图片显示闭环与占位图失败定位

图片检查分为入库、页面接入和最终构建三个时点；接入当轮就验证，不把已知灰图留到交付前。最终验收按“有效文件 → 精确引用 → 实际打包 → 成功解码 → 页面真实显示”逐层取证。磁盘能打开、构建成功、存在 `Image` Widget 或 fallback 看起来完整，都不能跳过后续层级。

GIF 同样执行以下闭环，但首帧解码成功只证明静态可见。动图须按真实格式解码并检查多帧、帧时序、循环及当前 iPhone 中的实际运动；预览图不能冒充播放成功。验证页面离开/返回、前后台、暂停/继续、系统减少动态开启时的静态预览及关闭后的恢复，并在 `.codex-work/image-load-audit.json` 的对应展示位记录动图/预览路径、实际播放结果与录屏/不同帧证据。Flutter 普通图片组件若不能正确暂停，应采用可控的播放/帧调度实现；HTML 通过响应 `prefers-reduced-motion` 切换内嵌动图与静态图，不能误以为 CSS `animation: none` 会停止 GIF。损坏、伪 GIF、仅有一帧却被声明为动图、播放卡死或离线失效均须修复后复验；正文与主操作不能被媒体失败阻塞。

1. **有效文件与资源类型**：逐个核对实际消费的独立图片，检查非零字节、MIME/签名、尺寸、哈希及真实解码；HTML/JSON 错误响应、下载预览页、截断文件和伪扩展名均失败。位图用当前 Flutter/iOS 实际使用的解码链验证；SVG 用实际 SVG 组件解析渲染，不冒充位图。原生 AppIcon/启动资源按对应资源集核验；独立 aduit/welcome.html 按第 12.1 节解码 Base64，并以离线页面中的 `complete`、`naturalWidth > 0` 和可见截图核验，不给独立 HTML 新增工程文件或远程图片依赖。
2. **精确引用与实际打包**：逐项关联 page ID/路由、内容 ID、展示位、资源 ID、磁盘相对路径和运行时 asset key，检查 Dart、JSON、种子数据、派生封面和背景装饰的引用一致。大小写、扩展名、空格及文件名按真实目录条目逐字核对，不能以 macOS 上路径能打开为准；Flutter asset key 不以 `/` 开头。检查 `pubspec.yaml` 的缩进和 `flutter/assets` 声明：声明父目录不能视为递归包含任意深度子目录，逐个声明实际子目录或文件。检查当前构建的资源清单与 App bundle，不假定一定有 `AssetManifest.json`；可用当前版本的 `AssetManifest.loadFromAssetBundle(rootBundle)` 或等价方式枚举，再用真实 key 加载、解码。代码生成/动态拼接 key 和适用的 package 资源前缀也须核对；随包图不能引用开发机绝对路径、临时下载目录、失效沙盒路径或运行时图片热链。
3. **加载成功必须可观察**：App 自有图片组件及背景/装饰加载链须区分 pending、decoded/首帧、error，不以完成网络请求、结束动画或显示回退组件作为成功。记录实际 `ImageProvider`/asset key、页面/内容/展示位、解码尺寸和原始异常到脱敏开发日志或运行记录；不把路径和异常暴露给用户。通过 `ImageStreamListener` 的图片/错误回调、`frameBuilder` 的非空 frame 或等价实际渲染机制取证；`errorBuilder`、背景 `onError` 和捕获异常不得静默吞错，fallback 仍计为失败。`precacheImage` 的 Future 结束也不单独证明成功，必须记录其错误回调。背景透明装饰可保持设计透明度，但照片零尺寸、全透明、被遮盖、完全裁掉或被占位层覆盖都不算显示。
4. **当前构建逐展示位运行**：在当前复用的现有 iPhone 运行目标完整重建并安装更新，标明构建标识/产物与资源哈希；冷启动清除内存缓存影响后断网验证。需要首装验证时仅使用可丢弃的本任务真实 App 调试安装，不卸载含真实用户数据的 App。逐个打开所有主要目的地、详情、筛选/搜索结果、横滑末端、轮播各卡和懒加载列表底部，覆盖当前已实现内容的全部计划展示位，不只看首屏或源码 Widget 数，必须实际点击并查看结果。按目标图片首帧/错误状态有界等待，不依赖持续渐变/呼吸动画的 `pumpAndSettle` 全局静止；超时或持续占位记失败并定位，不改成成功、不添加生产等待。随包图不能依赖此前在线缓存或再次联网；按页面逐页、分批进行真实 App 交互并记录结果，不把全库预加载搬进生产启动流程。用户私有照片只用真实测试导入/拍摄结果另验，不将合理空状态或模拟器相机不可用冒充图片解码缺陷。
5. **先定位再修复，复验失败继续修**：按文件 → key/数据绑定 → 声明/打包 → 解码 → 布局/叠层/缓存的顺序查找断点，给出可复现失败和对应修正。路径、注册、旧构建、错误回退或布局问题先修实际原因，不反复下载原本有效的照片，也不靠换 Logo、Emoji、灰块或隐藏错误掩盖。仅确认文件缺失/损坏、题材错误、无许可或无理由重复时走第 10.6 节真实第三方照片替换；Logo、转用插画和页面背景分别走既有品牌/装饰规则，不能混用来源。每个故障使用稳定展示位 ID，记录失败证据、已确认原因、实际修改文件/资源、修改后构建及同位置复验结果；只有看到目标图片正常显示并回归共享消费者后才关闭该故障。复验仍失败就基于新证据继续修，换诊断/修复方法，不以记录 `Failed`、达到最低轮次、反复重跑相同命令或“代码已修改”结束。针对实际缺陷使用测试 fixture 验证错误大小写/缺 key、未打包子目录、损坏或伪图片以及被 fallback 吞掉的异常会使验收失败；故障注入只用于测试，不破坏正式资源。
