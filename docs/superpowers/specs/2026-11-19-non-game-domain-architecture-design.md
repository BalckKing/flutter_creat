# 非游戏七领域分流架构设计

> 状态：待用户审阅
>
> 本文是 Flutter 工程生成工作流的架构规格。它描述领域分流契约、文档装载顺序、生成边界和验收接口；不代表当前资料包已经具备真实 Flutter App、iOS 工程或 Simulator 运行证据。

## 1. 目标与问题边界

现有工作流只把项目分为游戏和非游戏两大类。非游戏项目虽然已有统一的复杂成品、真实能力、视觉质量和运行验收要求，但缺少领域级产品契约，容易出现不同主题共用相同的欢迎页、底栏、卡片列表、详情页和结果页，只替换名称、颜色、Logo、图片或文案。

本次架构将非游戏项目拆为七个主领域，并保留游戏独立分支：

1. `tool`：工具
2. `education`：科普教育
3. `food`：美食
4. `travel`：旅游
5. `sports`：体育
6. `fitness_health`：健美健康
7. `photo_video`：摄影与录像

每个非游戏项目先加载统一的非游戏基础契约，再加载一个主领域契约，最后按需加载零到两个受控副领域契约。主领域决定主任务、产品身份、主导航和页面骨架；副领域只补充与主领域有明确数据关系的能力，不承担第二套完整产品。

本次不把领域契约变成通用页面模板，也不把七个领域变成七套互相复制的独立流程。基础层负责不可降低的质量底线，领域层负责不可互换的任务、对象、结果、能力和视觉表达。

## 2. 设计原则

### 2.1 基础契约先行

非游戏基础契约是所有 `project_type: non_game` 和 `project_type: mixed` 项目的前置输入。领域文档不得重复定义或降低基础契约的硬门槛；出现冲突时，基础契约的更严格规则优先。

基础契约继续继承现有工作流的全局要求：

- 复杂完整成品：至少 12 个独立功能页面、8 个核心模块、3 层有意义的任务/内容结构、12 个分类或情境族、120 个有效领域条目/案例/场景、12 条不同结果的端到端任务、6 种有价值的信息或交互形式。
- 每个独立页面必须有不同的结构骨架，不能通过换色、换图、换标题或换底栏伪造差异。
- 每项适用的 iOS 能力必须有真实入口、真实消费者、权限流程、拒绝回退、运行证据和记录；不适用能力必须记录主题与平台依据。
- 页面必须保持明亮主题、真实渐变消费者、半透明主题图片点缀、主题化动态效果、真实本地素材、无障碍、离线和错误恢复。
- 项目只生成 iPhone、Portrait 方向；最低 iOS 版本、`MinimumOSVersion`、Podfile、照片权限宏和 ATT 清理规则继续执行。
- 搜索仍是条件能力，不因领域拆分而默认为选中；只有领域工作流确实需要本地关键词定位时才声明 `Search: Selected`。
- 协议页继续直接进入唯一 App 内 WebView，使用具体项目名 HTTP URL，不经过协议索引页或中间页。
- 当前资料包没有实际 App 时，运行、产物和 iPhone 证据只能记录为 `Not verified`，不能由静态脚本替代。

### 2.2 领域差异必须落在任务和结果

领域差异至少要体现在以下六个维度中的四个：

1. 核心对象和对象关系；
2. 主任务的输入、过程和结果；
3. 页面骨架与信息组织方式；
4. 数据模型、持久化和回访状态；
5. 真实 iOS 能力、第三方 SDK 或组件消费者；
6. 视觉语法、媒体比例和主题化动效。

只改变 Logo、颜色、渐变、字体、图片、文案、卡片尺寸、底栏形状或页面标题，不构成领域差异，也不能通过领域验收。

### 2.3 主领域与副领域受控组合

每个非游戏项目必须指定一个 `primary_domain`。可以指定零到两个 `secondary_domains`，但副领域不能重复主领域，不能重复彼此，也不能创建第三层领域。

主领域负责：

- 首要用户问题和签名动作；
- 主导航和主工作区；
- 主要领域对象与结果；
- 至少一条从 Welcome 到结果回访的完整任务流；
- 页面清单中的核心页面骨架；
- 设计系统的主视觉语言。

副领域只能负责：

- 与主领域对象存在明确关系的补充能力；
- 可被主领域任务触发或回访的附加页面/模块；
- 能力矩阵中有实际消费者的辅助能力；
- 与主领域共享数据但不改变主领域身份的结果表达。

副领域不得：

- 复制另一套完整主导航；
- 添加与主任务无关的页面以凑数量；
- 只把副领域名称写入文案而没有对象关系和真实动作；
- 覆盖主领域的核心视觉和路由边界。

## 3. 项目类型和领域配置契约

### 3.1 顶层类型

项目类型仍只有三种：

- `non_game`：只有非游戏领域能力；必须有领域配置。
- `game`：只有游戏能力；使用现有游戏引擎必要性与沉浸式游戏大厅契约，不创建非游戏领域配置。
- `mixed`：有真实游戏模块和至少一个非游戏领域能力；必须同时有游戏契约和领域配置。

`mixed` 的主领域仍是非游戏主领域，游戏只能作为明确可达的独立任务模块；游戏不能隐藏在 Settings、About、二级菜单或不可见路由中。

### 3.2 机器可读领域配置

实现页面前，项目根目录的 `.codex-work/domain-selection.json` 必须存在，结构如下：

```json
{
  "schema_version": 1,
  "project_type": "non_game",
  "primary_domain": "travel",
  "secondary_domains": ["photo_video"],
  "base_contract": {
    "id": "non_game_base_v1",
    "path": "工作流文档/12-非游戏基础契约.md",
    "status": "Loaded"
  },
  "overlays": [
    {
      "id": "travel_v1",
      "domain": "travel",
      "path": "工作流文档/16-旅游领域契约.md",
      "status": "Loaded"
    },
    {
      "id": "photo_video_v1",
      "domain": "photo_video",
      "path": "工作流文档/19-摄影与录像领域契约.md",
      "status": "Loaded"
    }
  ],
  "resolved_contract_order": [
    "non_game_base_v1",
    "travel_v1",
    "photo_video_v1"
  ],
  "conflict_policy": "base_floor_primary_owner_secondary_extension",
  "evidence": [
    ".codex-work/domain-load.md",
    ".codex-work/domain-matrix.json"
  ]
}
```

约束：

- `project_type` 必须为 `non_game` 或 `mixed` 才能存在领域配置。
- `primary_domain` 必须是七个注册领域之一。
- `secondary_domains` 必须是数组，最多两个，不能重复、不能包含主领域。
- `base_contract.id` 必须为 `non_game_base_v1`，且状态为 `Loaded` 才能开始页面设计。
- `overlays` 必须与主领域和副领域一一对应，不能加载未声明的领域文档。
- `resolved_contract_order` 必须严格是基础契约、主领域契约、按用户声明顺序的副领域契约。
- `mixed` 项目必须同时存在 `.codex-work/game-engine.json`；`non_game` 项目不得创建游戏契约、游戏场景或游戏入口。
- 所有路径必须是工作流资源根或项目内的安全相对路径，不能指向临时下载目录、公共 Downloads、其他项目或符号链接。

### 3.3 冲突和覆盖规则

契约解析采用以下优先级：

1. 全局用户硬性要求和当前任务输入；
2. 非游戏基础契约的硬门槛；
3. 主领域契约的领域规则；
4. 副领域契约的补充规则；
5. 项目实际能力、平台限制和运行证据。

副领域不能降低基础契约或主领域的页面质量、内容深度、能力验收和无障碍要求。若副领域与主领域对同一对象、路由、权限或视觉令牌提出冲突，必须在 `.codex-work/domain-matrix.json` 中记录冲突、选择主领域所有权、保留的副领域扩展和被拒绝的内容；不能静默合并。

每个领域对象、动作、路由、能力和资源必须标注 `owner_domain`。一个对象只能有一个所有者，副领域通过关系或事件消费主领域对象，不复制对象主键或制造平行事实。

## 4. 非游戏基础契约

新增 `工作流文档/12-非游戏基础契约.md`，内容以可执行契约为主，至少包括：

### 4.1 统一产品闭环

每个非游戏项目必须完成：

```text
发现/选择领域对象
  → 创建或输入真实任务
  → 处理、分析或编排
  → 生成可解释结果
  → 保存、修改、分享或回访
  → 在历史/成果页再次使用
```

基础契约规定数据状态、错误/取消/重试、离线冷启动、前后台恢复、清除数据和资源释放，但不规定所有领域使用同一套页面或导航。

### 4.2 页面和模块底线

基础契约负责检查页面数量、模块数量、内容数量、任务数量、交互形式、分页边界、稳定 ID、内容去重、页面骨架差异和路由可达性。领域文档必须把这些数量映射到领域对象和真实任务，不得用无关条目、重复文案或空壳页面凑数。

### 4.3 能力矩阵

基础契约要求逐项评估照片/相机、麦克风/语音、通知、定位/地图、日历/提醒事项、联系人/分享、文件/文档、蓝牙/NFC、运动/HealthKit 以及其他主题相关能力。领域契约只负责说明领域依据和实际消费者，最终仍写入统一的 `.codex-work/capability-matrix.json`：

```text
capability
real_tool_or_sdk
version
license/source
actual_consumer
fallback
runtime_evidence
formula_record
status
owner_domain
domain_reason
```

### 4.4 基础视觉和交互底线

基础契约保留明亮色调、真实渐变令牌、半透明主题图片、主题化动态场景、真实图片和媒体加载、圆角、44pt 触控区域、Dynamic Type、VoiceOver、Reduce Motion、对比度、页面独立骨架、Launch/Welcome/Initialization/Settings/协议容器边界以及当前 iPhone 运行验收。领域文档必须将这些规则翻译为领域对象、材质、动效轨迹和交互反馈，不能只写“精致美观”。

### 4.5 设计系统和组件选择

领域选择完成后，先使用 `awesome-design-md` 选择或创建 `DESIGN.md`，再使用 `ui-ux-pro-max` 生成 `design-system/<slug>/MASTER.md`，完成九类 UI/UX 评测后才能选第三方组件。领域契约可以推荐组件，但不能把包名写入 `pubspec.yaml` 当作实现；组件必须有真实页面消费者、精确版本、许可证、runtime marker 和当前 iPhone 证据。

## 5. 七个领域契约

每份领域契约必须使用同一结构，确保生成器和校验器可以按字段读取：

1. 领域身份和用户问题；
2. 领域核心对象、字段和关系；
3. 主任务输入、过程、结果和可回访产物；
4. 至少八个领域核心模块的职责；
5. 页面骨架清单与独有结构说明；
6. 领域分类/情境族和 120 条内容/案例/场景的生成策略；
7. 领域能力矩阵和拒绝回退；
8. 领域视觉语法、图片/媒体比例、渐变、动效和点击反馈；
9. 空态、错误、取消、重试、离线、权限拒绝和清除恢复；
10. 数据、路由、持久化和跨页面状态；
11. 领域组件/SDK选择条件；
12. 领域验收矩阵和证据路径。

### 5.1 工具 `tool`

核心结果是“可复核的转换、计算、规划或诊断产物”，而不是单个输入框。对象包括 `ToolDefinition`、`InputProfile`、`OperationRun`、`ResultSnapshot`、`SavedPreset` 和 `ExportArtifact`，关系为“工具定义 → 输入配置 → 执行记录 → 结果快照 → 预设/导出”。

主任务必须支持不同输入产生不同、可解释、可比较的结果，并允许保存或分享一个结果快照。页面应以工作台、参数分区、实时结果、对照视图、历史运行和导出流程组织，不能退化为列表/详情壳。优先评估文件导入、分享、图表和本地通知；不适用能力必须根据工具的输入来源和风险边界记录依据。

### 5.2 科普教育 `education`

核心结果是“理解、实验、测验和复习进度”，而不是文章阅读完成。对象包括 `LearningPath`、`ConceptNode`、`LessonScene`、`ExperimentRun`、`QuizAttempt` 和 `ReviewSchedule`，关系为“学习路径 → 知识节点 → 课程/实验 → 测验 → 复习计划”。

主任务必须让用户从一个知识目标进入分层解释、图解或交互实验，得到可观察的结果并形成复习记录。页面应使用知识地图、时间线、实验台、分步讲解、测验反馈和进度回看等不同骨架；音频、视频、图表或时间线按主题选择真实消费者，不能用文章列表替代知识关系。

### 5.3 美食 `food`

核心结果是“从目标菜品到可执行烹饪和复盘”，而不是菜谱卡片浏览。对象包括 `Recipe`, `Ingredient`, `ServingPlan`, `PrepChecklist`, `CookingSession`, `TimerTask` 和 `ShoppingPlan`，关系为“菜谱 → 食材/份量 → 备料 → 步骤/计时 → 购物/复盘”。

主任务必须支持份量换算、步骤推进、计时和完成结果，并能回到购物清单或烹饪记录。页面应分别表达菜谱探索、食材关系、备料台、步骤计时、厨房进行中、替代方案和复盘；相机/照片、语音、通知、分享按真实功能选择并提供拒绝回退。

### 5.4 旅游 `travel`

核心结果是“从地点发现到路线、行程和现场记录”，而不是地点图片列表。对象包括 `Place`, `RoutePlan`, `ItineraryDay`, `OfflinePack`, `FieldNote` 和 `TripMemory`，关系为“地点 → 路线 → 行程日 → 离线包 → 实地记录 → 旅行回忆”。

主任务必须实际加载真实地图 SDK、许可地图瓦片或许可地理数据，并完成缩放、平移、定位、标记、路线或图层中的适用动作。页面应采用地图/空间总览、路线编辑、行程时间线、离线准备、现场记录、回忆展陈等不同骨架；定位、日历、照片、分享和离线能力必须按真实入口、权限和回退记录。

### 5.5 体育 `sports`

核心结果是“可执行的训练、赛事或运动表现记录”，而不是指标卡片墙。对象包括 `SportProfile`, `TrainingPlan`, `Session`, `Drill`, `PerformanceMetric`, `Goal` 和 `ReviewReport`，关系为“运动项目 → 计划 → 训练/赛事 → 指标 → 目标 → 复盘”。

主任务必须包含准备、进行中、完成、复盘和下一次行动。页面应区分计划编排、训练计时、动作/技术演示、实时记录、趋势分析、目标反馈和复盘报告；运动数据、计时、通知、媒体或 HealthKit 只在有真实消费者时接入。

### 5.6 健美健康 `fitness_health`

核心结果是“长期习惯、训练、营养和恢复的可解释变化”，而不是通用健康 Dashboard。对象包括 `HealthGoal`, `Habit`, `Workout`, `NutritionLog`, `RecoverySignal`, `HealthMetric` 和 `RiskNote`，关系为“目标 → 习惯/训练/饮食 → 指标与恢复 → 风险提示 → 趋势回访”。

主任务必须区分每日行动、周期趋势、恢复状态和安全提示，避免把医疗诊断伪装成建议。HealthKit、通知、日历、相机/语音等能力必须明确数据边界、授权时机、拒绝回退和隐私文案；不能因为主题名称而自动申请健康权限。

### 5.7 摄影与录像 `photo_video`

核心结果是“拍摄、导入、整理、编辑、编排和回看作品”，而不是图片卡片墙。对象包括 `CaptureProject`, `MediaAsset`, `Take`, `TimelineClip`, `EditVersion`, `ShotPlan` 和 `ExportPackage`，关系为“拍摄计划 → 媒体资产 → 时间线/编辑版本 → 作品包 → 导出/分享”。

主任务必须至少完成一次本地拍摄或相册导入、媒体预览、编辑/标注、版本保存和导出/分享中的适用闭环。相机、相册、麦克风、视频时间线、文件、分享和真实媒体 SDK 按实际 API 接入；页面需区分取景/导入、素材整理、时间线、编辑器、元数据、作品回看和导出状态，不能只使用图片列表。

## 6. 生成器和文档装载流程

生成器执行非游戏项目时按下列顺序工作：

1. 识别 `project_type`；若为 `game`，跳过领域装载并执行游戏契约；若为 `non_game`/`mixed`，进入领域选择。
2. 读取基础入口和所有既有全局正文，建立一次性章节索引、输入指纹和依赖图。
3. 校验主领域、副领域数量、注册表 ID、项目类型和用户主题的匹配关系。
4. 读取 `12-非游戏基础契约.md` 全文。
5. 读取主领域契约全文，再按声明顺序读取副领域契约全文。
6. 生成 `.codex-work/domain-selection.json`、`domain-load.md`、`domain-matrix.json`、`domain-trace.md` 和页面/能力/数据映射。
7. 在设计页面前完成 `DESIGN.md`、`MASTER.md`、UI/UX 评测和领域视觉/能力决策。
8. 先实现主领域的垂直任务切片，再实现其余模块和副领域扩展；副领域不得先于主领域生成独立产品壳。
9. 按统一基础验收和领域验收分别记录计划、实际实现、实际验证和缺口。
10. 只有所有适用领域硬门槛通过或明确记录 `Blocked`/`Not verified` 后，才进入既有最终材料、截图、iOS 权限核验和 Git handoff 顺序。

## 7. 校验器和回归范围

新增 `flutter-engine-runner/scripts/validate_domain_selection.py`，并添加对应的 `flutter_check/test_validate_domain_selection.py`。校验器至少检查：

- `.codex-work/domain-selection.json` 存在、JSON 合法且 `schema_version` 为 1；
- `project_type`、主领域、副领域、最大数量和重复约束正确；
- 基础契约 ID、领域注册表 ID、路径和状态完整；
- 装载顺序为基础 → 主领域 → 副领域；
- `mixed` 有游戏契约，`game` 没有领域配置，`non_game` 没有游戏配置；
- 每个领域契约包含核心对象、主任务、页面骨架、能力矩阵、视觉规则和验收矩阵；
- `domain-matrix.json` 为对象、动作、路由、能力和资源声明唯一所有者；
- 领域能力行包含真实工具、版本、来源/许可证、消费者、回退和运行证据字段；
- 领域页面不能声明通用壳替代独立骨架；
- 缺少真实运行证据时状态只能是 `Not verified` 或其他未通过状态，不能静态标 `Verified`。

## 8. 迁移与兼容

现有只有 `project_type: non_game` 的旧项目在没有领域配置时，不能静默选择领域并宣称通过。迁移过程应：

1. 根据用户主题和已确认的产品核心任务选择主领域；
2. 生成领域配置和加载记录；
3. 将现有页面、对象、能力和资源逐项标注 `owner_domain`；
4. 把无法归入领域的内容记录为待修复或删除候选，不在迁移中自动塞入无关功能；
5. 重新检查导航、页面骨架、能力矩阵和领域证据；
6. 在真实 App 运行证据缺失时保持 `Not verified`。

不修改用户既有业务数据、协议 URL、Logo 资源、`.codex-work/` 目录名、`aduit/` 交付白名单或最终 Git handoff 的“不提交代码”规则。领域文档只是生成和验收契约，不能成为 App bundle、运行时依赖或最终交付材料。

## 9. 非目标

- 不在本次架构中为七个领域预制一套可直接复制的 UI 页面。
- 不强制所有领域使用同一种路由、存储、媒体 SDK、地图服务或游戏引擎。
- 不因为领域拆分而默认启用搜索、相机、相册、麦克风、定位、通知、HealthKit 或其他权限。
- 不把领域数量、页面数量或内容数量当作真实运行质量的替代；所有硬门槛仍需要当前 iPhone 证据。
- 不创建真实 Flutter App、iOS 工程或模拟器证据来填补当前资料包缺口。

## 10. 验收结论标准

本架构只有在以下条件同时满足时才可标记为设计层 `Accepted`：

- 七个领域各自有明确、可执行、不可互换的领域契约；
- 基础契约不降低现有全局硬门槛；
- 主/副领域配置、装载顺序、所有权和冲突策略可机器校验；
- 游戏、非游戏和混合项目边界清晰；
- 生成入口、数据架构、视觉规则、能力矩阵、验收顺序和安装副本均有对应修改点；
- 校验器有通过和失败测试夹具；
- 规格中的“真实 iPhone 运行证据”仍明确区分为当前资料包不可验证的事项。

实现完成后，最终报告必须分别列出：基础契约状态、主领域状态、副领域状态、领域加载状态、领域矩阵状态、领域专项验收状态、真实运行证据缺口，以及不影响本地资料包回归的外部阻断项。
