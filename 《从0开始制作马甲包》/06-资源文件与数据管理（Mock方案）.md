# 06 - 资源文件与数据管理（Mock 方案）

本步骤的目标：**组织资源文件，完善数据管理类，使用 Mock 方案提供假数据，通过模拟请求数据展示假数据，让应用看起来像成品。同时，从一开始就用"可批量替换"的方式组织图片和文案，为将来的 B/C/D 等多马甲版本预留极低成本的换皮路径。**

---

## 一、前置输入

- 01 步骤生成的《当前项目信息.md》中的：
  - 文档位置：`docs/当前项目信息.md` 或项目根目录下的 `当前项目信息.md`
  - 项目名称
  - 功能模块列表
  - 品牌与视觉风格描述
- 05 步骤中已经实现的：
  - 数据模型
  - 数据管理类（初版）
  - 功能模块代码
- 你对资源与文案的整体偏好：
  - 图片风格（写实 / 插画 / 扁平图标等）；
  - 文案风格（严肃 / 轻松 / 活泼 / 专业等）；
  - 是否计划支持多语言。

## 二、目标产物

本步骤结束后，你应该得到：

1. **资源文件目录结构**：
   - `assets/{{项目名}}_img/` 目录
   - 图标、图片等资源文件组织清晰
   - **重要：A面资源绝对不能放在 `assets/images` 目录**，该目录是B面专用的

2. **完善的数据管理类（Mock 方案）**：
   - **数据使用 Mock 方案**：
     - **通过模拟请求数据**：使用 `Future.delayed` 模拟网络请求延迟（例如：500-1000ms）
     - **展示假数据**：所有数据都是假数据，不依赖外部接口
     - **假数据存放位置**：**所有数据文件尽量放在 `lib/{{项目名}}/data/` 文件夹里**，方便后续数据替换
     - 数据管理类在 `lib/{{项目名}}/data/repositories/` 目录下，提供假数据
   - **图片展示策略（严格执行）**：
     - **图片不重复展示**：使用的图片展示策略尽量不重复展示，确保不同模块、不同页面使用的图片尽量不重复
     - **图片数组配置**：
       - **每个模块之间留出独立的图片数组配置**，可以放置本地图片路径或网络图片 URL
       - 图片数组放在 `lib/{{项目名}}/data/images/` 文件夹下，按模块分类（例如：`lib/{{项目名}}/data/images/{{项目名}}_home_images.dart`、`lib/{{项目名}}/data/images/{{项目名}}_explore_images.dart`）
       - 图片数组使用 `List<String>` 类型，支持本地图片路径（如 `'assets/{{项目名}}_img/home/home_01.png'`）和网络图片 URL（如 `'https://...'`）
       - **修改图片数组即可生效**：只需要修改对应的图片数组文件，重新运行应用即可看到新的图片
       - 图片数组命名规范：`{{项目名}}_模块名_images.dart`（例如：`huddle_home_images.dart`）
       - 数据管理类从对应的图片数组文件中读取图片，确保图片不重复展示
   - **头像数据**：使用 `https://i.pravatar.cc/150?img=\(Int.random(in: 0...70))`（随机数范围 0-70）
   - **其他封面等图片**：
     - 优先在 `https://www.pinterest.com/` 中搜索真实图片 URL
     - **如果没有找到合适的图片**，可以使用以下 Unsplash 图片 URL：
       - `https://images.unsplash.com/photo-1522771739844-6a9f6d5f14af?w=500`
       - `https://images.unsplash.com/photo-1512436991641-6745cdb1723f?w=500`
       - `https://images.unsplash.com/photo-1506905925346-21bda4d32df4?w=500`
       - `https://images.unsplash.com/photo-1519681393784-d120267933ba?w=500`
       - `https://images.unsplash.com/photo-1534270804882-6b5048b1c1fc?w=500`
   - 文案（标题、描述、按钮文字等）统一使用英文，由 AI 自主创作，要求贴合产品场景、语气统一
   - 数据量充足（列表至少 10-20 条）

#### 禁用词（强制）
- **禁用词列表**：`mock`、`local`、`offline`、`device storage`、`local data`、`mock data`、`local storage`、`offline only`
- **禁用原因**：App Store 审核要求应用不能暴露"本地模拟数据"的技术实现细节，必须呈现为"真实应用"
- **适用范围**：所有用户可见的 UI 文案（按钮文字、提示信息、页面标题、空态文案）
- **不适用范围**：代码注释、变量名、开发文档

3. **文案配置结构（可选，为多马甲做准备）**：
   - 一份「文案配置」结构（可选 JSON / Dart / ARB），例如：
   ```json
   {
     "appName": "Example Reader",
     "home_title": "今日推荐",
     "home_tab_recommend": "推荐",
     "home_tab_favorites": "收藏",
     "profile_title": "个人中心"
   }
   ```
   - 在代码中，页面和组件不再直接写死字符串，而是通过文案访问函数/类（如 `CopyConfig.of(context).homeTitle`）

4. **在 `pubspec.yaml` 中正确声明资源文件**：

```yaml
flutter:
  assets:
    - assets/{{项目名}}_img/
```

## 九、注意事项

### 数据真实性是关键
- 不要使用占位文本（如 "Lorem ipsum"），要使用真实场景的英文内容。
- 图片 URL 要真实可用，不要使用占位图片服务。

### 数据量要充足
- 列表页面至少要有 10-20 条数据，让用户感觉应用有真实内容。
- 如果应用有分页功能，确保有足够的数据支持分页。

### 资源文件命名规范
- **A面资源目录**：所有A面资源文件放在 `assets/{{项目名}}_img/` 目录下。
- **重要：A面资源绝对不能放在 `assets/images` 目录**，该目录是B面专用的。
- 子目录可以按功能模块分类（如 `home/`、`profile/`）。
- **图片资源优先级**：
  1. 优先在 `https://www.pinterest.com/` 中搜索真实图片 URL
  2. 如果没有找到合适的图片，可以使用提供的 Unsplash 图片 URL
  3. 
### 图片数据源规范
- **头像必须使用 pravatar.cc**，确保格式正确：`https://i.pravatar.cc/150?img=\(Int.random(in: 0...70))`
- **其他图片优先使用 Pinterest 的真实 URL**，确保图片可用
- **默认图片作为备选方案**，当找不到合适图片时使用

### 默认图片管理
- **按模块分类存放**，方便管理和替换
- **命名格式统一**：`模块名_01.png`、`模块名_02.png`
- **在 pubspec.yaml 中正确声明**，确保资源文件能被正确加载
- **后续替换**：默认图片的命名格式设计是为了方便后续快速替换本地图片，替换时只需要将新的图片文件放到对应目录，保持相同的文件名即可

### 可配置化设计（为多马甲做准备）
- **不要把文案和资源路径写死在业务代码中**
  - 所有 UI 文案、图片路径尽量走配置层，方便后续批量替换；  
  - 这一步的"抽象程度"越好，之后做马甲的成本越低。

- **命名尽量语义化**
  - `home_title` 比 `text1` 更易维护；  
  - 当你未来打开配置文件时，只看 key 就能大致知道是哪个位置的文案/资源。

- **先完成 A 面，再考虑 B/C/D**
  - 不必一开始就设计得过度复杂；  
  - 确保 A 面能稳定使用配置层后，再按同样结构添加其他马甲的配置文件即可。
